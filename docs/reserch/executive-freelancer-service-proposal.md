# 発注企業・受注側JV・フリーエンジニアをつなぐ開発サービスの追加・修正案

調査日 2026年11月28日 ｜ 対象 Engineering Platform（`c51c75c`）｜ 国内向け商品企画・設計提案

## 1. 何を売るか

**最優先は「依頼を引き受ける」「成果を提出する」「サービスが後工程を引き取る」を一つの案件で完結させること。** 案件を受注したJVの経営責任者は、誰にいくらで何を頼み、顧客に何をいつ届けられるかを判断する。発注企業は専用画面から進捗を確認し、仕様変更や納入に対して自社の判断を返す。フリーエンジニアは、自分への依頼内容・報酬・完成条件を確認し、普段の開発環境で実装して提出する。提出後の顧客説明、条件変更の折衝、リリース調整、受入回答の回収は本サービスの窓口が担当する。

現行カタログには、案件受付、予算配分、ロードマップ、リリース判定、顧客受入、証跡確認がすでにある。欠けているのは、①受託者本人が使う入口、②外注の取引条件と技術成果の結び付き、③提出後に窓口が顧客・リリース責任者・経営層の間で案件を進める仕組みである。この三点を扱う当初の36件に、顧客への情報公開、発注側の承認、契約・知的資産、アプリの引き渡しを扱う24件（37〜60）を加えた。**提案は計60件**。経営層向けには規格に沿ったプロセスの実行と適合準備を支援し、受託者は規格の用語や管理帳票を覚えずに参加できる設計とする。

想定する商流は、**発注企業がこちら側のJVに開発を依頼し、受注側がフリーエンジニアに実装を委託する**形である。案件には実際の契約当事者と、JVを代表して遂行・採算・情報公開を統括する人を登録する。顧客は外注取引に特化する場合と、経営・コスト面でも業務提携する場合がある。サービスは委任された範囲で連絡・進行を担う。公開人材市場の集客、契約当事者になる事業、報酬の預かり・送金を始めるかは別の事業判断になる。

## 4. 誰が何を引き受けるか

国内の受託開発で、会社を指す言葉は**発注者（ユーザ企業）**と**受注者（ITベンダ）**。IPAもこの組合せで、仕様や検収方法の合意を説明している。人を指す画面名は、顧客側で案件の判断に責任を持つ人を**発注側プロジェクト責任者**、こちら側で受注・予算・遂行・情報公開を統括する経営者を**受注側統括責任者（JV責任者）**とすることを提案する。いずれも本サービスで責任の所在を示す呼称で、各社の正式な役職名も併記できる。日程や作業を管理するPMとは担当業務を区別し、同じ人が兼務する場合は案件に記録する。[IPA「情報システム・モデル取引・契約書（第二版）」](https://www.ipa.go.jp/digital/model/model20201222.html)

| 立場 | 本人が行うこと | サービスが引き取ること |
| --- | --- | --- |
| 受注側統括責任者（JV責任者） | 投資、外注枠、委任範囲、重大な納期・予算変更、リリースの事業判断。案件ごとに、どの顧客の誰に何を公開するかを決める。権限内で承認・保留・却下 | 根拠・選択肢・影響額・回答期限をまとめ、判断が必要な時点で依頼する |
| フリーエンジニア（実装の受託者） | 自分の条件を確認して受諾・相談・辞退、外部環境で実装、成果版を提出、合意範囲の技術的な修正を再提出 | 顧客への伝達・交渉、公開作業、顧客受入の回収、進捗報告の転記。本人には次に必要な操作と回答だけを返す |
| 発注企業・外注取引型 | 発注側プロジェクト責任者が契約額・納期・進捗を確認する。自社の担当者がレビューし、権限を持つ承認者・検収者・署名者が各手続きを行う | 継続利用する顧客ポータルに、自社の回答待ち、公開済みの資料、合意版、次の期限をまとめる。単発の参加者には案件限定リンクも使える |
| 発注企業・業務提携型 | 上記に加え、提携契約で定めた共同予算、費用負担、ロードマップ等をJV責任者と確認し、委任範囲で共同決裁する | 契約と公開設定に従って共同管理対象を集計し、各社の決裁記録を分けて保存する |
| VSEが指定する案件窓口・検収者・リリース責任者・運用当番 | 例外的な折衝、委託成果の検収、技術的な公開可否、障害時の復旧を権限に応じて決める。外部承認リンクや既存運用ツールで参加できる | 主担当と代理、応答期限、結果の記録を案件に持つ。VSE側で兼務する場合も、自己承認を禁止する判断は別の権限者へ送る |
| AIと実行基盤 | AIが依頼・回答・リリース説明の案を作る。ルールが配信、期限監視、再送、証跡の照合、承認後の配備依頼を実行する | 条件を確約する権限、リスク受容、検収、最終受入は実際の本人に帰属する。AI停止時は同じ窓口・履歴で定型文と人手に切り替わる |

**引き渡しの成立条件。** 「提出を受け付けました」の時点で提出者に控えを返し、案件窓口に次の担当・期限を割り当てる。配備不能、顧客の無応答、担当者の不在は窓口に残る。本人に新しい作業が発生するのは、合意済みの完成条件に照らした修正、または新条件を本人が承諾した追加依頼の場合である。

### 4.1 JV責任者が決める顧客への公開範囲

「公開」は、案件で指定した相手企業・担当者に見せることを指す。顧客企業を案件に招待した時点では案件名と招待内容のみを表示する。JV責任者が契約上の開示範囲に従って項目・資料の版・相手・期間を選び、相手の画面を確認して公開する。以下は設定の初期案である。

| 情報・操作 | 外注取引型の顧客 | 業務提携型の顧客 | 受注側統括責任者 |
| --- | --- | --- | --- |
| 発注額、契約条件、合意した納期、納入・受入状況 | 自社の契約・公開済みの進捗を閲覧。指定された人が承認・検収 | 同左。共同の変更は契約で定めた当事者が決裁 | 対外提示する版を選定。顧客からの回答を受領 |
| 共同予算・コスト・配分 | 初期非公開 | 合意した費目・期間・集計単位だけを開示。例として共同試験費の予算・実績・各社の負担額 | 公開する集計と根拠を確認し、社内計画との差額を管理 |
| JV内部予算、外注単価、個人別報酬、粗利、社内会議資料 | 初期非公開 | 同じく初期非公開。提携契約で必要とされる項目を個別に審査 | 担当案件で内部権限に従い閲覧。根拠明細を付ける場合も個別指定 |
| 契約・知財・引き渡し | 自社が当事者の契約、公開済みの資産明細、必要な登録手続き | 共同保有・共同利用の条件や双方の担当手続きを追加 | 当事者ごとの原本と公開版を管理し、未合意事項の解消を依頼 |

例として契約額1,000万円、JV内部予算700万円、委託費300万円の案件では、外注取引型の顧客に見える金額は契約額1,000万円。提携契約で共同試験費80万円の折半を合意した顧客には、追加で共同試験費80万円と各社負担40万円を表示できる。明細へのリンク、粗利率、合計からの逆算、CSV・カレンダー・通知・AI回答でも内部金額が漏れないことを試験する。フリーエンジニアには自分への発注額と条件を表示する。

JV責任者は自社側の情報公開を決め、顧客側は自社で誰が閲覧・検収・署名できるかを契約上の権限内で決める。資料を読める人、案件の業務承認者、契約を締結できる人を個別に登録する。

## 7. 端から端までの動作例

架空案件として、VSEが顧客から「受注一覧のCSV出力」を受注し、登録済みのエンジニア一人に実装を依頼する。委託条件は「合意した5列・指定の文字コードで出力」、成果は外部リポジトリの確定版と確認結果で提出するものとする。

| 段階 | エンジニアが見ること・すること | サービス、顧客、VSEが行うこと |
| --- | --- | --- |
| 発注・受諾 | F-03で対象列、完成例、報酬、納期、検査・支払予定を読み、引き受ける | スポンサーの予算決裁、個別発注、本人の受諾を記録し、J-11の納入物に関連付ける |
| 仕様の質問 | 「出力順は画面の並びと同じですか」とF-04から一度だけ質問する | AIが仕様の記述と未確定点を窓口に示す。窓口が顧客から回答を取り、確定した順序と回答日をF-04に返す |
| 追加要望 | 顧客が6列目を希望したとき、自分に影響する追加見積と納期案を回答する | サービスがJ-08に変更を起票。経営層に原価・期限への影響を示し、顧客と受託者それぞれの条件を確認する。未合意なら5列の発注を維持する |
| 提出・委託検収 | F-05に確定版と確認結果を登録し、控えを受け取る。F-06に「提出済み／次は発注元が確認」と出る | 合意版と同じコミットのテストを照合。指定検収者が委託成果を検収し、経理には受領日・検収額・支払期日を渡す |
| 配備・失敗時 | 通常は本人の操作なし。問題がコードに起因し、元の条件を満たさない場合だけ、対象版と再現条件付きの修正依頼を受ける | サービスがリリース説明・承認・配備依頼を仲介。配備先で障害が起きれば運用当番が切戻しを判断し、窓口が顧客へ続報。旧版のまま成功通知を送ることを防ぐ |

案件には少なくとも**発注条件の状態、受託者の提出状態、委託元の検収状態、実環境への配備状態、顧客の受入状態、支払状態**を別々に持たせる。「委託検収済み・本番配備待ち・支払予定あり」は正常な組合せである。中止・担当交代の際も、その時点までの提出・受領・未精算分と引継ぎ先を残す。終了後に本人が保有すべき帳票は控えとして取得可能にし、他案件や作業資料への権限は契約に従い失効させる。

**顧客名義で初めてiOSアプリを公開する場合。** JV責任者は顧客の案件ホームに公開予定日、承認が必要なストア掲載文、引渡対象の資産を載せる。発注側プロジェクト責任者は自社の契約署名者とAppleの登録担当を指名する。顧客が法人登録を完了したら、顧客チームにJVの作業者を招待する。最初から顧客のチームで配信するため、別チームへのアプリ譲渡は発生しない。検収時には、顧客ロゴ、新規の画面デザイン、JVが保有する既存部品を個別に確認する。顧客が次のビルドを扱えることと運用窓口を確認したら、JVの一時アクセスを終了する。

| 3. 国内販売の条件を満たす | モバイル、要員枠、変更再合意、検収・請求照合、運用引継ぎを実装。計画・カレンダーのもう一方、4種のコード連携、6種のチャットとPagerDutyを提供元別に順次検証 | 顧客に提示する対応表に、検証済みの機能、制限、構成、最終試験日を記載できる。販売する構成ごとに通知不達、当番交代、再同期、部分検収・精算を通す |
| 4. 選ばれる理由を検証する | 外注の配分案比較と相手別の週報を加え、現行手段と同じ案件条件で、判断待ち・納期調整・証跡回収の時間を比較する | 受託者の手間を増やさず、窓口・経営層の作業時間が減るかを測り、案件単価と運用原価で継続提供できるか判断する |

**顧客機能の着手順。** 最初に37〜40・42で公開範囲と承認者を設定し、43〜45で発注企業が予定を確認してJVの申請に回答するところまでつなぐ。次に49・52・53で、契約と資産の帰属案を顧客が同じ案件で確認できるようにする。業務提携の試行では41・46を加えて、共同費用の改訂を両社が決裁する。アプリ納入の試行は56・57から始め、顧客名義の新規公開なら58・60、他チームの既存アプリ移管なら59・60を重点的に検証する。

**連携の実装方針**

- **ソース管理と配備の権限。** 成果の照合はSSOTの順序に従いGitHub→GitLab→Azure Repos→AWS CodeCommit、初期はクラウド版を対象にする。外部リポジトリを正本とし、保存するのは許可された参照、識別子、検証・承認記録。公開操作は27の専用接続に対象環境・許可された手順・期限を限定する。読取接続にリリース権限を追加しない。実配備先を接続できない顧客には、指定担当が外部で実行し、実行結果を取り込む方式も選べるようにする。[SSOT第13章](../SSOT.md)
- **日程の正本。** GitHub Projectsの計画、Google Calendar／Microsoft 365の共有会議、サービスが発行した依頼・回答期限は出所を表示する。個人の予定表を取り込まず、エンジニアが案件に共有した空き枠を使う。変更案は本人・顧客が合意して初めて確約に反映し、外部計画を更新する担当には原本へのリンクを渡す。計画同期を読取一方向に保っても、サービス内での発注・受諾・回答は完結できる。[日程同期の設計判断](../SSOT.md)
- **通知とオンコール。** アプリ内・メールを基礎に、Slack、Microsoft Teamsから接続し、Discord、Mattermost、Google Chat、Chatworkを追加する。各提供元で「投稿」「本人を確認した受領」「障害時の代替経路」を別々に試験する。送信専用でも認証リンクで当番が応答できる構成にする。当番とエスカレーションの正本はPagerDutyとし、休日・夜間対応を引き受ける組織と時間帯を案件開始時に明示する。[通知・当番の既存設計](../design/gap-coverage.md)
- **データと実装の境界。** 新しい発注・受諾・提出・検収には案件ID、契約当事者、対象版、原本、実行者、時刻を持たせる。顧客との契約変更と委託先との変更には別のIDを振り、関連付ける。判断と監査の同時保存は既存基盤を使い、外部配信は送信待ち記録と重複防止キーで再試行する。ワークフロー・判定は `crates/platform`、HTTP境界は `crates/server`、同期・配信ジョブは `crates/worker` に置く。[開発ガイド](../../AGENTS.md)・[判断の実装](../../crates/platform/src/decision.rs)・[同期の実装](../../crates/platform/src/sync.rs)

## 9. 適合準備と商品性の検証

上層部のポートフォリオは複数案件を扱うが、準備状況は**対象案件・対象プロファイル・採用版ごと**に表示する。初期対象は非セーフティクリティカルなソフトウェアを単一チームで単一製品として開発するVSEのBasicプロファイル。下表は製品側の証跡設計案である。規格本文との要求単位の対応確定は、利用許諾を確認した正規資料と専門家レビューを前提に、既存のGate 0で行う。[ISO/IEC 29110-5-1-2:2025 公開概要](https://www.iso.org/standard/82669.html)・[SSOTの規格・表示方針](../SSOT.md)

| 経営側で確認したい問い | 通常操作から集める記録 | 欠けたときの表示 |
| --- | --- | --- |
| 何を、いつ、いくらで合意したか | 発注版、受諾者、合意済み変更、計画の履歴 | 未回答の当事者、未確定の条件、回答期限 |
| 作ったものが要求に対応するか | 完成条件、要求・設計参照、提出コミット、同じ版の検証結果 | 試験未取得、条件未検証、版不一致、確認担当 |
| 誰が何を根拠に公開したか | ルール版と判定、例外の根拠・期限、実務承認、経営判断、実配備記録 | 未承認、例外失効、配備結果未確認 |
| 誰が受け取り、何が残ったか | 委託検収、顧客受入、契約別の差戻し・再提出、運用引継ぎ | 当事者別の未回答、未引継ぎ、対応責任者 |

**有償化の検証方法。** 次の数値はPoC用の目標案であり、実績値ではない。案件の規模・契約形態を合わせ、現在のメール・チャット・表計算での運用と比べる。完了案件だけを抽出せず、途中離脱・辞退・顧客未回答も集計する。

| 観点 | 指標と判定案 |
| --- | --- |
| 受託者が自走できるか | 初見の受託者5人中4人以上が支援なしで受諾・提出まで完了。ISO用語の入力は0箇所。失敗した操作と所要時間を記録する |
| サービスが仲介を引き取れたか | 完了案件あたり、受託者本人が顧客折衝または配備の手配を求められた回数を数える。通常経路の目標は0回。人手に移した折衝は窓口の工数として別に測る |
| 経営判断と日程調整が速くなるか | 顧客からの質問受付→確定回答、外注変更受付→決裁の中央値と遅い案件の所要時間を導入前後で比較。期限を過ぎて担当が空欄の案件は0件を目指す |
| 取引・品質の誤りを防げるか | 条件改訂、二重提出、二重請求、別版のCI成功、未承認公開、他社閲覧の各試験で誤処理0件。提出から顧客受入まで、対象版と当事者を全試験案件で追跡できる |
| JV責任者が意図した内容だけが顧客に届くか | 同一顧客の外注案件と提携案件を用意する。契約額と共同費を公開した後、JVの非公開予算・粗利・個人別報酬が画面、添付、出力、購読、通知、AI回答のいずれにも現れないことを確認する。提携終了後も再試験する |
| 顧客が案件の確認から引き渡しまで完了できるか | 顧客の担当者が日程変更を確認し、権限者が正しい版に回答できた割合、未処理申請の日数、引き渡し後に顧客が自社権限で更新できた件数を記録する。Apple確認待ちの日数とJVの作業待ちを分けて測る |
| 継続して販売できるか | 一案件あたりの窓口有人対応分数、AI・通知・当番の原価、1社の月間受発注件数、継続利用意向を記録。経営側の月額＋案件量による課金と受託者招待無料を価格仮説として検証する |

最初の商談で見せる一連の操作は、**経営者が依頼を発行し、初めて招待された一人がコードの参照を提出し、窓口が顧客の質問とリリースを引き受け、経営者が合意・採算・公開結果を同じ案件で確認するところまで**とする。この流れが一案件で成立すれば、追加コネクタや経営分析がどの顧客の導入判断を変えるかを切り分けて検証できる。
