# VSE／ISO/IEC 29110対応開発支援ツールの機能ギャップ調査

- 調査日: 2026-11-28
- 対象リポジトリ: Engineering Platform
- 対象文書: `docs/SSOT.md`、`docs/openapi.yaml`、`docs/design/design-request.md`、README、`crates/`、`apps/web/src/`
- 目的: 現在の実装と製品構想を区別し、VSEの開発プロセス支援、ISO/IEC 29110 Basic Profileの適合準備、追加要求であるコードホスティング連携、チャット通知、オンコール対応に必要な不足機能を整理する

## 1. 結論

本リポジトリは、規格適合準備を支援する製品の設計資料と画面モック、および固定サンプルを使ったCI判定デモを持つ。実際の顧客プロジェクトでBasic Profileのプロセスを運用し、複数のコードホスティング、プロジェクト計画・カレンダー、通知先をつなぎ、経営層に最新状況と判断事項を示し、評価者向けの改ざん検証可能な証跡を出す段階には達していない。

現行のAPIはローカルデモ用の実行登録・取得が中心で、GitHub等の実データ、プロジェクトスケジュール、カレンダー、AIモデル、認証・認可、承認ワークフロー、複数プロジェクトのPM／SIデータ、通知先、オンコール先を処理する本番APIはない。設計依頼書に列挙された多数の画面は、SSOT上も架空のモックデータで動く表示用画面とされている。デモで動くゲートは、固定の`Rust`と`Web`チェックを`demo-ci-v1`で評価するものに限られる。

したがって、現時点では「ISO/IEC 29110準拠ツール」や「組織の適合を判定するツール」と表示できない。適切な製品目的は、組織が自ら定めたプロセスを実行し、必要な人間の判断と客観的な証跡をつなぐ「適合準備・継続的保証の支援」である。ISO/IEC 29110-3-2の認証対象はVSEが実施するプロセスであり、ツールや製品の認証とは異なる。[ISO/IEC 29110-3-2:2018](https://www.iso.org/standard/62732.html)

## 2. 対象範囲と評価上の注意

### 2.1 製品が現在掲げる範囲

SSOTで定める初期範囲は、原則25人以下のVSE、非セーフティクリティカルなソフトウェア開発、Generic Profile GroupのBasic Profile、単一チーム・単一製品、Project Management（PM）とSoftware Implementation（SI）である。ISOの公開情報でも、VSEは最大25人の企業・組織・部門・プロジェクトとして説明され、Basicの2025年ガイドは単一製品を単一チームで開発するVSEを対象としている。[ISO/IEC 29110-1-1:2024](https://www.iso.org/standard/85337.html)・[ISO/IEC 29110-4-1:2018](https://www.iso.org/standard/67223.html)・[ISO/IEC 29110-5-1-2:2025](https://www.iso.org/standard/82669.html)

「VSE全般」「29110全プロファイル」への対応は、現在のMVP範囲より広い。Entry、Intermediate、Advanced、システムエンジニアリング、サービス提供等を同じControl Packとして扱わず、別の適用範囲・別版として管理する必要がある。

### 2.2 適合性評価の限界

この報告はリポジトリ、製品画面の仕様、ISO等が公開する規格の概要情報を照合した機能ギャップ調査である。ISO/IEC 29110-4-1:2018の正規本文を使った要求単位の逐条評価ではない。SSOTも、正規本文の専門家レビューとBasicの規範要求のControl Catalog承認を未完了としている。

そのため、本報告では規格本文の要求文を転載・言い換えせず、実装に必要な機能領域を製品側の言葉で整理する。厳密な「満たす／満たさない」の判定、Control ID、条項ごとの証跡、必須・任意の区別は、利用許諾を含むGate 0の解消後、規格専門家によるレビューを経て確定する。

### 2.3 状態の区分

| 状態 | 意味 |
| --- | --- |
| デモ実装 | ローカルサンプルに限ってAPI／Worker／DB上で動作する |
| 画面モック | React画面、遷移、表示例はあるが、実データAPI、権限、永続化、外部サービス接続はない |
| 未実装 | SSOT上で未着手・保留、または実装コード・APIが確認できない |
| 要件確定待ち | 正規規格本文、専門家レビュー、顧客PoC、提供者APIの仕様確認等が必要 |

「画面が存在する」ことは、対応機能が実装済みであることを示さない。

### 2.4 今回の調査で採用するターゲットとアクター

依頼者の最新方針を受け、この調査では**本サービスの直接利用者をVSEの上層部に限定**する。主な利用者は経営者、役員、事業責任者、CTO、事業部長、案件スポンサーなど、複数案件の状況と経営判断に責任を持つ人である。開発者を本サービスの利用者・有償シート対象として想定せず、開発者向けの作業画面やコード編集機能は製品ターゲットから外す。

開発者、PM、品質担当、顧客、評価者はISO/IEC 29110に関係するプロセス上のアクターとして残るが、原則として本サービスに直接ログインせず、Git、CI、課題管理、文書、カレンダー等の既存システムがデータを供給する。経営層向け画面は、案件別・ポートフォリオ横断で進捗、計画差異、重大リスク、期限超過、承認待ち、証跡の準備状況、経営判断が必要な項目を示す。必要な人の判断は実際の責任者・顧客・承認者が行った事実を保持し、経営層だけで規格プロセスを代替したように見せない。

| 区分 | アクター | 本サービスとの関係 |
| --- | --- | --- |
| 直接利用者（ターゲット） | VSEの経営者、役員、事業責任者、CTO、事業部長、案件スポンサー | プロジェクト・ポートフォリオの状況を確認し、経営判断、優先度変更、組織レベルの承認・エスカレーションを行う |
| 間接アクター | PM、開発者、設計者、QA／品質担当、リリース責任者、顧客 | 本来の業務システムで活動し、計画・要求・レビュー・CI・テスト・受入等の記録を残す。識別子を連携して記録の担当・承認関係を結び付ける |
| 外部評価者 | 認証機関・評価者、監査担当 | 権限を限定した証跡パックや閲覧範囲を通じ、必要時に根拠を確認する。通常の経営ダッシュボード利用者ではない |
| 連携システム | GitHub、GitLab、AWS CodeCommit、Azure Repos、課題・計画管理、Google Calendar、Microsoft 365 Calendar、通知・オンコールサービス | 活動や日程の正本としてデータを供給する。Gitリポジトリだけで計画・会議・マイルストーンを把握できるとは限らない |

この方針に合わせて[SSOT](../SSOT.md)は経営層ターゲットとスケジュール同期を反映済みだが、[Webデザイン依頼書](../design/design-request.md)には開発者・PM向けの直接利用画面が残っている。既存画面モックは実装済み製品ではなく、対象外または再設計が必要な案として扱う。

### 2.5 経営層が担う仕事と現場へ委任する仕事

「上層部だけが行う作業」がすべて経営者の手作業になるわけではない。多くは**経営層が最終説明責任・投資権限を持ち、PMや現場責任者が案を作り、日々の運用を担う**仕事である。サービスは経営層に入力作業を増やすのではなく、提案と実績を集め、経営判断を記録して現場の正本システムへつなぐ。

| 経営テーマ | 経営層が決める／承認すること | PM・現場が作成・実行すること | サービスで支援すること |
| --- | --- | --- | --- |
| 事業・プロダクト戦略 | どの顧客課題・市場・製品に取り組むか、何を成功とするか、継続・転換・撤退の条件 | 顧客調査、要求候補、技術選択肢、ユーザー検証を提示 | 戦略目標、対象顧客、価値仮説、KPI、根拠、承認履歴を管理 |
| 新規案件・投資判断 | 案件を開始するか、投資枠、スポンサー、事業上の優先度、期待利益と許容リスク | 提案書、概算見積り、実現性、代替案、依存条件を作成 | 案件受付、事業ケース、選択肢比較、承認・保留・却下、再審査日を記録 |
| 複数案件の優先順位 | 限られた予算・人員をどの案件に先に使うか、何を止める／延期するか | 案件別の見積り、価値、リスク、依存関係、必要ロールを提示 | ポートフォリオ一覧、優先度基準、シナリオ比較、優先順位変更の影響を表示 |
| 開発要員・能力の配分 | 人員の追加・採用・外部委託、複数案件間の重大な競合や能力不足を解決 | PM／部門責任者が具体的な担当者、稼働率、休暇・交代を調整 | 役割別の必要量と供給量、期間別の過負荷、キーパーソン依存、競合を可視化 |
| プロダクト／プロジェクトロードマップ | 事業目標、主要な成果時期、顧客への約束、リリース時期の許容幅、案件間の順序 | PM／プロダクト責任者がマイルストーン、依存関係、作業分解、更新予測を作る | 戦略ロードマップと実行計画を分け、確約／目標／予測、遅延幅、根拠、変更履歴を表示 |
| 予算・契約・採算 | 予算上限、価格・契約条件、採算割れや追加費用を受け入れる条件 | PM／営業／経理が工数、原価、納期、変更費用、請求状況を更新 | 承認予算と予測コスト、契約マイルストーン、差異、追加投資判断を連携。財務データは許可された情報源からのみ取得 |
| リスク・例外・品質統制 | 組織として許容する重大リスク、例外、顧客への説明、強制停止・継続・中止 | リスク登録、対策、技術評価、テスト結果、是正案を提示 | 閾値超過と未解決事項のエスカレーション、判断者・理由・条件・期限を監査記録 |
| リリース・事業移行 | 高リスク時のリリース可否、重大な顧客影響、運用受入、事業継続の判断 | リリース責任者が準備状況、試験、既知問題、切戻し計画を提示 | 根拠付きGo／No-Go、未完了事項、承認条件、事後レビューを記録 |
| 成果・便益の確認 | 投資目的に対して成果が出たか、追加投資・方針変更が必要か | プロダクト／運用担当が利用率、品質、納期、顧客反応等を測定 | 期待値と実績、測定時期、データ出典、次の改善・終了判断を追跡 |

プロジェクトスポンサーは、事業ケースの継続妥当性、プロジェクトの統治、戦略整合、便益、重要判断、障害のエスカレーションを担うと説明されている。[APM: Project sponsorship](https://www.apm.org.uk/resources/what-is-project-management/what-is-sponsorship/) ポートフォリオ管理では、案件の選定・優先順位付け、開始・停止判断、資源需要とポートフォリオ健全性の確認を行う。[PMI: The Standard for Portfolio Management](https://www.pmi.org/-/media/pmi/documents/public/pdf/certifications/standard-for-portfolio-management-third-edition.pdf?rev=67c367d7cf8f483d8e67f99af78205f7)

これは役割分担の実務モデルであり、ISO/IEC 29110の規範要求を直接列挙したものではない。VSEでは経営者がPMや技術責任者を兼務することもあるため、システム上は人名と役割・決裁権限を分けて設定できる必要がある。

## 3. 基準範囲・規格情報

| 項目 | 調査時点の基準 | 製品への意味 |
| --- | --- | --- |
| VSE | 原則25人以下 | 初期顧客の規模だけでなく、導入・記録の負担が小さいことを評価する |
| Basic Profileの規範的なプロファイル仕様 | ISO/IEC 29110-4-1:2018。ISOページでは2024年に確認され、現行版とされる | 要求単位のマッピング元。正規本文によるレビューは未完了 |
| Basic Profile実施ガイド | ISO/IEC 29110-5-1-2:2025 | PM／SIのワークフローやテンプレート設計の参照元。SSOTでは整合確認が一部に留まる |
| Agile／DevOpsガイド | ISO/IEC 29110-5-5:2026。ISO公式ページでは2026-11-16公開 | CI/CDとの対応を追加する場合、版と専門家レビューをControl Packに明記する |
| Agileソフトウェア開発ガイド | ISO/IEC 29110-5-4:2025 | Agile実践の補足的な参照候補。5-5:2026との適用関係を整理する |
| 認証スキーム | ISO/IEC 29110-3-2:2018と2025年追補 | 認証機関によるプロセス認証との境界をUI、契約、監査出力で明示する |

SSOTにある`ISO/IEC 29110-5-5:2026`の名称・年は調査時点のISO公式情報と一致している。公式情報ではAgile/DevOpsガイドとして2026年11月に発行済みである。[ISO/IEC 29110-5-5:2026](https://www.iso.org/standard/76641.html) 以前の調査メモにあった「未発行／5-4のみが該当する」という記述は採用しない。

## 4. 機能ギャップ一覧

以下の「不足」は、現行実装で提供されていないか、画面案だけで実運用の仕組みがないものを指す。規範的な必要性そのものの確定には、2.2節の専門家レビューが必要である。

### 4.1 規格管理、Control Pack、プロファイル

| ID | 不足機能 | 必要な対応 | 状態・根拠 |
| --- | --- | --- | --- |
| STD-01 | 正式なControl Catalog | 規範的Control、ガイド、組織調整、自動ルールを区別し、各項目に自社作成ID、適用Profile／版、出典番号・箇条番号、説明、必要な証跡、機械検査、人の承認ロールを持たせる | 未確定。SSOTでは正規本文の確認・専門家承認がGate 0のブロッカー |
| STD-02 | 要求から実装・証跡までの規格トレーサビリティ | Control → PM/SIプロセス領域 → 組織手順 → 成果物 → 機械ルール／人の判断 → Evidence Manifestを相互参照できるようにする | 未実装。UI案にControl詳細・監査ダッシュボードはある |
| STD-03 | プロファイル、Control Pack、ルールの版固定 | プロジェクト開始時にProfile、Control Pack、ルール、テンプレート、強制レベルを固定し、変更履歴と承認を残す | 方針は確定、実装なし |
| STD-04 | プロファイルの適用範囲判定 | チーム人数、製品数、クリティカリティ、開発形態等を導入時に記録し、対象外・要専門家確認のケースを識別する | 未設計。Basicの対象範囲を超えた案件に誤って「対応」を表示するリスク |
| STD-05 | Tailoring・非該当・代替の統制 | 適用しない理由、代替手段、リスク、申請者、独立承認者、有効期間を保存する。組織調整はパックの基準版を上書きせず、差分として管理する | 画面案のみ。画面仕様上Should扱いであり、製品要件の優先度を再評価する |
| STD-06 | 改訂の差分・移行 | 旧版と新版のControl／ルール差分、既存プロジェクトへの影響、未充足となる項目、移行承認、実行記録を出す | 画面案はLater。複数版運用の前提として早期設計が必要 |
| STD-07 | 規格情報の権利管理 | 規格本文、無償公開本文、逐条言い換えを無許諾でDB・プロンプト・RAG・テストに含めない。権利確認、利用範囲、参照元・ライセンス状態を管理する | SSOT方針あり。運用・レビュー・AIパイプラインの実装は未確認 |
| STD-08 | 規格表示と認証の境界 | 製品説明、契約、画面、監査パックに第三者認証との違いを示し、AIが適合を判定する表現を避ける | 方針あり。実際の全表示・契約レビューは未完了 |
| STD-09 | 専門家・評価者のレビュー証跡 | Control Packの承認者、レビュー版、差戻し、適用判断、第三者評価者からの形式フィードバックを記録する | 未実装。評価者受容はPoC未検証 |

### 4.2 PM（プロジェクト管理）を支援する機能

Basic ProfileのPMを「PRゲート」だけで代替できない。プロジェクト計画・合意・進捗・問題対応・変更・納入判断などの管理情報と、関連する承認・証跡を一続きに扱う必要がある。今回のターゲット方針では、これらを開発者に本サービスへ手入力させるのではなく、正本となる既存システムから同期し、経営層が計画と実績を確認できるようにする。現状のJ-01〜J-09画面案はモックで、実データや業務状態遷移はない。

| ID | 不足機能 | 必要な対応 |
| --- | --- | --- |
| PM-01 | 案件・契約・SOWの管理 | 顧客、契約／SOWの版、範囲、前提、制約、納入物、期限、変更履歴を保存する。原本のハッシュ・出典箇所・データ分類を記録する |
| PM-02 | プロジェクト計画 | 目的・範囲、作業分解、成果物、スケジュール、見積り、役割、リスク、構成管理、品質方針、顧客との合意を正本システムから同期し、基準計画と改訂履歴を保持する |
| PM-03 | 活動・資源・責任者の割当 | 課題・計画システムから担当、責任、期限、依存関係を取り込み、未割当・過負荷・担当交代・休暇による懸念を経営層に集約する |
| PM-04 | 進捗と計画差異 | 計画値と実績（課題、PR、テスト、成果物等）を対応させ、遅延、未完了、再計画、是正判断の履歴を残す。データの取得元と最終同期時刻も表示する |
| PM-05 | リスク・問題・是正処置 | 発生可能性・影響、対応責任者、対策、期限、残余リスク、判断根拠、完了確認を追跡し、関連要求・変更・ゲート・リリースと結び付ける |
| PM-06 | 変更要求と影響分析 | 顧客／社内の起票、対象範囲、要求・設計・テスト・費用・スケジュールへの影響、承認／却下、反映結果を管理する。AI候補は人が確定する |
| PM-07 | 顧客との合意・連絡・会議記録 | 要求、計画、変更、リリース、受入に関する決定者・日時・内容を保存し、決定事項から要求・リスク・変更にリンクする |
| PM-08 | マイルストーン・納入物 | 成果物、予定・実績日、提出先、提出版、受領・受入状態、差戻し、再提出を一元管理する |
| PM-09 | プロジェクト監視と経営アクション | 未充足Control、承認待ち、ブロック、期限超過、例外、証跡欠落を案件・ポートフォリオ単位で優先順に提示する。経営判断の要否と実務上の対応責任者を分けて表示し、判断後の実施状況を追跡する |
| PM-10 | 終了・引継ぎ・学習 | 完了条件、未解決事項、顧客受入、保守引継ぎ、教訓、最終証跡を閉じ、次の案件に再利用できる形で保存する |
| PM-11 | 事業ケースと案件立上げ | 課題・機会、戦略整合、選択肢（実施しない案を含む）、想定便益、費用、リスク、制約、スポンサー、成功指標を登録し、開始・保留・却下を承認する。実務担当者が案を作り、経営層の判断を記録する |
| PM-12 | ポートフォリオ優先順位・ロードマップ | 複数案件を事業価値、緊急性、リスク、顧客約束、費用、依存関係に基づき比較する。目標ロードマップと確約済みマイルストーンを分け、延期・中止・優先度変更の影響を残す |
| PM-13 | 経営資源・予算の配分 | 役割別の必要キャパシティと供給、予算消費・予測、外部調達の選択肢を期間ごとに比較し、共有要員の競合を検知する。個人単位の勤務監視を目的とせず、配分判断に必要な集計を表示する |
| PM-14 | 期待便益と成果の確認 | 事業ケースで定めたKPIの基準値・期待値・実績値・出典・確認日を記録し、リリース後の継続投資・改善・終了判断へつなぐ |

### 4.2.1 経営層向けスケジュール同期

スケジュール同期は、このターゲットにおける**中核要件（P0）**である。経営層向けに使える予定と遅延を出すには、開発者の手入力画面を増やすよりも、計画・課題管理を正本として同期し、カレンダー上の重要会議や意思決定期限を重ねる必要がある。Gitコネクタだけでは予定日、依存関係、マイルストーン、会議を網羅できない。AWS CodeCommitなどリポジトリ主体のサービスでは、別の課題・計画ソースの接続も必要となる。

#### 同期対象と情報源

| 情報領域 | 代表的な情報源 | 経営層に示す情報 |
| --- | --- | --- |
| 計画・作業項目 | GitHub Projects、GitLab Issues／Milestones、Azure Boards、Jira等 | 計画・予測開始日と終了日、期限、担当組織／責任者、状態、優先度、依存関係、進捗、更新日時 |
| ベースライン・マイルストーン | 課題・計画管理、リリース管理、合意済み計画 | 当初計画、承認済み改訂、現在予測、実績日、遅延日数、変更理由、承認者 |
| 経営会議・顧客会議・レビュー日程 | Google Calendar、Microsoft 365 / Outlook Calendar | 対象案件、開催日時、決定事項の期限、次回レビュー、開催状態。個人予定表ではなく、許可された共有カレンダーを既定の対象とする |
| 開発・納入の実績イベント | GitHub、GitLab、AWS CodeCommit、Azure Repos、CI／リリース基盤 | PR/MR、レビュー、ビルド、テスト、リリース、受入等の完了状況。個別のコード作業ではなく計画項目との集計関係を示す |

Google Calendarの同期は初回全件取得後に同期トークンを保存し、追加・変更・削除の差分を継続取得する。トークンが無効になった場合の再全件同期も必要である。Microsoft GraphのcalendarView delta queryも初回同期と差分リンクによる更新・削除取得を提供するため、コネクタは各社固有のカーソルと再同期条件を扱う。[Google Calendar差分同期](https://developers.google.com/workspace/calendar/api/guides/sync)・[Microsoft Graph Calendar delta](https://learn.microsoft.com/en-us/graph/delta-query-events?tabs=http)

#### 不足している同期機能

1. **情報源と正本の定義**: プロジェクト、マイルストーン、日付、担当、状態、会議情報ごとに正本を定める。同じ項目を複数システムが更新する場合の優先順位も設定する。
2. **初回取込と差分同期**: 全件初期同期、Webhookまたは差分API、定期リコンシリエーション、ページング、カーソル／syncToken保管、トークン失効時の再取得を行う。
3. **計画ベースラインの保持**: 初回計画、承認済み改訂、最新予測、実績を別々に保存し、上書きで当初期限や遅延履歴を消さない。計画変更の理由・承認者・変更日時を結ぶ。
4. **エンティティ対応付け**: 外部ID、プロジェクト、リポジトリ、課題、マイルストーン、リリースの対応表を管理し、重複・孤立・誤った組織紐付けを検出する。AIが候補を出す場合も確定者と根拠を残す。
5. **日付・依存関係の正規化**: 日付のみ、時刻付き、終日、繰返し、期限、開始／終了、予測日、休日、営業日、タイムゾーン、夏時間を区別する。先行・後続関係から影響範囲とクリティカルな遅延を求める。
6. **会議イベントの安全な同期**: 共有対象カレンダーや分類条件を明示し、個人・非公開予定は既定で除外する。経営ダッシュボードに必要な最小限の件名、時刻、対象案件、主催者、会議URLのみを扱い、本文・参加者一覧は不要なら取らない。
7. **更新・削除の意味付け**: 延期、取消、削除、シリーズ全体と単一回の変更、課題のクローズ／再開を区別し、業務記録と計画履歴を消さずに状態として反映する。
8. **同期健全性の可視化**: 最終成功・最終試行・同期遅延・権限不足・API停止・対象数・エラー詳細を示し、古い情報に「最新」と誤認させない。再試行、全件同期、接続解除、再認可の手順を用意する。
9. **衝突と冪等性**: Webhookの重複・順不同、同時更新、部分同期、レート制限、通信断を扱い、同じ外部イベントの二重登録や過去版への巻戻しを防ぐ。
10. **経営ビュー**: 案件横断のロードマップ、計画対予測、期限超過、次の意思決定日、リスク／ブロック、担当責任者、影響を受けるマイルストーン、同期鮮度を一画面で確認できる。
11. **通知との連携**: マイルストーン接近・遅延、会議前の判断事項未解決、同期停止、予定変更を重大度・閾値に応じて通知し、重複抑止と経営層への要約を行う。
12. **監査と権限**: 取得範囲、接続者、権限、外部ID、取込・変更差分、再同期、手動修正の主体と時刻を監査する。経営層の閲覧権限を案件・顧客・機密レベルで制限する。
13. **初期は一方向同期**: 原則は正本システムから本サービスへの読取同期とする。本サービスでの経営判断は監査対象の判断記録として保存する。スケジュールの書戻しが必要なら、対象フィールド、競合解決、承認、変更通知を定義した上で明示的に追加する。
14. **運用と利用制限**: APIコスト、レート制限、同期周期、データ保持・削除、契約上の権限、サービス停止時の手動確認手順を定め、組織削除や接続解除後に外部データの複製を適切に処理する。

オンコール当番表はプロジェクト計画・経営会議カレンダーとは別のドメインである。当番サービスを別の正本に置き、プロジェクト日程の同期状態と混同しない。

### 4.3 SI（ソフトウェア実装）を支援する機能

SIの詳細データは経営層が個々の開発作業を行うためのものではなく、既存システムから進捗・トレーサビリティ・証跡を集約するための情報源である。開発者に本サービスのアカウントや入力を必須にせず、Git／CI／課題・テスト管理の識別子と活動記録を取り込む。

| ID | 不足機能 | 必要な対応 |

| SI-02 | 要求の承認とベースライン | 作成・レビュー・承認・差戻し・変更中・廃止の状態遷移、作成者と承認者の分離、顧客承認、承認版の固定を実装する |
| SI-03 | 設計・ADR | 要求を設計判断・アーキテクチャ・詳細設計に対応付け、設計レビュー、代替案、判断理由、結果、改訂、承認を記録する |

| SI-07 | テストケースと結果 | 単体・結合・受入等のケース、対象要求、手順・期待結果、実行者／環境、成功・失敗・スキップ、失敗詳細、再試験を管理する |

| SI-12 | 顧客納入・受入 | 納入物のダウンロードとハッシュ、受入条件、顧客の判断・コメント・差戻し・再提出を記録し、受入を証跡にする |

### 4.4 ゲート、ルール、例外

SSOTはA: Structural、B: Traceability & Quality、C: Human Authority、D: Evidence Integrityを定めるが、「具体ルールは未実装」と明記している。デモのCI判定は本番Control PackやISO/IEC 29110の適合判定ではない。

不足している機能は次のとおり。

1. ゲートごとの入力スキーマ、ルールID、説明、対象Control、判定主体、証跡、エラー修正案の定義。
2. 入力スナップショット・ルール版・評価実行の保存と、後日の同一判定再現。
3. 警告のみ→ソフト→ハードの段階導入、プロジェクト／ブランチ／リリース別の適用、停止・再開の監査記録。
4. 必須チェックの欠落、重複、別コミット、古い結果、再実行、キャンセル、タイムアウト、提供元不明、署名不一致の扱い。
5. PR以外のマイルストーン、顧客承認、リリース・受入ゲート。
6. 例外の申請、理由・リスク・代替策、独立承認、期限、再審査、期限切れの再ブロック、取消、延長を新しい承認として記録する仕組み。
7. ポリシー変更・例外・バイパス権限の職務分離と改ざん防止。
8. ゲートをプロバイダー別の必須チェックに登録・検証し、ブランチ保護の設定漏れ・変更を検知する仕組み。

#### 4.5.3 CI、テスト、セキュリティ成果物の接続

コードホスティングとCI実行基盤は別コネクタとして扱う。GitHub Actions、GitLab CI、AWS CodeBuild／CodePipeline、Azure Pipelines、Jenkins等から、実行ID、対象SHA、状態、テストレポート、SAST、依存関係スキャン、SBOM、成果物ハッシュ、署名、ログの参照先を取込む。規格固有ゲートはAIのテキスト要約で判定せず、保存済みの構造化結果と版管理されたルールで再現する。

1. 組織／プロジェクト／ユーザー単位の接続設定と宛先検証、テスト通知、無効化、再認可。

#### 4.6.3 チャット通知とオンコールの境界

Slack、Discord、Teams等へのメッセージ投稿は通知経路であり、単独では必ずしも当番表、エスカレーション、応答確認、電話・Push通知を提供しない。オンコールではチャネル投稿の成功だけを「担当者へ通知できた」と見なさない。Discord Webhookのように送信専用の方式もある。応答保証が必要な場合、オンコール管理サービスと接続するか、別途スケジュール・エスカレーション機能を提供する。

### 4.8 承認、認証、認可、職務分離

実装コードで認証・認可を確認できず、デモAPIにはローカルサンプル向けルートのみがある。以下が不足する。

- GitHub OAuth／SSO、招待の受諾・失効、セッション、MFAやIdP要件、ユーザー無効化。
- 組織／プロジェクト／リポジトリ／顧客ポータル／評価者共有のテナント境界とアクセス制御。
- 経営層の直接利用者、組織管理者、評価者等に対するサーバー側ロール判定。PM、設計者、開発者、QA、リリース責任者、顧客の活動主体は、外部システムの本人ID・役割を対応付けて証跡に記録する。直接利用者としてのアカウント発行は必須にしない。
- 経営層の閲覧範囲（組織、事業部、顧客、案件、機密区分）を設定し、全社横断閲覧や承認権限を役職だけで自動付与しない。
- 作成者・実施者・レビュー者・承認者・ポリシー管理者の分離。自己承認、AIによる自分の生成物の承認、権限の迂回をDB/API／CIで拒否する。
- 承認依頼、期限、コメント必須、差戻し、取消、再依頼、同時更新、承認後の対象版変更による失効。
- 期限付き評価者共有リンクの範囲、メール認証、失効、ダウンロード監査、情報の持ち出し制御。
- 操作ごとの監査ログ、管理者操作の記録、ロール変更履歴、アクセストークン発行・失効。

### 4.9 Evidence、監査、保管

現在はPostgreSQLにデモ判定・監査イベントを保存する。DB管理者による更新・削除を防げず、暗号署名やWORM保管も実装されていない。

必要な不足機能は以下。

1. Evidence Manifestの正式スキーマとスキーマ版、プロジェクト／Profile／Control Pack版、コミット、ルール／ポリシーのハッシュ、CI実行、入力・出力のダイジェスト、承認、例外、AIモデル・テンプレート識別子を含む記録。
2. ハッシュ計算、署名鍵管理（KMS等）、署名検証、鍵ローテーション、透明性ログとの連携、検証失敗の理由表示。
3. Gitホスティングと別の信頼境界にある追記専用／WORM保管。S3 Object Lock、Azure Immutable Blob、同等の保管方式を接続可能にする。
4. 保持期間、法的保全、削除禁止、期限満了後の削除、顧客の契約と地域設定を含むライフサイクル制御。
5. 監査イベントの連番・時刻・実行主体・対象・変更前後、追記専用化、検索・CSV/JSON出力、管理者による改ざん検出。
6. Controlから証跡への逆引き、欠落／一部充足／例外／検証失敗の状態、活動別カバレッジ。
7. 監査パックの生成（対象期間／リリース、対応表、成果物、承認、例外、ログ、Manifest）、ファイルハッシュ、期限付き共有、失効とアクセスログ。
8. 実際の第三者評価者による出力形式のレビュー。機械生成物が評価者に受け入れられるかをPoCで検証する。

### 4.10 AI機能とAIガバナンス

AI Requirements ReviewerはMVPの計画にあるが、モデル接続、実行、承認フローは未実装である。AIの出力をブロッキング判定に用いない方針は維持する。

- 要求の曖昧さ、矛盾、テスト可能性、欠落、設計との不整合、SOWからの候補抽出、リンク候補、計画・リリースノート下書き、計画差異とリスクの経営向け要約の実行機能。AI要約には元データへのリンクと不確実性を付け、判断を自動確定しない。
- AI所見の対象版・対象箇所・モデル・プロンプトテンプレート版・結果ハッシュ・生成時刻・人の採否／却下理由の保存。
- 入力のデータ分類と送信可否、顧客ごとのAI無効化、Secret／Credentialの除外、外部URL取得の既定無効化。
- エージェントにマージ、承認、例外承認、ポリシー編集、証跡削除を許可しないこと。人間の作成者／承認者分離と同じサーバー側制御。
- Repo、Issue、SOW、コメントを未信頼データとして扱うPrompt Injection耐性、parser→型付きデータ→許可ツール→モデルの境界、人へのエスカレーション。
- データ保持、学習利用、リージョン、再委託先、削除、インシデント通知、監査権、生成物の責任を契約・設定・実行ログと一致させる。
- 専門家が作成した評価データで適合率・再現率、誤指摘、見落とし、悪意ある入力を定期評価し、モデル変更前後を比較する。
- 低信頼・非対応モデル・無効状態のUI表示。AI処理障害時にも人の承認と決定論的ゲートを継続可能にする。

### 4.11 VSEに必要な使いやすさと運用支援

少人数組織で記録・管理負担が増えると定着しない。直接の利用者である経営層が複数案件の最新状況を短時間で判断できること、既存ツールへの入力を重複させないことが必要である。

- 経営層向けの短時間オンボーディング。接続する計画・課題・カレンダー・SCM、対象範囲、経営ダッシュボード、通知先を段階的に設定できる。
- 既存プロジェクトの初期インポートと差分同期、重複ID・未リンク・日付欠損・同期停止を診断する。
- 入力フォームや開発タスク管理を重複して提供せず、正本システムへの参照、更新元、最終同期時刻を表示する。
- 計画対実績、予測日、遅延傾向、重大リスク、未解決の経営判断、データ鮮度を要約し、根拠へドリルダウンできる。
- 未承認・期限超過・リンク欠落・例外期限を経営判断、運用担当の処理、開発チームの対応に分けて提示し、責任主体を混同しない。
- 日本語を標準とし、日付・時差・休日、英語表示、CSV／PDF／JSONの文字化け・表記を検証する。
- 利用者が規格本文を読まなくても経営判断に必要な意味と限界を理解できるガイド。規格要求の誤解を招く独自解釈や「合格保証」を表示しない。
- 価格／プラン制限、利用量、保存量、通知量、AI費用を透明化し、上限時に証跡やゲートを消失させない。

現行の顧客ポータル・開発者向け作業画面は、今回の直接利用者方針のMustとはしない。経営判断に必要な外部承認・顧客受入の証跡を収集する経路は別途必要であり、連携先や期限付きの承認リンク等で補う。

### 4.13 SaaS、セキュリティ、可用性

SSOTはローカルComposeを現状とし、本番インフラを保留としている。外販前には次の機能・運用統制が必要である。

- マルチテナント分離、暗号化（通信・保管）、鍵管理、Secret管理、脆弱性管理、セキュアなビルドとデプロイ。
- バックアップ、復旧目標、障害検知、保守、更新、ロールバック、データ移行、災害復旧。
- 監視、構造化ログ、メトリクス、トレース、問い合わせ用ID、管理者監査、個人情報マスキング。
- API認証・認可、入力検証、Webhook署名、CSRF／リプレイ／大量送信対策、レート制限、リクエストサイズ制限。
- サービス稼働状況、顧客向け障害告知、インシデント対応、脆弱性受付・修正期限、サポート窓口。
- データの保存地域、バックアップ地域、AI提供者・再委託先、保持と削除の契約、組織削除時の完全なデータ処理。
- セキュリティレビューと侵入・権限境界評価。社内開発リポジトリのCI通過を、製品本番運用のセキュリティ保証と混同しない。

## 5. コネクタ共通設計の追加要求

### 5.1 アーキテクチャ境界

`crates/platform`に外部サービス共通モデル、イベント正規化、冪等性、ルーティング、監査記録の境界を置く。HTTP受付と署名確認は`crates/server`、配送・再試行・定期同期・期限監視・エスカレーション起動は`crates/worker`に置く。各外部サービスのSDK/API詳細はAdapterに閉じ込め、業務ルールから分離する。

追加する概念モデルの候補:

- `ConnectorInstallation`: provider、tenant、scope、credential reference、capabilities、状態、最終同期。
- `ExternalEvent`: provider、delivery id、event kind、resource key、head SHA、occurred/received time、署名検証結果。
- `Notification`: event id、severity、template version、redacted payload、destinations、delivery attempts、status。
- `OnCallTarget`: provider、service/team、schedule/escalation policy reference、current responder、coverage status。
- `Incident`: source event、dedup key、priority、acknowledged by/at、escalations、resolved by/at、timeline。
- `EvidenceManifest`: schema version、profile/control pack/policy versions、digest list、approvals、exceptions、signature, retention locator.

### 5.2 信頼性要件

- 外部から届いた同一イベントを複数回処理しても、判定・監査イベント・通知を二重作成しない。
- DB更新とメッセージ配送をOutbox等で分離し、トランザクション確定後に配送する。配送失敗が判定結果を巻き戻さない。
- 各プロバイダーのAPI制限、Webhook再送、長時間障害、資格情報失効を検知し、Backoff／dead-letter／再処理を提供する。
- 1つの通知先の障害で他のチャネルやゲート判定を止めない。複数チャネルへ送る時の個人情報・秘密情報の最小化を行う。
- 監査記録は送信の試行・成功・失敗・再試行・応答操作・当番変更を保持し、送信本文にSecretを残さない。
- Provider capabilityを「イベント受信」「メッセージ送信」「インタラクション」「ユーザー識別」「配信確認」「当番照会」「ページング」に分け、プロバイダーごとにテストする。

## 6. 網羅性を確認する受入シナリオ

実装フェーズで各シナリオを統合テスト・外部サービスSandbox・Composeスモークに分けて検証する。ここではテストは実行していない。

### 6.1 規格・プロセス

- Basic ProfileのControl Pack版を選び、プロジェクト開始後に意図せず更新されない。
- 顧客がSOW由来の要求を承認し、承認済み要求の改訂は差分・再承認・旧版証跡を残す。
- PMが計画、進捗、リスク、是正、変更、顧客合意を登録し、各項目が成果物・要求・リリースにリンクする。
- 要求から設計、実装、テスト、検証、リリース、受入まで双方向に辿れる。リンクがない項目とAI候補だけの項目を区別する。
- 例外に理由、リスク、独立承認者、期限がなくては有効化できない。期限切れ後は再審査状態になる。
- 同一入力・同一ルール版で同一の判定とManifestが再現できる。別SHAのチェック結果を誤って流用しない。

### 6.2 コードホスティング

- GitHub、GitLab、AWS CodeCommit、Azure Reposの各Sandboxで、インストール／OAuth、対象リポジトリ選択、権限説明、イベント検証、PR/MRまたは相当する変更要求の同期を行う。
- Push、PR/MR作成・更新・再開・クローズ・マージ、レビュー、CI完了、force-push、Webhook重複・順不同を処理する。
- GitHub Checks、GitLab External Status Checks、Azure PR Status／Branch Policy、CodeCommit Approval Rule等、提供者別の仕組みに応じたゲート連携を検証する。
- 対象SHAが更新されたら旧ゲート結果と承認を失効し、新SHAで再評価する。
- 一時失敗、429、Webhook再送、アクセストークン失効の後に再同期しても二重記録や誤通過が発生しない。

### 6.3 チャット・オンコール

- Slack、Discord、Teams、Mattermost、Google Chat、Chatworkの各テスト宛先へ、重大度別にリンク付き通知を配信する。
- 無効な資格情報、失効したWebhook、権限不足、レート制限、チャンネル削除時に、失敗状態・再試行・管理者への代替通知を確認する。
- 送信専用Webhookに双方向操作を表示しない。操作可能なチャネルでは署名検証、製品ロール照合、二重クリック抑止を確認する。
- オンコール担当が無応答の場合、設定された期限後に二次担当へエスカレーションされる。AckはResolveと別々に記録する。
- 当番のカバー漏れ、夜間／休日、時差、臨時交代、プロバイダー停止を検出し、フォールバック経路をテストする。
- チャット通知が失敗してもゲート判定と証跡保存は完了し、後から配送状態を監査できる。

### 6.4 スケジュール同期

- GitHub Projects、GitLab Issues／Milestones、Azure Boards等の計画データと、Google Calendar／Microsoft 365 Calendarの許可された共有予定を同期し、対応する案件・リポジトリを誤りなく結び付ける。
- 初回全件取得後、追加・変更・削除・取消を差分同期する。Webhook重複・順不同、ページング、429、トークン期限切れ、権限失効後に回復しても二重登録やデータ消失が起きない。
- 当初ベースライン、承認済み計画変更、最新予測、実績が別々に残り、過去時点の計画差異を再現できる。
- マイルストーン延期、課題の期限変更、会議移動・取消、繰返し予定の単一回変更が区別され、遅延影響と通知先が正しく更新される。
- 日付のみ／時刻付き／終日、異なるタイムゾーン、夏時間、日付境界を含む予定を正しく表示する。個人の非公開カレンダー予定は既定で取り込まない。
- 同期が止まった状態を正常な最新情報として表示しない。経営ダッシュボードに最終成功時刻、鮮度、エラーと対応担当を示す。
- CodeCommitなど計画管理を持たないSCMでは、別の計画システムを設定しなければポートフォリオの計画情報が欠けることを明示する。
- 会議日程・プロジェクト計画とオンコール当番表を別々に表示し、互いの更新・削除が他方へ波及しない。

### 6.5 証跡・アクセス・データ保護

- 他組織のリポジトリ、要求、監査ログ、共有リンク、通知先、当番情報へアクセスできない。
- 署名検証失敗、ハッシュ不一致、期限切れ、保持先削除を検出し、通過扱いにしない。
- 評価者リンクの期限切れ・失効・権限外アクセスを拒否し、閲覧・ダウンロードを記録する。
- AI無効化、Secret検出、分類上未許可のデータ送信をサーバー側で止め、ゲートはAIなしでも動作する。
- 退職者の権限失効がGitコネクタ、承認、通知、オンコール当番に反映される。
