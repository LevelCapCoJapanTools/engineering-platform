## 1. 目的と提供価値

**確定**: 小規模なソフトウェア開発組織（VSE、原則25人以下）向けに、ISO/IEC 29110 のプロセス実行を支援する Continuous Assurance／適合準備（Compliance Readiness）基盤をつくる。

**確定（2026-11-28）**: 本サービスの直接利用者はVSEの上層部に限定する。経営者、役員、事業責任者、CTO、事業部長、案件スポンサーが複数案件の計画・実績・リスク・証跡準備状況を確認し、必要な経営判断を行う。開発者、PM、設計者、QA、顧客等はプロセス上のアクターとして残るが、本サービスの直接利用者や有償シート対象とはせず、Git、CI、課題・計画管理、文書、カレンダー等の既存システムから活動データを取り込む。実際の作業や承認を行った主体は連携データから記録し、経営層だけでプロセスを代替したように扱わない。

製品の一文仕様:

> 課題・計画管理、カレンダー、Git・CI上の開発イベント、要求・設計・テスト・承認を同期し、バージョン管理された Control Catalog と Evidence Manifest に対応付ける。上層部には複数案件の計画・実績・リスク・判断事項を示す。AIは要約とレビューを補助し、決定論的なルールが客観的に検証できる統制を評価し、権限を持つ人間が意味的な判断と承認を行う。証跡は署名付きで改ざん耐性のある保管先に残す。

直接利用者とプロセス上のアクターを分ける。経営層向けの閲覧・判断画面を中心に設計し、開発者向けの作業管理、コード編集、日々の入力を製品要件にしない。連携先は経営ダッシュボードの表示元であり、Gitコネクタだけでなく、計画管理とカレンダーの同期を製品の中核に含める。

責任分界の原則:

| 担当 | 扱う領域 |
| --- | --- |
| CI（決定論的検証） | 存在、形式、ID、リンク、テスト結果、署名、役割 |
| 人間 | 意味的妥当性、顧客合意、リスク判断、承認、受入 |
| AI | 上の二つの間を埋める下書き、要約、曖昧性・矛盾の指摘、リンク候補 |

差別化の中心はコード生成ではなく、要求から監査証跡までをCIのマージ条件に変換する統制基盤（Control Plane）に置く。GitHub／GitLabの既存機能とは競合せず、その上に重ねる。

### 提供しないもの（確定）

- 第三者認証の代替。ISO/IEC 29110 の認証は ISO/IEC 29110-3-2 の枠組みで外部の認証機関が行うプロセス認証であり、製品はその準備と証跡整備を支援するだけ
- AIによる適合性の最終判定。AIの出力だけでゲートを通過させない
- 完成したソフトウェアの品質や適合性の保証

### 4層の分離（確定）

規範的要求とガイドの推奨を混同しないため、統制を次の4層に分けて保持する。ガイドの例示をそのまま規格要求としてCIで強制しない。

1. `normative-control` — Profile Specification に基づく要求
2. `implementation-guidance` — 実施ガイドに基づく推奨
3. `organization-tailoring` — 顧客組織ごとの調整
4. `automated-policy` — CIで実行するルール

各ルールは、どの層のどの Control に由来するかを持つ。

### プロファイルのバージョン固定（確定）

案件ごとに profile と Control Pack のバージョンを固定する。規格改訂による挙動変化は自動適用せず、移行レポートを伴う明示的なマイグレーションで行う。

## 4. 知的財産と表示の制約（確定）

ISO の公開方針（調査済み）に基づき、次を守る。違反は事業上のブロッカーとして扱う。

- ISO 規格本文を、許諾なくリポジトリ、データベース、プロンプト、RAG、学習データに含めない。無償公開の文書も同じ扱いにする
- Control Catalog には自社で作成したメタデータだけを置く（例: `control_id`、`profile`、`source_ref`、`evidence_type`、`machine_check`、`human_gate`）。規格本文の転載や逐条の言い換えは入れない
- 製品名、サービス名、ドメインに「ISO」を含めない。ISO のロゴを使わない
- 規格は「ISO/IEC 29110-4-1:2018」のように正式な番号で参照する

表示の基準:

| 表現 | 可否 |
| --- | --- |
| 「ISO/IEC 29110 の適合準備を支援」 | 推奨 |
| 「ISO/IEC 29110 を参考にした開発支援」 | 可 |
| 「ISO/IEC 29110 Basic 対応のプロセス実装支援」 | 対応付けの専門家検証後に可 |
| 「ISO/IEC 29110 準拠プロセスの証跡生成を支援」 | 何が準拠するかを明示する場合に可 |
| 「ISO認証済み」「AIがISO/IEC 29110を認証」 | 不可 |

## 5. アーキテクチャ方針

### 採用済みの構成（確定）

| 領域 | 採用構成 | 理由 |
| --- | --- | --- |
| リポジトリ | Rust 2024 Cargo workspace と React／TypeScript のモノレポ | API、Web、DBの変更を同じPRで検証する |
| API | Axum／Tokio、`crates/server` | HTTP、入力制約、稼働・準備確認を扱う |
| 共通ロジック | `crates/platform` | ワークフロー、ゲート、監査、GitHubデータの境界を共有する |
| Worker | Tokio、`crates/worker` の別プロセス | APIから独立してキューを処理する |
| 永続化 | PostgreSQL 17／SQLx | キュー、判定、監査イベントをトランザクションで整合させる |
| 開発とCI | Docker Compose、GitHub Actions | ローカルとCIで同じ一連の動作を検証する |

### 判定の再現性（確定）

- ゲートの判定は、保存済みの入力（チェック結果、成果物のハッシュ、承認記録）とバージョン付きのルールだけで再現できるようにする
- ルールを変えるときはポリシーのバージョンを上げ、既存の判定結果を書き換えない
- 判定と対応する監査イベントは同じDBトランザクションで記録する
- AIの出力はブロッキング判定の入力にしない。参考所見として保存し、人間の判断材料にする

### 顧客リポジトリのモデル（仮説）

docs-as-code と evidence-as-data を採る。文書をWordファイル単位で強制せず、必要な情報、状態、証跡を型付きデータとして扱う。顧客リポジトリ内の配置案は次のとおりで、PoCで確定する。

```text
.vse/            profile、control-map、policy、exceptions、schemas
docs/            sow、project-plan、requirements（REQ-xxxx）、design/adr、verification、validation
trace/edges.yaml REQ→設計→コード→テストの関係
evidence/        manifests、approvals、ci、attestations
```

### CIゲート（確定。各ゲートの具体ルールは未実装）

既存CIを置き換えず、GitHub の required status check として差し込む。

| ゲート | 検証内容 |
| --- | --- |
| A: Structural | 必須メタデータ、成果物、ID、profile／version、スキーマ |
| B: Traceability & Quality | 要求→設計→コード→テストのリンク、lint、テスト、SAST、依存関係ポリシー |
| C: Human Authority | 顧客の要求承認、設計レビュー、例外承認、リリース承認 |
| D: Evidence Integrity | commit SHA、ポリシーのハッシュ、CI実行ID、成果物ダイジェスト、承認者、時刻、AIモデル情報を Manifest にして署名 |

導入時は warn → soft gate → hard gate の順に段階的に強制する。

### 例外処理（確定）

管理者による無条件のバイパスは設けない。例外は申請者、理由、リスク、対象、有効期限、独立した承認者を持つ証跡として記録し、期限到来時に再審査する。

### 監査証跡の保護（確定、実装は未着手）

1. Git の保護ブランチ、署名付きコミット、変更不可のリリースタグ
2. リリースごとの Evidence Manifest への暗号署名（Sigstore／Cosign または KMS）
3. Git ホスティングとは別の信頼境界にある WORM／追記専用の保管先（例: S3 Object Lock）

AIレビューはプロンプト本文を永続保存せず、テンプレートのバージョンとハッシュ、モデル識別子、入出力のハッシュを残す。

## 6. AIエージェントの方針（確定）

権限:

- エージェントにマージ、ポリシー編集、証跡削除、例外承認の権限を与えない
- エージェントは自分が生成した変更を承認できない。作成者、承認者、ポリシー管理者を分離し、CIで強制する
- 認証情報は短命のOIDCトークン、リポジトリ単位のスコープ、読み取り専用を既定にする

Prompt Injection 対策:

- リポジトリ、Issue、README、SOW、コメントはすべて信頼できない入力として扱う
- 入力は parser → 型付きデータ → 許可リスト化したツール → モデル の順に渡す
- シークレットをコンテキストに入れない。外部URLの取得は既定で無効
- 不審な指示を検出したら人間にエスカレーションする

データ分類と実行形態:

| 分類 | 実行形態 |
| --- | --- |
| Public | マネージドの汎用モデル |
| Internal | 学習利用なし・保持なし相当の契約があるエンタープライズAPI |
| Confidential | プライベートエンドポイント／VPC |
| Highly Confidential | オンプレミス／オープンウェイトモデル |
| Secret／Credential | LLMへ送らない |

## 7. データ保護と契約（確定、詳細は保留）

顧客データに個人情報が含まれる場合、AI APIの利用は個人情報保護委員会のガイドラインに沿った委託先管理（安全管理措置の確認、契約、取扱状況の把握）として扱う。AIガバナンスの基準には経済産業省「AI事業者ガイドライン」の最新版を採る。

顧客契約で定める事項: 利用目的、学習利用の禁止、保持期間、リージョン、再委託先、削除、インシデント通知、監査権、生成物の責任分界、知的財産、秘密保持、ログ保存期間、AI機能を無効にするモード。

## 8. 現在の実装: ローカルデモ

1. Web画面がシナリオを送信する。APIはGitHub Checksに合わせた固定サンプルと受付イベントを同じトランザクションで保存し、実行IDを返す。
2. Workerは `FOR UPDATE SKIP LOCKED` で未処理の行を1件取得する。同じコミットSHAの `Rust` と `Web` に対応するチェックがそれぞれ1件あり、どちらも `completed` かつ `success` のときに通過とする。それ以外は理由付きでブロックする。別コミットの結果は判定対象から外す。
3. Workerはポリシーバージョン、判定結果、監査イベントを同時に確定する。処理中にトランザクションが中断された場合は未処理行として残る。記録済みの判定は再処理しない。
4. Web画面は判定と監査ログを取得する。監査イベントには実行IDに対応する受付・判定の時刻と処理主体を記録する。

| デモシナリオ | Webチェック | 期待結果 |
| --- | --- | --- |
| すべて成功 | 成功 | 通過 |
| チェック失敗 | 失敗 | ブロック |
| チェック実行中 | 未完了 | ブロック |
| チェックが欠落 | 欠落 | ブロック |

デモポリシーの識別子は `demo-ci-v1`。対象は `example/demo-project` のサンプルスナップショット。デモ用HTTPルートとWorkerは `EP_DEMO_MODE=1` で有効になる。APIが起動時にSQLxマイグレーションを実行してからWorkerを起動する。監査イベントの保存先は開発用PostgreSQLで、DB管理者による更新や削除を防ぐ機能はない。監査時刻はDBで記録し、UIはブラウザのローカル時刻で表示する。

このデモは規格固有の判定を含まない。ISO/IEC 29110 に関する判定は、第10章の Gate 0 を満たすまで実装しない。デモ画面は Web の `#/demo` で開く。

### 製品画面のモック

[Webデザイン依頼書](design/design-request.md) の全画面と全部品を `apps/web` に React で実装している（`#/screens` が画面一覧、`#/catalog` が部品カタログ）。モックは次の前提で作る。

- 画面は表示専用で、ゲート判定、権限判定、状態遷移のロジックを持たない。表示する値と「操作できるか・できない理由」は呼び出し側から渡す
- データは `apps/web/src/mocks` の架空のサンプルデータで、API には接続しない。デモ画面だけが API に接続する
- 2026-11-28 の[機能ギャップ調査](reserch/gap-analysis-vse-iso29110.md)を受けて、画面を経営層ターゲットに合わせて再設計した。追加した画面は、経営ダッシュボード、経営判断、ポートフォリオ、案件受付と事業ケース、優先順位、要員・予算、戦略ロードマップ、便益・成果、経営スケジュール、連携と同期、通知とオンコールである。既存画面は、経営層が閲覧・判断する前提に改訂した
- PM・開発者・QA・顧客等の活動は、外部システムから同期した値として出典（正本）と最終同期時刻を付けて表示する。編集は正本のシステムで行い、本サービスに開発者向けの入力画面を置かない。実際の作業者・承認者は外部IDで記録し、経営層のアカウントと区別する
- 顧客など、アカウントを持たない実際の承認者は、期限付きの承認リンクで承認・差戻しを行う
- 調査の各ギャップIDと画面の対応は [ギャップ対応表](design/gap-coverage.md) で管理する。画面モックがあることは、その機能の本番実装を意味しない。実際の外部サービス接続、認証・認可、同期、通知配信、オンコール連携、署名、WORM 保管は、第13章の保留事項をSSOTで確定してから実装する
- 画面遷移はハッシュ方式のモック用ルーター（`apps/web/src/lib/router.tsx`）で行う。URL 設計は本番の実装時に決める
- 色、文字、余白は `apps/web/src/design/tokens.css` のデザイントークンで定義し、ライトとダークのテーマを持つ
- 部品は `apps/web/src/ui`、画面は `apps/web/src/screens/<画面群>` に置き、ファイル冒頭に画面IDを書く

## 9. 開発リポジトリのCIゲート

GitHub Actions の `CI` が `main` へのpushおよび `main` 向けPRで動く。`Rust` は整形、Clippy、PostgreSQL統合テスト、ビルドを実行し、`Web` はテスト、型検査、ビルドを実行する。`Compose smoke` は4つのサンプルが監査ログまで到達することを検証する。`CI Gate` は3ジョブすべてが成功した場合のみ通過する。GitHub側の `main` 保護ルールで `CI Gate` を必須にする。

| 観点 | 検証先 |
| --- | --- |
| 不足・未完了・失敗・重複・別コミットの扱い | [ゲート単体テスト](../crates/platform/src/gate.rs) |
| 並行Workerと監査記録 | [PostgreSQL統合テスト](../crates/platform/tests/workflow.rs) |
| Webプロキシから判定と監査記録まで | [Composeスモークテスト](../scripts/smoke.mjs) |
| 経営判断の職務分離と監査、外部イベントの重複・順不同、同期カーソルの失効 | [PostgreSQL統合テスト](../crates/platform/tests/decisions_and_sync.rs) |
| Webhook の署名検証から重複除外まで | [Composeスモークテスト](../scripts/smoke.mjs) |
| リポジトリの必須チェック | [CIワークフロー](../.github/workflows/ci.yml) |

## 10. 事業判断とGo／No-Go

**確定**: 判断は「条件付きGO」。技術PoCは進めてよいが、外販と規格固有の判定の実装は Gate 0 を満たしてからにする。

### Gate 0（外販・規格固有実装の前提）

| 項目 | Go条件 | 状態 |

## 11. 事業上の前提（仮説）

- 販売は「ISOを導入する」ではなく「既存のGitHubにAppを入れると、PRに品質ゲートと証跡がつく」という訴求にする。29110は裏側の枠組みとして使う
- 最初の3〜5社はプロセス整備込みの導入PoCとして受注し、Control Pack、移行ツール、監査UXを磨く
- 価格案: Starter ¥49,800／月、Team ¥99,800／月、Partner ¥198,000〜／月、Private ¥1.5〜3.0M／年〜、導入支援 ¥200k〜800k、事前点検 ¥300k〜1M／回。プロジェクト課金（¥80k〜200k／案件）も検証する
- 最大の原価リスクはLLM費用ではなく、顧客ごとの個別対応の人件費。Control Pack と Adapter の境界を製品レベルで固定し、SaaSがコンサル業化するのを防ぐ
- 国内で ISO/IEC 29110 認証を求める企業数（直接TAM）は未検証。同等の国内向け商用SaaSは調査で確認できていないが、存在しないことの証明ではない

### 確定した設計判断（2026-11-28、推奨案を採用）

依頼者が判断を委ねたため、次の推奨案を確定とする。変更する場合はこの表を更新し、影響する実装と文書を同じ変更で直す。

| 領域 | 確定した判断 | 理由 |
| --- | --- | --- |
| 画面の実装方式 | React の画面を残し、Rust の API に接続する。画面は表示専用のまま、値と操作可否を API から受け取る | 画面は値を外から受け取る形で作ってあり、移行の手戻りが最も小さい |
| 計画の正本 | 最初の計画ソースは GitHub Projects。カレンダーは Google Calendar と Microsoft 365 Calendar の共有カレンダーのみ。GitLab Issues、Azure Boards、Jira は同じアダプター契約で後から追加する | 初期顧客は GitHub 利用を前提とし、経営会議はどちらかのカレンダーにあることが多い |
| 同期の方向 | 正本からの読取一方向。本サービスでの経営判断は判断記録として保存し、正本へ書き戻さない | 競合解決と承認の設計を後回しにでき、正本の信頼性を保てる |
| 計画の日付 | 当初・承認済み改訂・予測・実績を追記専用の履歴として保存し、上書きしない。鮮度のしきい値は60分 | 過去時点の計画差異を再現でき、遅延の履歴が消えない |
| 外部イベント | 提供元と配信IDで重複を除外し、同じリソースの古い版で新しい状態を巻き戻さない。Webhook は署名を検証し、検証できないものは保存しない | 再送・順不同・偽装への耐性（調査 SCM-03、SCM-04） |
| 追加のコードホスティング | GitHub、GitLab、Azure Repos、AWS CodeCommit の順。最初はクラウド版のみ | API の成熟度と、ゲートを必須化できる仕組みの有無 |
| 通知 | アプリ内とメールを基礎に、Slack、Microsoft Teams（Workflows または通知 Bot）の順で追加する。配信は Outbox と冪等キーで行う | 国内の小規模組織での利用が多く、双方向操作の仕組みが成熟している |
| オンコール | 当番表とエスカレーションは自社で持たず、PagerDuty を正本とする。Opsgenie は新規に接続しない | 当番管理の再実装を避け、提供元のサポート終了の影響を受けない |
| 外部承認 | アカウントを持たない承認者は、対象の版に紐付いた1回限りの期限付きリンクと、メールのワンタイムコードで本人確認して承認する | 現場にアカウントを要求しない方針と、承認の本人性を両立する |
| 経営判断 | 依頼者本人は判断できない。理由は必須、保留には再審査日が必須。判断と監査イベントは同じトランザクションで記録する | 職務分離と監査の再現性 |
| 認証 | 経営層の利用者は OIDC（Google、Microsoft）でサインインし、MFA を必須とする。SAML は Enterprise 版で追加する | 小規模組織の既存 ID をそのまま使える |
| 証跡の保護 | Evidence Manifest を KMS の鍵で署名し、S3 Object Lock（Compliance モード）に保管する。透明性ログとの連携は後から追加する | 成熟した部品で、Git ホスティングと別の信頼境界を作れる |
| AI | 評価データで基準を満たすまで、顧客環境での AI 機能は既定で無効とする。有効にしても参考所見に限る | 誤通過のリスクを避ける |

### 実装済みの範囲（2026-11-28）

`crates/platform` に次を実装し、単体テストと PostgreSQL 統合テストで検証している。外部サービスへの実際の接続（OAuth、API 呼び出し）と、経営層の認証はまだ実装していない。

- 経営判断の記録（`decision`）: 職務分離と入力の検証、判断と監査イベントの同一トランザクションでの記録
- 計画の日付履歴（`schedule`）: 追記専用の履歴、ずれの計算、過去時点の再現、同期の鮮度の判定
- 外部イベントの受信（`webhook`、`sync`）: GitHub Webhook の署名検証、配信IDによる重複除外、古い版による巻戻しの防止。API の `POST /api/v1/webhooks/github` は `EP_GITHUB_WEBHOOK_SECRET` を設定したときだけ有効になる

次の設計作業:

1. 経営層の OIDC 認証、組織・閲覧範囲・判断権限のサーバー側判定を実装し、経営判断の API を公開する
2. GitHub App のインストールと GitHub Projects・カレンダーの初回同期・差分同期を実装し、受信したイベントから計画の日付履歴と鮮度を更新する
3. 画面を API に接続する（経営ダッシュボード、経営判断、ポートフォリオ、連携の状態から）
4. 並行して Gate 0（ISO／JSAの許諾確認、正規資料の入手、専門家レビュー）を進める
