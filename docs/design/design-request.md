# Webデザイン依頼書

この文書は、Webデザイナー（エージェント）に画面デザインと Next.js による画面モックを依頼するためのもの。製品の前提は [SSOT](../SSOT.md) を正本とする。この依頼書と SSOT が食い違う場合は SSOT を優先し、食い違いを報告すること。

## 1. 依頼の概要

| 項目 | 内容 |
| --- | --- |
| 依頼内容 | 第5章の全部品と第6章の全画面のUIデザイン、および Next.js で動く画面モック一式 |
| 製品 | 小規模ソフトウェア開発組織向けの適合準備・継続的保証（Continuous Assurance）SaaS |
| 利用者 | 5〜25名程度の受託ソフトウェア開発会社のメンバー、その発注元の顧客、外部の評価者 |
| 言語 | 日本語を主とする。英語化できるよう文言は1か所に集約する |
| 対象デバイス | デスクトップのブラウザを主とする（1280px以上）。「スマートフォン対応」と記した画面は390px幅でも全操作ができること |
| 製品名 | 未定。プレースホルダ「Product Name」を使う |

### 製品を一言で

GitHub 上の開発（要求、設計、コード、テスト、承認）を統制項目（Control）に対応付ける製品。AIが文書作成とレビューを補助し、CIゲートが機械的に検証できる項目を強制し、人間が意味の判断と承認を行う。すべての結果は、改ざん耐性のある監査証跡として保存する。

訴求の中心は「いつものPRに品質ゲートと証跡がつく」こと。規格は裏側の枠組みであり、前面に押し出さない。

## 2. 必ず守ること

### 表示と文言の制約

- 「ISO」のロゴ、またはロゴに似た意匠を使わない。製品名、ロゴ案に「ISO」を含めない
- 「ISO認証済み」「AIが適合を判定」「認証を取得できます」など、認証や適合判定を約束する表現を使わない。推奨する表現は「ISO/IEC 29110 の適合準備を支援」
- 規格は「ISO/IEC 29110-4-1:2018」のように正式な番号で参照する
- 規格本文の文章を、画面やサンプルデータに入れない。統制項目は `CTL-PM-001` のような架空の自社IDと、自社で書いた短い説明で表す

### 判断の主体を見分けられるようにする

この製品の核心は「誰が判断したか」の区別。全画面で次の4種類を、色だけに頼らずアイコンとラベルで区別する（部品 `ActorLabel`）。

| 主体 | 意味 | 表示の要件 |
| --- | --- | --- |
| CI | 決定論的なルールによる通過・ブロック | ゲートの結果として最も強く表示する |
| 人間 | 承認者の名前、ロール、時刻を伴う判断 | 誰が判断したかを必ず表示する |
| AI | 下書き、指摘、リンク候補 | 常に「AI・参考」と明示する。通過や合格のように見せない。採用・却下の操作を付ける |
| システム | 受付、署名、保管などの自動処理 | 控えめに表示する |

### 状態の語彙

全画面で同じ語と色を使う（部品 `StatusBadge`）。

| 対象 | 状態 |
| --- | --- |
| ゲート | 通過／ブロック／警告／例外適用中／実行中／未実行 |
| 承認 | 下書き／承認待ち／承認済み／差戻し／取り下げ |
| 要求・設計 | 下書き／レビュー中／承認待ち／承認済み／変更中／廃止 |
| AI所見 | 未確認／採用／却下 |
| 例外 | 申請中／有効／期限切れ／却下／取り下げ |
| リスク・是正 | 未対応／対応中／監視中／完了 |
| 変更要求 | 起票／影響分析中／承認待ち／承認済み／却下／反映済み |
| リリース | 準備中／ゲート確認中／承認待ち／リリース済み／受入済み／差戻し |
| 証跡 | 記録済み／署名済み／保管済み（WORM）／検証失敗 |

ゲートの強制レベルは「警告のみ」「ソフト（例外で通過可）」「ハード」の3段階（部品 `EnforcementBadge`）。判定がどのレベルで出たかを常に添える。

## 3. ロールと権限

1人が複数ロールを持つことがある。画面仕様の「操作」欄の権限は、このロール名で書く。

| ロール | 所属 | 主な操作 |
| --- | --- | --- |
| 組織管理者 | 開発会社 | 組織、メンバー、連携、プランの管理 |
| PM | 開発会社 | 計画、進捗、リスク、変更、リリース判断 |
| アナリスト | 開発会社 | 要求の作成・管理 |
| 設計者 | 開発会社 | 設計、ADR、レビュー |
| 開発者 | 開発会社 | 実装、PR |
| QA | 開発会社 | テスト、検証結果の記録 |
| リリース管理者 | 開発会社 | リリース承認 |
| ポリシー管理者 | 開発会社 | ゲートのルールと Control Pack の管理 |
| 顧客 | 発注元 | 自案件の要求承認、変更承認、受入 |
| 評価者 | 外部 | 共有された監査パックの閲覧のみ（期限付き） |
| パートナー管理者 | コンサル等 | 複数の顧客組織の横断管理 |

職務分離: 作成者は自分の成果物を承認できない。AIエージェントは承認、マージ、ポリシー編集、証跡削除ができない。操作できないボタンは非表示にせず無効化し、理由を表示する（部品 `SoDNotice`）。

## 4. 画面の共通仕様

個別の画面仕様に書いていない限り、次を適用する。

### 4.1 レイアウトの種類

| 種類 | 構成 | 使う画面 |
| --- | --- | --- |
| 公開レイアウト | `PublicHeader`、本文（最大幅1120px）、`PublicFooter` | 公開サイト |
| 中央寄せレイアウト | ロゴ、中央のカード（幅480px）、フッターのリンク | サインイン、招待、エラー |
| オンボーディング | ロゴ、`Stepper`（上部）、本文カード（幅720px）、「戻る」「次へ」 | オンボーディング |
| アプリ | `GlobalHeader`（上部固定）、`SideNav`（左240px、折りたたみ可）、`Breadcrumb`、`PageHeader`、本文 | 組織とプロジェクトの画面 |
| 詳細 | アプリのレイアウトの本文を、メイン（左）と `MetaSidebar`（右320px）に分ける | 各詳細画面 |
| ポータル | `PortalHeader`（プロジェクト名、ユーザー）、本文（最大幅800px）。サイドナビなし | 顧客ポータル、評価者ビュー |

### 4.2 一覧画面の共通仕様

- 上部に `FilterBar`（キーワード、状態、担当者、期間など画面ごとの条件）と、右端に主要な操作ボタン
- `DataTable`: 列の並べ替え、50件ごとのページ送り、行のクリックで詳細へ移動、列の表示切替
- 状態: 読み込み中（`Skeleton`）、0件（`EmptyState`。初回と絞り込み結果なしで文言を分ける）、取得失敗（`ErrorState` と再試行）
- 選択した条件はURLに残る前提でデザインする（再読み込みで保持）

### 4.3 詳細画面の共通仕様

- `PageHeader`: ID、タイトル、`StatusBadge`、主要な操作ボタン（最大3つ、残りは「その他」メニュー）
- `MetaSidebar`: 作成者、作成日時、更新者、更新日時、担当者、関連項目、承認状況（`ApprovalPanel`）
- メインの下部にタブ: 「内容」「関連」「履歴」（`Timeline`）「コメント」（`CommentThread`）
- 編集は同じ画面内で編集モードに切り替える。未保存で離れようとしたら `ConfirmDialog` を出す
- 承認済みの項目を編集すると状態が「変更中」に戻ることを、編集開始前に `Banner` で知らせる

## 6. 画面仕様

各画面の書式:

- **目的** — 画面で達成すること
- **利用者** — 主に使うロール
- **構成** — 画面を上から（または左から）順に分けた領域と、そこに置く部品
- **表示項目** — 表や詳細に表示するデータ
- **操作** — ボタンなどの操作、実行できるロール、実行後の結果
- **状態** — デザインが必要な画面の状態（共通仕様の状態は省略）

### 6.1 公開サイト

#### P-01 トップ

- **目的**: 製品の価値を伝え、PoCの相談につなげる
- **利用者**: 開発会社の経営者、PM、品質担当
- **構成**

  3. 仕組み: 「AIが下書きする → CIが検査する → 人が承認する → 証跡が残る」の4段の図。各段に `ActorLabel` と同じアイコンを使う
  4. 主な機能: 6機能のカード（要求管理、トレーサビリティ、CIゲート、例外管理、証跡と署名、監査パック）。各カードから P-02 の該当箇所へ

- **構成**: 上部に絞り込み（要求の状態、種類、欠落のみ表示、AI候補を表示）、中央に `TraceGraph`（4列: 要求、設計、コード／PR、テスト）、右にノードを選択したときの詳細パネル（`IdLink`、状態、リンク一覧、「リンクを追加」）
- **操作**: ノードの選択、AI候補の確定・却下、リンクの追加（アナリスト、設計者、開発者、QA）、表示の拡大縮小、画像出力
- **状態**: ノードが多い（200以上）場合の集約表示、欠落0件

#### T-02 トレーサビリティ表

- **表示項目**: 行が要求、列が 設計、コード／PR、テストケース、テスト結果、検証。セルにリンク数と状態の色（あり／なし／AI候補のみ）
- **構成**: 上部に列ごとの `CoverageMeter`
- **操作**: セルを押すと `Drawer` でリンク一覧、CSV 出力

#### T-03 テスト・検証結果

- **構成**: `Tabs`「テストケース」「テスト結果」「検証記録」「妥当性確認記録」
  - テストケース: ID、タイトル、種類（単体／結合／受入）、対応する要求、最新の結果
  - テスト結果: CI実行ごとの結果（成功数、失敗数、スキップ数、`CodeRef`、`Timestamp`）、失敗の一覧
  - 検証・妥当性確認記録: 対象、方法、結果、実施者（`UserChip`）、レビュー者、証跡
- **操作**: テストケースの登録（QA）、検証記録の作成と承認（QA。実施者と承認者は別の人）

### 6.6 プロジェクト: ゲート・PR・例外

#### G-01 ゲート実行の一覧

- **表示項目**: 実行ID、対象（PR 番号とタイトル、またはブランチ）、コミット（`HashDisplay`）、作成者（人／AIエージェントの `ActorLabel`）、`GateSummaryStrip`、総合判定の `StatusBadge`、`EnforcementBadge`、`PolicyVersionTag`、実行日時

#### G-02 ゲート実行の詳細

- **目的**: なぜブロックされたか、どう直せばよいかを示す
- **構成**
  1. `PageHeader`: 総合判定（大きな `StatusBadge`）、PR のタイトルと `CodeRef`、コミット、「再実行」
  2. 判定の要約: 「ブロック: 2件の問題を修正してください」のような一文と、修正項目への目次
  3. ゲートA〜D を `GateResultPanel` で縦に並べる。ブロックの理由ごとに ルールID、メッセージ、対象（`IdLink` やファイル）、修正方法、「例外を申請」ボタン（ソフトの場合のみ）
  4. 必要な人間の承認（ゲートC）: `ApprovalPanel`
  5. AIの参考所見: `AIFindingCard` の一覧。見出しに「判定には使われていません」と明記
  6. 判定の再現情報（折りたたみ）: ポリシーのバージョンと `HashDisplay`、入力スナップショットのハッシュ、CI実行ID、判定日時
- **状態**: 全通過、ブロック、警告のみ、例外適用中（適用中の例外の `ExceptionSummary`）、実行中、古いコミット（新しいコミットへの案内）

#### G-03 PR 一覧（Should）

- **表示項目**: PR 番号、タイトル、作成者（`ActorLabel`。AIエージェントの PR を区別）、`GateSummaryStrip`、レビュー状況、対応する要求、更新日時

#### E-01 例外の一覧

- **表示項目**: EXC-ID、対象のルールとゲート、対象のPR・リリース、申請者、承認者、`StatusBadge`、`DeadlineIndicator`
- **構成**: 上部に「有効な例外」「7日以内に期限切れ」「期限切れ」の `StatCard`

#### E-02 例外の申請

- **構成**: `Modal`（大）またはページ。上部に対象のゲート失敗の内容（G-02 から引き継ぎ、読み取り専用）
- **表示項目**: 理由（必須）、リスクと影響（必須）、代替の対策（任意）、期限（`DatePicker`。最大期間の制約と説明）、承認者（`Combobox`。申請者本人は選べない）
- **操作**: 「申請する」
- **状態**: ハードの強制レベルで申請不可（理由の説明）

#### E-03 例外の詳細・承認

- **操作**: 承認・却下（承認者。コメント必須）、取り下げ（申請者）、期限の延長申請（新しい申請として扱う）

### 6.7 プロジェクト: リリースと受入

  2. リリースゲート: `ChecklistPanel`（必要な文書がそろっている、承認済み要求のテストがすべて成功、未解決の変更要求なし、有効な例外の一覧、成果物の署名済み など）。各項目に判定の主体（CI／人間）
  3. 成果物: 名前、`HashDisplay`、`SignatureBadge`、SBOM の有無
  4. 含まれる変更: 要求、変更要求、PR の一覧
  5. リリースノート: `MarkdownEditor`（「AIで下書き」あり）

  2. 内容の要約: プロジェクト、プロファイル、Control Pack のバージョン、コミット、ポリシーのハッシュ、要求スナップショットのハッシュ、CI実行ID、テストレポートのハッシュ、成果物のハッシュ（すべて `HashDisplay`）

  6. 保管: 保管先、`RetentionBadge`、保持期限

  3. 形式: ZIP（PDF の要約と JSON）
  4. 生成: 進捗表示 → 完了後に「ダウンロード」と `ShareLinkPanel`（評価者への共有）

## 7. 主要な利用の流れ

デザインはこの流れが途切れず辿れることを確認すること。

1. **導入**: A-01 → A-04 → A-05 → A-06 → A-07 → A-08 → A-09 → A-10 → O-01
2. **要求の確定**: J-02（SOW から要求候補）→ R-02（アナリストが作成）→ R-03（AIレビュー）→ R-04 → X-02（顧客が承認）
3. **日々の開発**: 開発者が PR を作る → W-01（GitHub 上のチェック）→ G-02（ブロックの理由と修正方法）→ 修正 → 通過
4. **ゲート失敗時の例外**: G-02 → E-02（申請）→ O-02（承認者の受信箱）→ E-03（承認）→ G-02（例外適用中で通過）
5. **変更**: X-01（顧客が起票）→ J-08（影響分析と承認）→ R-02（要求の更新）
6. **リリースと受入**: L-02（リリースゲート）→ リリース承認 → X-03（顧客の受入）→ V-04（Manifest が署名・保管済み）
7. **監査対応**: V-01 → V-02 → V-06（監査パックの出力と共有リンク）→ X-04（評価者が閲覧）

## 9. 実装の制約（Rust 側への移植のため）

受け取った Next.js のモックは、Rust のバックエンドと組み合わせる形に移植する。移植しやすくするため、次を守ること。

- **画面は表示専用にする**。業務ロジック（ゲート判定、権限判定、状態遷移）を書かない。表示に必要な値と「操作できるか・できない理由」はすべて props で受け取る
- **Next.js 固有のサーバー機能を使わない**。Server Actions、Route Handlers、Middleware、サーバーでのデータ取得を使わない。`next/image`、`next/font` などに依存しない
- **データはモックで与える**。型付きの固定データを1か所に置き、ページはそれを読み込んで描画する。型も1か所にまとめる。項目名は将来のAPIに合わせて英語の snake_case にする
- **スタイルはCSS変数のデザイントークンと素のCSS（CSS Modules 可）にする**。実行時の CSS-in-JS は使わない。Tailwind を使う場合はトークンをCSS変数で定義する
- **依存ライブラリを最小にする**。UIライブラリやグラフ描画ライブラリを使う場合は、事前に名前と理由を挙げる
- **部品は第5章の名前で作る**。画面ファイルの冒頭に画面IDをコメントで書く
- **文言は辞書ファイルに集約する**
- **外部通信をしない**。アナリティクス、外部フォント、CDN、外部画像を読み込まない
- **サンプルデータは架空のもの**にする。実在の会社名、人名、ISO 規格本文を使わない
