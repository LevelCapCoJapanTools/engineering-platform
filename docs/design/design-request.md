# Webデザイン依頼書

この文書は、Webデザイナー（エージェント）に画面デザインと Next.js による画面モックを依頼するためのもの。製品の前提は [SSOT](../SSOT.md) を正本とする。この依頼書と SSOT が食い違う場合は SSOT を優先し、食い違いを報告すること。

## 1. 依頼の概要

| 項目 | 内容 |
| --- | --- |
| 依頼内容 | 第5章の全部品と第6章の全画面のUIデザイン、および Next.js で動く画面モック一式 |
| 製品 | 小規模ソフトウェア開発組織向けの適合準備・継続的保証（Continuous Assurance）SaaS |
| 利用者 | 直接利用者は、5〜25名程度のソフトウェア開発会社の経営層（経営者、役員、事業責任者、CTO、事業部長、案件スポンサー）と、組織管理者・ポリシー管理者。PM・開発者・QA・顧客は既存システムで活動するプロセス上のアクターで、原則ログインしない（2026-11-28 の SSOT 確定事項）。外部の評価者は期限付きで閲覧する。2026-11-28 の追補で、発注企業（発注側プロジェクト責任者・担当者・承認者・検収者・署名者）とフリーエンジニア（実装の受託者）も直接利用者になった |
| 言語 | 日本語を主とする。英語化できるよう文言は1か所に集約する |
| 対象デバイス | デスクトップのブラウザを主とする（1280px以上）。「スマートフォン対応」と記した画面は390px幅でも全操作ができること |
| 製品名 | 未定。プレースホルダ「Product Name」を使う |

### 製品を一言で

課題・計画管理、カレンダー、Git・CI 上の開発（要求、設計、コード、テスト、承認）を同期し、統制項目（Control）と証跡に対応付ける製品。経営層には複数案件の計画・実績・リスク・判断事項を示し、経営判断を記録する。AIは要約とレビューを補助し、決定論的なルールが機械的に検証できる項目を評価し、権限を持つ人間が意味の判断と承認を行う。すべての結果は、改ざん耐性のある監査証跡として保存する。

訴求の中心は「現場に入力を増やさずに、経営層が案件の最新状況と判断事項を根拠付きで把握できる」こと。規格は裏側の枠組みであり、前面に押し出さない。

2026-11-28 の[追加・修正案](../reserch/executive-freelancer-service-proposal.md)を受けて、商流「発注企業 → 受注側（VSE／JV）→ フリーエンジニア」を扱う画面（6.18〜6.24）と顧客ポータルの拡張を追加した。受託者は条件を確認して受諾し、普段の開発環境で実装して成果を提出するだけでよく、提出後の顧客説明、条件変更の折衝、リリース調整、受入の回収は本サービスの案件窓口が引き取る。改修60件と画面の対応は [追補の対応表](proposal-coverage.md) を参照する。

2026-11-28 の[機能ギャップ調査](../reserch/gap-analysis-vse-iso29110.md)を受けて、経営、連携と同期、通知とオンコールの画面（6.14〜6.17）を追加し、既存画面を経営層が閲覧・判断する前提に改訂した。ギャップIDと画面の対応は [ギャップ対応表](gap-coverage.md) を参照する。

## 2. 必ず守ること

### 表示と文言の制約

- 「ISO」のロゴ、またはロゴに似た意匠を使わない。製品名、ロゴ案に「ISO」を含めない
- 「ISO認証済み」「AIが適合を判定」「認証を取得できます」など、認証や適合判定を約束する表現を使わない。推奨する表現は「ISO/IEC 29110 の適合準備を支援」
- 規格は「ISO/IEC 29110-4-1:2018」のように正式な番号で参照する
- 規格本文の文章を、画面やサンプルデータに入れない。統制項目は `CTL-PM-001` のような架空の自社IDと、自社で書いた短い説明で表す

### 判断の主体を見分けられるようにする

この製品の核心は「誰が判断したか」の区別。全画面で次の4種類を、色だけに頼らずアイコンとラベルで区別する（部品 `ActorLabel`）。

| 主体 | 意味 | 表示の要件 |
| --- | --- | --- |
| CI | 決定論的なルールによる通過・ブロック | ゲートの結果として最も強く表示する |
| 人間 | 承認者の名前、ロール、時刻を伴う判断 | 誰が判断したかを必ず表示する |
| AI | 下書き、指摘、リンク候補 | 常に「AI・参考」と明示する。通過や合格のように見せない。採用・却下の操作を付ける |
| システム | 受付、署名、保管などの自動処理 | 控えめに表示する |

### 状態の語彙

全画面で同じ語と色を使う（部品 `StatusBadge`）。

| 対象 | 状態 |
| --- | --- |
| ゲート | 通過／ブロック／警告／例外適用中／実行中／未実行 |
| 承認 | 下書き／承認待ち／承認済み／差戻し／取り下げ |
| 要求・設計 | 下書き／レビュー中／承認待ち／承認済み／変更中／廃止 |
| AI所見 | 未確認／採用／却下 |
| 例外 | 申請中／有効／期限切れ／却下／取り下げ |
| リスク・是正 | 未対応／対応中／監視中／完了 |
| 変更要求 | 起票／影響分析中／承認待ち／承認済み／却下／反映済み |
| リリース | 準備中／ゲート確認中／承認待ち／リリース済み／受入済み／差戻し |
| 証跡 | 記録済み／署名済み／保管済み（WORM）／検証失敗 |

| 同期 | 同期中／遅延／古い情報／同期失敗／再認可が必要／初回同期中／停止中／未接続 |
| 案件の健全性 | 順調／注意／遅延／判定不可 |
| 日付の確度 | 確約／目標／予測／実績 |
| 経営判断 | 判断待ち／承認／条件付き承認／保留／却下／担当者へ回付 |
| 事業ケース | 作成中／提出済み／審議中／開始承認／保留／却下／終了 |
| 通知の配信 | 送信待ち／送信中／配信済み／受付済み（配信確認なし）／再試行中／失敗／再処理待ち／集約・抑止 |
| インシデント | 未受領／受領済み／解決（受領と解決を区別する） |
| 外部チェックの異常 | 古いコミットの結果／必須チェックなし／重複／キャンセル／タイムアウト／提供元不明／署名不一致（どれも通過扱いにしない） |
| 重大度 | 緊急／高／中／低／情報 |

ゲートの強制レベルは「警告のみ」「ソフト（例外で通過可）」「ハード」の3段階（部品 `EnforcementBadge`）。判定がどのレベルで出たかを常に添える。

### 出典と鮮度を必ず示す

経営向けの値の多くは、既存システム（課題・計画管理、カレンダー、Git、CI）から同期したもの。同期した値には出典（正本）と最終同期時刻を付ける（部品 `SourceTag`、`Freshness`）。同期が止まった・古いデータがある画面は、上部に `StaleDataNotice` を出し、古い値を最新のように見せない。正本で編集すべき項目は、本サービスに入力欄を置かず「正本で開く」リンクにする。

## 3. ロールと権限

1人が複数ロールを持つことがある（VSE では経営者が PM や技術責任者を兼ねることもある）。画面仕様の「操作」欄の権限は、このロール名で書く。ロールは人名と分けて設定し、役職から閲覧範囲や判断権限を自動で付与しない。

| 区分 | ロール | 所属 | 主な操作 |
| --- | --- | --- | --- |
| 直接利用者 | 経営者 | 開発会社 | ポートフォリオの確認、投資・優先順位・資源配分の判断 |
| 直接利用者 | 役員 | 開発会社 | 担当範囲の案件の確認と判断 |
| 直接利用者 | 事業責任者 | 開発会社 | 事業ケース、便益、ロードマップの判断 |
| 直接利用者 | CTO | 開発会社 | 技術リスク、品質統制、例外の判断 |
| 直接利用者 | 事業部長 | 開発会社 | 事業部内の案件・要員・予算の判断 |
| 直接利用者 | 案件スポンサー | 開発会社 | 担当案件の継続妥当性、重要判断、エスカレーション対応 |
| 直接利用者 | 組織管理者 | 開発会社 | 組織、利用者、連携、プランの管理 |
| 直接利用者 | ポリシー管理者 | 開発会社 | ゲートのルールと Control Pack の管理 |
| アクター | PM | 開発会社 | 計画、進捗、リスク、変更（課題・計画管理で実施） |
| アクター | アナリスト | 開発会社 | 要求の作成・管理（文書・課題管理で実施） |
| アクター | 設計者 | 開発会社 | 設計、ADR、レビュー（Git で実施） |
| アクター | 開発者 | 開発会社 | 実装、PR（Git で実施） |
| アクター | QA | 開発会社 | テスト、検証結果の記録（CI・テスト管理で実施） |
| アクター | リリース管理者 | 開発会社 | リリース準備と承認（リリース管理で実施） |
| アクター | 顧客 | 発注元 | 要求承認、変更承認、受入（期限付きの承認リンク、または顧客ポータル） |
| 外部 | 評価者 | 外部 | 共有された監査パックの閲覧のみ（期限付き） |
| 外部 | パートナー管理者 | コンサル等 | 委任された顧客組織の横断管理 |
| 直接利用者（追補） | 受注側統括責任者（JV責任者） | 受注側 | 受注・予算・遂行の統括、顧客への公開範囲の決定、外注枠と委任範囲の判断 |
| 直接利用者（追補） | 案件窓口 | 本サービス | 顧客との往復、条件変更の折衝、リリース調整、受入の回収、対外連絡の送信 |
| 直接利用者（追補） | フリーエンジニア | 受託者 | 条件の確認と受諾・相談・辞退、質問、成果の提出、合意範囲の修正、取引履歴の確認 |
| 直接利用者（追補） | 発注側プロジェクト責任者 | 発注企業 | 自社の案件の判断、自社の権限者の指名 |
| 直接利用者（追補） | 発注側担当者・承認者・検収者・署名者・管理者 | 発注企業 | 閲覧とレビュー、申請の承認、受入、契約の署名、権限者と代理の登録（それぞれ別の権限） |

追補の利用者は、同じ案件でも見える範囲が違う。顧客には契約額と公開済みの進捗・資料だけを見せ、JV内部予算、外注単価、個人別報酬、粗利、社内会議資料は出さない（業務提携型には合意した共同費目と各社の負担額を追加する）。受託者には自分の発注額と条件だけを見せ、規格の用語や管理帳票の入力を求めない。

アクターは本サービスのアカウントを持たず、外部システムの本人ID（GitHub、Jira、Slack 等）で記録する（部品 `ExternalActor`。対応付けは S-09）。経営層の画面では「経営の判断」と「実務の対応」を分けて示し（部品 `ResponsibilitySplit`）、経営層だけでプロセスを代替したように見せない。

職務分離: 作成者は自分の成果物を承認できない。判断の依頼者は自分の依頼を判断できない。ポリシー管理者は自分が関わる例外を承認できない。AIエージェントは承認、マージ、ポリシー編集、証跡削除ができない。操作できないボタンは非表示にせず無効化し、理由を表示する（部品 `SoDNotice`）。

## 4. 画面の共通仕様

個別の画面仕様に書いていない限り、次を適用する。

### 4.1 レイアウトの種類

| 種類 | 構成 | 使う画面 |
| --- | --- | --- |
| 公開レイアウト | `PublicHeader`、本文（最大幅1120px）、`PublicFooter` | 公開サイト |
| 中央寄せレイアウト | ロゴ、中央のカード（幅480px）、フッターのリンク | サインイン、招待、エラー |
| オンボーディング | ロゴ、`Stepper`（上部）、本文カード（幅720px）、「戻る」「次へ」 | オンボーディング |
| アプリ | `GlobalHeader`（上部固定）、`SideNav`（左240px、折りたたみ可）、`Breadcrumb`、`PageHeader`、本文 | 組織とプロジェクトの画面 |
| 詳細 | アプリのレイアウトの本文を、メイン（左）と `MetaSidebar`（右320px）に分ける | 各詳細画面 |
| ポータル | `PortalHeader`（プロジェクト名、ユーザー）、本文（最大幅800px）。サイドナビなし | 顧客ポータル、評価者ビュー |

### 4.2 一覧画面の共通仕様

- 上部に `FilterBar`（キーワード、状態、担当者、期間など画面ごとの条件）と、右端に主要な操作ボタン
- `DataTable`: 列の並べ替え、50件ごとのページ送り、行のクリックで詳細へ移動、列の表示切替
- 状態: 読み込み中（`Skeleton`）、0件（`EmptyState`。初回と絞り込み結果なしで文言を分ける）、取得失敗（`ErrorState` と再試行）
- 選択した条件はURLに残る前提でデザインする（再読み込みで保持）

### 4.3 詳細画面の共通仕様

- `PageHeader`: ID、タイトル、`StatusBadge`、主要な操作ボタン（最大3つ、残りは「その他」メニュー）
- `MetaSidebar`: 作成者、作成日時、更新者、更新日時、担当者、関連項目、承認状況（`ApprovalPanel`）
- メインの下部にタブ: 「内容」「関連」「履歴」（`Timeline`）「コメント」（`CommentThread`）
- 編集は同じ画面内で編集モードに切り替える。未保存で離れようとしたら `ConfirmDialog` を出す
- 承認済みの項目を編集すると状態が「変更中」に戻ることを、編集開始前に `Banner` で知らせる

## 6. 画面仕様

各画面の書式:

- **目的** — 画面で達成すること
- **利用者** — 主に使うロール
- **構成** — 画面を上から（または左から）順に分けた領域と、そこに置く部品
- **表示項目** — 表や詳細に表示するデータ
- **操作** — ボタンなどの操作、実行できるロール、実行後の結果
- **状態** — デザインが必要な画面の状態（共通仕様の状態は省略）

### 6.1 公開サイト

#### P-01 トップ

- **目的**: 経営層に、複数案件の計画・実績・リスク・判断事項を既存ツールから同期して一画面で示す価値を伝える
- **利用者**: 経営者、役員、事業責任者、CTO（未登録）
- **構成**
  1. ヒーロー: 見出し「全案件の計画と実績、判断事項をひとつの画面に」、説明、「PoCを相談」「機能を見る」、補足（既存のツールを読み取るだけ／開発者のアカウントは不要／判断は AI ではなく人）、ポートフォリオのイメージ（案件ごとの健全性、`SourceTag`、`PlanDates`（compact）、判断待ち）
  2. 課題 4 件: 遅れに気づくのが遅い、判断の根拠が残らない、現場に報告書を書かせている、品質の説明と監査前の証拠集め
  3. 仕組み 4 段: 既存システムから同期（システム）→ AI が要約（AI・参考）→ ルールと CI が検査（CI）→ 責任者が判断（人間）
  4. 主な機能 6 件: ポートフォリオ、計画とカレンダーの同期、経営判断の記録、投資と配分、ゲートと例外、証跡と監査パック
  5. 導入の流れ: 計画とカレンダーを接続 → コードホスティングを接続 → 警告モードで開始 → 段階的に強制
  6. 連携先: 課題・計画管理、共有カレンダー、コードホスティング、チャット、オンコールを `ProviderBadge`（ベータ・予定の表示付き）で列挙
  7. 信頼（学習に使わない、無効化できる、判定はルールと人）、セキュリティと稼働状況へのリンク、規格との関係の注記、CTA
- **対応する要求**: ORG-11, STD-08, 2.4

#### P-02 機能紹介

- **構成**: 機能ごとの節。先頭に経営層向けの 5 節を追加: ポートフォリオ（`SourceTag`・`PlanDates`）、計画とカレンダーの同期（`RoadmapTimeline`、当初・改訂・予測・実績の区別、非公開予定を取り込まない、読み取り専用）、経営判断の記録（`ResponsibilitySplit`）、投資と配分（個人の稼働監視をしない旨）、連携・通知・オンコール。既存の要求管理〜監査パックは維持。「顧客ポータル」は「顧客の承認と受入」に改め、期限付きの承認リンクを主にする
- **対応する要求**: ORG-11, 4.2.1, 4.5, 4.6, 4.7

#### P-03 料金

- **構成**: 課金は経営層シート＋プロジェクト数。開発者・PM・QA・顧客は課金対象外であることをリードと比較表に明記。プラン 4 枚（Starter: 2 シート・3 プロジェクト、Team: 5 シート・10 プロジェクト、Partner: 15 シート、Private）。比較表に シート数、プロジェクト数、アクター（課金なし）、計画・カレンダー同期、コードホスティング 4 種、チャット通知、オンコール連携、投資と配分を追加。追加サービスに「追加の経営層シート・プロジェクト」。FAQ に「開発者の分の料金」「GitLab・CodeCommit・Azure Repos」「上限でデータが消えるか」
- **対応する要求**: ORG-10, ORG-11, 4.11

#### P-04 セキュリティとデータの扱い

- **構成**: 既存の節に追加: 連携先の資格情報と同期データ（暗号化・分離・ローテーション、Webhook の署名検証、カレンダーは最小項目・非公開予定を取り込まない）、閲覧範囲とアクセス制御（役職で全社閲覧を付与しない、MFA、退職者の反映）、保存地域と削除（AI の再委託先とリージョン、組織削除時の複製の削除）、運用と障害への備え。問い合わせ欄に「脆弱性の報告」（P-11）と「稼働状況」（P-10）
- **対応する要求**: ORG-11, 4.13, SCM-10, 4.2.1-6, 4.8

#### P-05 規格との関係

### 6.3 組織の画面

#### O-01 経営ダッシュボード

- **目的**: 経営層が、案件全体の状況と経営判断が必要なことを短時間で把握する
- **利用者**: 経営者、役員、事業責任者、CTO、事業部長、案件スポンサー
- **構成**

  2. `StatCard` ×6: 判断待ち（うち3日以内）、遅延・注意の案件（予測が遅れたマイルストーン数）、予算超過見込み、証跡準備度（平均）、対応中のインシデント（未受領数）、7日以内に期限が来る例外
  3. 経営判断が必要なこと: 期限・影響額・重大度順の判断カード（最大4件）。実務上の承認者が別にいるものは回付の案内を表示
  4. 案件の健全性と計画対予測の表: 案件、健全性、終了日（当初→予測とずれ）、予測コスト／予算、証跡準備度、出典と鮮度
  5. 対応の分担（3列）: 経営判断が必要／運用担当の処理（連携の再認可など）／開発チームの対応（外部IDの担当者と出典のツール）
  6. 重大リスクと統制の状況: 影響×発生可能性が高い未完了リスク、ブロック中の PR、期限が近い例外
  7. ゲート運用の指標（既存）
  8. 右列: AIによる要約（参考。元データの ID リンクと確信度。確信度が低いものは警告）、予算・要員の要約（役割別・期間別。個人の稼働は出さない）、データの出典（案件ごとの `SourceTag`）
- **操作**: 各カード・行から詳細へ。ポートフォリオ、スケジュールへの導線
- **状態**: 通常、データが古い（全出典が古い同期時刻）、AI無効（`AIUnavailableNotice`）、空（連携先の接続・案件受付への導線）、読み込み中、エラー

- **利用者**: 経営層
- **構成**
  1. タブ: 判断待ち／担当者へ回付済み／判断済み（件数付き）
  2. 絞込み: 種類（投資、優先順位、要員・資源、リスク受容、例外、リリース・顧客説明、変更・追加費用、予算、便益・継続）、案件（組織全体を含む）

  4. マイルストーンの日付の表: 確度（確約・目標・予測・実績）、当初・承認済み改訂・予測・実績・ずれ（`PlanDates`）、依存先、担当
  5. 遅延の影響範囲: 遅れているマイルストーンから依存関係をたどり、後続への影響と確約日への影響を示す
  6. 次の判断と会議（共有カレンダーから）。オンコールの当番表はここに表示しない
  7. 計画変更の履歴: 種類（予測の更新、マイルストーンの延期、作業項目の期限変更、会議の移動・取消、計画の改訂）で区別し、変更前後、理由、変更者、承認者、出典を表示。基準日以前のものだけ表示
- **状態**: 既定、過去の基準日、同期が古い、読み込み中、取得失敗

#### J-11 マイルストーン・納入物

- **目的**: 成果物の提出と受入の状況を一元的に確認する
- **対応する要求**: PM-08、SI-12（受入・差戻し・再提出）
- **構成**: 正本の帯、`StatCard`（受入済み、差戻し中、受入待ち、予定日を過ぎた未提出）、絞り込み（状態、マイルストーン）、一覧（納入物、マイルストーン、予定・実績、提出先、提出版、状態、最後の出来事）、マイルストーンと納入物の対応。行を押すと `Drawer` で詳細（状態、予定・実績、提出先、提出版、ハッシュ、出典、提出・受領・差戻し・再提出・受入の履歴、差戻しの対応者）
- **状態**: 一覧の共通状態、詳細を表示

#### J-12 終了・引継ぎ

- **追加**: 運用への引受（運用先、保守期間、当番〈元の受託者を自動で当番にしない〉、終了後の照会の受付先）、手順・連絡先の引受記録、運用へ渡す既知の問題、未決済の取引。未引継ぎ・未決済があれば「終了を承認」を無効化
- **状態**: 「顧客受入済み・未引継ぎあり」を追加
- **対応する要求**: 30

#### J-13 文書・ファイルの取込み

- **目的**: リポジトリ以外の文書も含めて、証跡となる文書を取り込み管理する
- **対応する要求**: SI-13
- **構成**: 取込み元（連携した文書リポジトリ、手動取込み）、`StatCard`（取り込んだ文書、形式エラー、注意、経営層・PMのみ閲覧）、絞り込み（種類、形式検査）、一覧（文書、種類（Markdown・構造化データ・一般ファイル）、形式検査の結果と理由、版、SHA-256、データ分類、閲覧範囲、出典、取込み者・日時、関連）
- **操作**: 「ファイルを取り込む」（`Modal`: ファイル、種類、構造化データの形式、データ分類、閲覧できる人、関連付ける項目。Highly Confidential は AI に送らない旨）
- **状態**: 一覧の共通状態、形式エラーのみ、取込みモーダル
- **注意**: docs-as-code は必須にしない。形式エラーの文書は取込みを保留し、証跡として扱わない

### 6.5 プロジェクト: 要求・設計・トレーサビリティ

#### R-01 要求一覧

- **目的**: 要求の状態、承認版、受入基準、設計・テストへのつながりを一覧で確認する
- **利用者**: 経営層（閲覧）、組織管理者

- **操作**: 行を選んで「承認者に依頼」（R-04）、行クリックで R-02
- **状態**: 通常、読み込み中、空（正本に要求がない／未連携。連携の確認へ）、絞り込み結果0件、エラー、同期遅延（`StaleDataNotice`）

#### R-02 要求の詳細

- **目的**: 1件の要求の内容、承認版の固定、状態遷移、承認記録、下流へのつながりを根拠付きで確認する
- **利用者**: 経営層（閲覧）
- **構成**

  2. タブ「内容」: 本文、受入基準（なければ警告）、種類・優先度・出典・版・正本ファイル・関連課題
  3. タブ「トレース」: 設計→コード／PR→テストケース→実行結果→検証→妥当性確認→リリース成果物のリンク表（記録された場所、確定者。AI候補は「AI候補・未確定（確信度）」）

  5. タブ「AIの所見」（R-03 の埋め込み）、「コメント」（正本から同期）
  6. 右列: 状態と `StateFlow`、承認版の固定（版、日時、内容のハッシュ）、担当者、現在の版の承認（`ApprovalPanel` は判断不可・注記「承認者本人が正本または期限付き承認リンクで行う。経営層は代行しない」）、データ分類、関連する変更要求
- **状態**: 通常、承認済み、変更中（承認版 v3 のまま v4 が再承認待ち。差分への導線）、承認待ち、職務分離（作成者の承認を数えない `SoDNotice`）、差戻し（理由と日時）、廃止、同期遅延、読み込み中、エラー
- **対応する要求**: SI-01, SI-02, SI-04, 4.8（作成者と承認者の分離、承認後の版変更による失効）

#### R-03 AI要求レビュー

- **目的**: AIの指摘を人が判断し、要求の品質を上げる
- **構成**: 左に要求の本文（指摘箇所をハイライト。ハイライトを押すと右の所見へ移動）、右に `AIFindingCard` の一覧（種類ごとにまとめる: 不審な指示、曖昧性、矛盾、テスト可能性、不足）。上部にレビュー実行の情報（実行者、日時、モデル、テンプレートのバージョン、対象の版）
- **操作**: 所見ごとの採用（本文の修正画面へ。提案文を挿入可）・却下（理由必須）、「再レビュー」
- **状態**: 実行中、所見0件、本文が更新され所見が古い（`Banner` と再レビューの案内）、本文にAIへの指示とみられる文がある（`Banner`（失敗）: AIは従っていないこと、確認を依頼した相手を表示し、該当箇所をハイライト）、AI無効

#### R-04 要求の承認依頼

- **目的**: 選んだ要求の承認を、実際の承認者に期限付き承認リンクで依頼する
- **構成**: `Modal`。対象要求の表（状態、受入基準、未確認のAI所見、除外）、承認者（顧客・PM。作成者は選べない）、リンクの有効期限、依頼メッセージ
- **操作**: 「依頼する」→ 承認者ごとに1回だけ使えるリンク（`/approve/<token>`、送信先メール、メールの確認コードで本人確認、有効期限）を一覧表示
- **状態**: 条件を満たさない要求を含む、すべて条件を満たす、送信済み
- **対応する要求**: SI-02, 4.8（承認依頼・期限・本人確認）, ORG-07（期限付き承認リンクでの外部承認）

#### R-05 要求の版比較

- **目的**: 要求の版の差分と再承認の要否・状況、旧版（承認版）の証跡の保持を確認する

- **状態**: 通常（REQ-0008: 承認版 v3 → v4 再承認待ち）、再承認済み、比較できる版がない、読み込み中、エラー
- **対応する要求**: SI-01（変更前後の比較）, SI-02（承認版の固定、再承認）, SI-05, 6.1（承認済み要求の改訂は差分・再承認・旧版証跡を残す）

#### D-01 設計・ADR 一覧

### 6.6 プロジェクト: ゲート・PR・例外

#### G-01 ゲート実行の一覧

- **目的**: 接続したすべての Git サービスの PR／MR とブランチについて、ゲート A〜D の判定を確認する
- **利用者**: 経営層（閲覧）、ポリシー管理者

- **状態**: 読み込み中、0件、絞り込み結果0件、エラー
- **対応する要求**: SCM-01, SCM-07, 4.5.2, 4.4-1

#### G-02 ゲート実行の詳細

- **目的**: 判定の理由と根拠を、ルール・統制項目・判定主体・証跡まで辿れる形で示す
- **構成**
  1. 判定の要約（総合判定、修正が必要な項目、ゲート A〜D）
  2. ゲートごとの `GateResultPanel`
  3. ルールと判定の根拠（表）: ルールID、説明（自社作成）、対象の統制項目（V-02 へのリンク）、判定の主体（CI／人間）、必要な証跡、結果、修正案
  4. 入力した外部チェック結果（表）: チェック名、提供元、コミット、結果、扱い、受信日時。異常（`CHECK_ANOMALY`: 古いコミットの結果、必須チェックなし、重複、キャンセル、タイムアウト、提供元不明、署名不一致）はどれも「通過として扱わない」と表示する
  5. 必要な人間の承認（ゲートC）: 経営層の画面からは承認しない。承認は Git サービス上のレビューで行われ、外部IDで記録される
  6. AIの参考所見（判定に使わない）

### 6.16 連携と同期

#### K-01 連携と同期

- **目的**: すべての連携の状態と鮮度を一覧し、止まっている連携にすぐ対応する
- **利用者**: 組織管理者、経営層（閲覧）
- **構成**
  1. 止まっている連携（同期失敗・再認可が必要）の `Banner`。止まっている間の値は「古い情報」と表示することを明記
  2. 計画管理を持たないコードホスティング（AWS CodeCommit）がある場合の警告: 別の計画システムを接続しないと計画情報が欠ける
  3. `StatCard`: 接続中、止まっている連携、遅延している連携、受信イベントの再処理待ち
  4. 関連画面への導線: 外部データの対応付け（K-05）、正本と同期ルール（K-06）、受信イベントと再同期（K-07）、初期インポートと診断（K-08）
  5. 種類別（課題・計画管理、共有カレンダー、コードホスティング、CI・品質ツール、チャット通知、オンコール管理、証跡の保管先）の表: 接続（`ProviderBadge`、ベータ等の表示）、対象範囲・提供形態、状態（`SyncBadge` とエラー）、最終同期（`Freshness`）、対象数、方式（読み取りのみ／状態の書込み／送信のみ／応答操作）、操作（再認可、再試行、詳細）
  6. オンコール管理の節に「当番表の正本はオンコール管理サービス。計画同期とは別に扱い、更新・削除は波及しない」を表示
- **操作**: 連携を追加（K-02）、能力の比較（K-04）、再認可、再試行
- **状態**: 通常、連携0件（計画システムの接続を促す）、読み込み中、エラー
- **対応する要求**: 4.2.1-8、4.2.1 末尾（オンコールとの分離）、4.5.4（CodeCommit の計画ソース）、6.4（計画管理を持たない SCM の明示）、SCM-07

#### K-02 連携の追加

- **目的**: 取得するデータと書込みの用途を確認したうえで、外部サービスを接続する
- **利用者**: 組織管理者
- **構成**（`Stepper`: 種類 → サービス → 接続先 → 権限と取得データ → 対象範囲 → 正本 → 確認）
  1. 種類: `OptionCard`。計画管理と共有カレンダーに「優先」を表示
  2. サービス: ベータ・予定・非推奨（Opsgenie）を表示。予定は選択不可、非推奨は警告。CodeCommit 選択時は計画管理を別途接続する案内
  3. 接続先（ホスティング境界）: GitHub.com／Enterprise Cloud／Enterprise Server、GitLab.com／Self-Managed、Azure DevOps Services／Server、AWS アカウント ID・リージョン・引き受けるロールの ARN。自社運用は URL と TLS 検証の説明
  4. 権限と取得データ: 権限ごとの用途と読み取り／書込みの区別。資格情報は暗号化して保管し、組織・リポジトリ単位で分離し、画面・ログに出さない旨
  5. 対象範囲: カレンダーは共有カレンダーのみ（個人の予定表は既定で対象外）、非公開予定の除外、取得する項目の最小化（本文・参加者一覧は既定で取得しない）。個人予定を含めた場合は警告。SCM はリポジトリの選択
  6. 正本: 正本にする／参照のみ。初期は読取一方向で、ゲート結果の書込み以外は書き戻さない
  7. 確認: 設定の一覧と、初回は全件、以降は差分の説明
- **操作**: 戻る、次へ、接続して初回同期を始める（K-03 の初回同期中へ）
- **状態**: 各ステップ、権限不足（ステップ4でエラー。読み取りのみの接続ではゲートを必須にできない旨）、接続失敗（確認でエラー、問い合わせ用ID、再試行）
- **対応する要求**: SCM-02、SCM-09、SCM-10、4.2.1-1、4.2.1-6、4.2.1-13、4.5.2（AWS アカウント・リージョン、IAM ロール）、4.5.4、4.7（Opsgenie の非推奨）

#### K-03 連携の詳細

- **目的**: 1つの連携の同期の健全性を確かめ、止まったときに復旧する
- **利用者**: 組織管理者、接続者
- **構成**
  1. ヘッダー: 名前、`SyncBadge`、サービス、種類、提供形態。操作: 今すぐ同期、全件を再同期、再認可（必要時）
  2. 状態ごとの `Banner`: 再認可が必要（欠落期間を再認可後に自動で再取得）、同期失敗、遅延、初回同期中（完了まで経営ダッシュボードでは「判定不可」）
  3. `StatCard`: 最終成功、最終試行、同期の遅れ、対象数
  4. タブ「同期の状態」: 方式、周期、差分の位置（カーソル／syncToken／deltaLink）の有効・失効（失効時は全件再同期）、次回の実行、エラーの詳細。Webhook の検証方式・結果・最終受信・24時間の検証失敗。レート制限の残量と回復時刻、429 と Retry-After に従った待機（重複送信しない）。欠落期間の再取得（期間、状態、補完件数）。このサービスで使える能力の要約（K-04 へ）
  5. タブ「権限と取得データ」: 取得するデータ、書込みの用途、資格情報（種類、保管方法、最終ローテーション、有効期限、権限、接続者）とローテーション・失効・権限の縮小、接続の解除（取得済みデータの複製は保持期間に従って削除、証跡は削除しない）
  6. タブ「受信イベント」: 直近のイベント（K-07 へ）
  7. タブ「変更の記録」: 接続、切断、権限変更、資格情報の更新、再同期、手動修正の実行者と日時
- **操作**: 全件を再同期（確認ダイアログ。過去の計画履歴は消さない）、資格情報の失効（危険操作）、接続の解除（名前の入力が必要）
- **状態**: 現在の状態（既定）、同期中、遅延、再認可が必要、同期失敗、初回同期中、読み込み中、エラー

- **目的**: 条件を確認し、引き受ける・相談する・辞退する
- **利用者**: フリーエンジニア
- **構成**: 依頼ID・依頼元・依頼名、状態、版（`VersionPin`）、次に動く人。前の版からの変更（`TermsDiff`。例: ORD-0101 の v1→v2 は依頼額 40万→45万円、対象外に「6列目」を追加）。条件（作るもの、完成の判定、対象外、提出するもの、提出先、依頼額、納期、検収予定日、支払期日、支払方法。前の版と違う項目に「変更」）。資料（共有された資料と版）。既読と回答の記録（既読は受諾ではない）。受諾後は取引の6状態（`TradeStateStrip`）と合意した条件の控え
- **操作**: 「引き受ける」（版を明示した確認ダイアログでチェックが必要。送信中は押せず、控え ACK-… を発行）、「条件を相談する」（見積額・開始可能日・納期の対案・理由。新しい版を承諾するまで条件は確定しない）、「辞退する」（理由は任意）、「質問する」、受諾後は「成果を提出する」「合意した条件の控えを保存」
- **状態**: 表示中の依頼（ルートの依頼）、回答待ち、受諾済み、旧版を表示中（v1 を開いたまま「引き受ける」を押しても受諾にならず、新しい版の通知と再読込を出す）、相談中、辞退、条件未確定（支払期日・支払方法などの必須項目が未設定で、回答できない）
- **対応する要求**: 02, 04, 08

#### F-04 質問と回答

- **目的**: 仕様の質問や「作業を進められない」連絡を一度で窓口に渡し、確定した回答を受け取る
- **利用者**: フリーエンジニア
- **構成**: 「質問する」「作業を進められない」ボタン、入力フォーム、自分の質問の一覧（受付番号、依頼ID、状態、回答予定・回答日）と詳細（本文、作業停止の内容、受付日時、担当窓口と代理の有無、回答予定、「窓口が発注企業へ確認中。あなたの操作は不要」、確定した回答と根拠、経過）、補足の送信
- **操作**: 質問（対象の依頼・件名・内容）、作業停止の連絡（いつまでに必要か・止まっている作業・暫定案）→ 受付番号と回答予定の控え。補足を送る、遅れる見込みを連絡、回答を確認しました
- **状態**: 通常、質問を作成、作業停止の連絡、回答済みを表示、空。回答を待つ間は本人の対応件数に数えない。発注企業の連絡先は表示しない
- **対応する要求**: 05, 08

#### F-05 成果の提出

- **目的**: 外部の開発環境で作った成果の参照を、提出時の版を固定して提出する
- **利用者**: フリーエンジニア
- **構成**: 合意した完成条件（自己確認のチェック）、成果の参照（Git サービスの選択: GitHub／GitLab／Azure Repos／AWS CodeCommit、「参照を取り込む」、PR/MR の URL、確定コミット SHA、成果物の識別子）、確認結果、注意点。画面下に「提出する」「下書きを保存」
- **操作**: 参照の取込（PR と確定コミット、CI の結果を取得）、下書きの保存、提出 → 控え SUB-…（提出した版・次の担当・検収予定日）、控えの保存、F-06 へ
- **状態**: 入力中、参照を取込済み、提出済み（控え。PR にあとからコミットが増えても提出時の版を検収する）、連携障害（確認待ち。手入力で提出でき、提出日時を残して窓口が参照を確認）、下書きを復元、セッション切れ（入力を保ったまま確認コードで再開）。送信中は二重送信できない
- **対応する要求**: 06, 08, 23（提出側）, 31（提出側）

#### F-06 提出結果・修正

- **目的**: 委託元の検収結果と次の担当を確認し、合意範囲の修正だけを再提出する
- **利用者**: フリーエンジニア
- **構成**: 検収の状態と検収予定日、次に動く人、取引の6状態（`TradeStateStrip`）、完成条件ごとの検収結果（合格・差戻し・確認中、分納の回、差戻しの理由と再現手順）、修正版の提出、提出履歴（旧版を残す）
- **操作**: 修正版の提出（確定コミットと修正内容）→ 控え。差戻しの理由について質問。範囲外の要望は窓口に相談（無償の修正タスクを自動で作らない）
- **状態**: 検収中、一部検収（分納。検収済みの分は支払期日どおり）、差戻し（範囲内の修正）、範囲外の要望（新しい依頼として窓口が条件を提示）、検収済み（配備・顧客の受入・支払は別に進み、顧客の受入を待って支払期日を繰り下げない）、未提出
- **対応する要求**: 07, 24（受託者から見た検収）

#### F-07 取引履歴

- **目的**: 自分の発注額・検収・請求・支払を確認し、帳票を取得し、不一致を照会する
- **利用者**: フリーエンジニア
- **構成**: 支払期日の方針（顧客の受入や請求書の到着日で繰り下げない）、合計（発注額・検収済み・支払済み。本人の分だけ）、依頼ごとの表（発注額、検収額、請求番号と日付、支払期日、支払実績、状態、発注書・提出控えの取得）
- **操作**: 発注書（受諾した版）と提出控えの保存、金額・期日の照会（対象・種類・内容 → 受付番号と回答予定）
- **状態**: 通常、不一致を照会（支払額と検収額の不一致を表示）、依頼元を切替、空。依頼元と発注企業の契約額やほかの受託者への発注額は表示しない。契約終了後も帳票を取得できる
- **対応する要求**: 16（受託者側）

### 6.19 案件窓口

サービスの案件窓口（担当者とAI・ルール）が、顧客との往復、条件変更の折衝、対外送信、期限と代理を管理する画面。

#### H-01 窓口の受信箱

- **目的**: 受託者・顧客・JV からの問い合わせを案件ごとに受け付け、回答待ちの相手・担当・代理・期限を一覧で管理する
- **利用者**: 案件窓口
- **構成**: 営業時間・休業日の帯（`Banner`）、`StatCard`（未回答、顧客へ確認中、期限超過（代理へ移行済みを含む）、保留（案件不明））、`Tabs`（未回答／受託者から／顧客から／JVから／回答済み）、問い合わせ台帳（`DataTable`: 受付番号、件名と案件・発注、発信側（`FromTag`＋`ExternalActor`）、状態、回答待ちの相手、担当・代理、応答期限（超過日数））、再合意中の変更条件（顧客との条件・委託条件の状態、H-04 へ）、保留中の返信（案件を特定できない返信。どの案件にも表示しない）
- **操作**: 行から H-02 へ。保留の返信を「案件に結び付ける」（送信者が当事者の案件だけを候補に出す）。対外送信の承認（H-03）、担当と期限（H-05）、週報（H-06）へ
- **状態**: 通常、AI停止中（受付と定型の受領通知は継続し、回答は定型文と手入力で続ける説明）、空、読み込み中、エラー
- **対応する要求**: 17, 21, 36

#### H-02 問い合わせの往復

- **目的**: 1件の問い合わせの往復を一続きで扱い、根拠のある回答だけを、見せてよい相手に送る
- **利用者**: 案件窓口
- **構成**: 往復の履歴（受信経路＝案件別の受信アドレス・限定フォーム・アプリ内、公開範囲 `AudienceTag`、社内メモは顧客・受託者に出さない）、回答欄（AI の回答案＝確信度・モデル・テンプレート版、文面、根拠の表＝資料・版・公開範囲・「版を開く」、送信前の検査＝社内メモ・外注単価・確約日と予測日の区別・根拠の公開範囲、宛先）、右列に受付情報・担当と代理・関連する発注・記録
- **操作**: 「確認して送信」で宛先・文面・対象版・重複防止キーを確認してから窓口名義で送信。送信後は二重に送れない。受託者への回答は質問した本人にだけ表示する
- **状態**: 回答案あり、受託者への回答、顧客返信を取り込み（件名の受付番号で元の質問に結び付けたことを表示）、根拠不足（確認質問。承認済み資料に答えがない問いは回答案にせず顧客への確認質問にする）、社内情報の混入を検出（外注の金額を含むため送信不可）、回答済み、AI停止中（定型文から作成）、読み込み中、エラー
- **対応する要求**: 17, 18, 19, 36

#### H-03 対外送信の承認と配信結果

- **目的**: 窓口名義の対外連絡を、委任済みの定型連絡と人の確認が必要な連絡に分け、配信結果まで追う
- **利用者**: 案件窓口、受注側統括責任者（JV責任者）
- **構成**: 委任ルールの表（受領通知・回答予定・定型の催促は自動、金額・範囲・納期・障害説明は常に人が確認）、`Tabs`（確認待ち／配信失敗／送信済み／自動送信の記録）、送信のカード（区分、状態、案件、重複防止キー、宛先、送信経路、対象版、送り方、承認者と日時、送信日時、文面）
- **操作**: 「宛先・文面・対象版を確認して送信」、承認後に宛先・文面が変わったものは「変更後の内容で再承認して送信」、配信失敗は「代替経路（メール）で再送」（同じ重複防止キーで二重発信しない）。回答が届いて送らなかった催促は「送信しなかった」と記録
- **状態**: 通常、再承認が必要、配信失敗、空、読み込み中、エラー
- **対応する要求**: 19, 21, 32

#### H-04 変更条件の再合意

- **目的**: 1つの変更要求について、顧客との条件と受託者への委託条件を別々に合意し、両方がそろったものだけを反映する
- **利用者**: 案件窓口、受注側統括責任者（JV責任者）
- **構成**: 顧客との条件（状態、顧客への追加費用、期限への影響、発注側承認者、合意日時。顧客に公開）と委託条件（状態、対象の発注、受託者、追加の報酬、期限への影響、経過。社内と受託者本人のみ）を左右に並べる。責任の分担（`ResponsibilitySplit`: 顧客の承認・受託者の承諾・経営判断／案件窓口）。合意がそろったときの更新候補（要求・発注・計画）
- **操作**: 両方の合意がそろったら「更新候補を作る」（正本の担当者へリンクを送る）と「確定版を受託者の画面で確認」（F-03）。経営判断が必要なら M-02 へ。合意前はどちらも押せず理由を表示する
- **状態**: 顧客のみ合意（委託範囲は増えていないことを表示）、受託者が相談中、両者合意、経営判断が必要、読み込み中、エラー
- **対応する要求**: 20, 07, 14

#### H-05 担当・代理・応答期限

- **目的**: 回答・判断を待っているものごとに、追いかける人と、期限を過ぎたら引き継ぐ人を決める
- **利用者**: 案件窓口
- **構成**: 営業時間の帯、待ちごとのカード（種類＝質問・未検収・承認待ち・受入待ち、対象、待っている相手、主担当、代理（現在の担当の表示）、応答期限、次の連絡先、催促と引継ぎの段階＝送信済み・予定・送らない（回答済み）・完了）
- **操作**: 「担当と期限を変更」（主担当と代理は別の人でなければ保存できない）
- **状態**: 通常、代理へ移行、休業日（休業日の期限は翌営業日に、催促も送らない）、読み込み中、エラー
- **対応する要求**: 21, 05

#### H-06 相手別の週報

- **目的**: 同じ実績から、相手ごとに見せてよい内容だけで週報を作る
- **利用者**: 案件窓口
- **構成**: `Segmented`（顧客向け／上層部向け／受託者向け。受託者向けは対象者を選ぶ）、週報（宛先、公開範囲、AI の要約（参考）、根拠付きの記述＝根拠と取得時刻、顧客向けに出していない情報の注記）、記述の出所の表（どの記述を誰向けに使うか）
- **操作**: 相手の見え方の確認、送信（社外向けは H-03 の確認待ちに入る）。社外向けでは「社内版を添付する」を選べない
- **状態**: 顧客向け、上層部向け、受託者向け、AI無効（定型の報告をそのまま組み立てる）、読み込み中、エラー
- **対応する要求**: 22, 36

### 6.20 受託者への発注と採算

受注側の経営層が、受託者への発注、稼働枠、照合、委託単位への分解、外注原価を扱う画面。

#### B-01 受託者への発注

- **目的**: 受注側が受託者に出した依頼を一覧で把握し、次に動く人と期限を確認する
- **利用者**: 受注側の経営層（JV責任者）、案件窓口
- **構成**: `StatCard`（回答待ち、委託検収待ち、作業中、完了）、社内のみの注記、`FilterBar`（案件、発注条件、次に動く人、キーワード）、`DataTable`（発注番号と件名、受託者 `ExternalActor`、条件の版 `VersionPin`、取引の状態 `TradeStateStrip`、次に動く人 `NextActor` と期限、報酬（社内のみ））
- **操作**: 「依頼書を作成」（B-02）、行から B-03
- **状態**: 通常、絞り込み、0件、読み込み中、エラー。この組織が出した発注だけを表示し、受託者がほかの依頼元から受けている発注（例: ORD-0201）は出さない
- **対応する要求**: 02, 03, 04, 24

#### B-02 依頼書の作成

- **目的**: 承認済みの案件から条件を引き継いで、受託者への発注条件を作り、版として確定発行する
- **利用者**: 受注側の経営層（JV責任者）、外注枠の委任者
- **構成**:
  1. 引き継ぐ案件（`Select`）と、引き継ぐ値（状態、予算上限、依頼可能な範囲、案件窓口、納入責任者）。開始が承認されていない案件には警告
  2. AI の分解案（「AI・参考」。採用は人が決める）
  3. 発注条件: 受託者、発注日、作業内容、対象外、完成条件、納入先、納入期日、検査期日、報酬、支払期日、支払方法、発注者
  4. 発行前の確認: 開始承認・必須項目・外注枠の範囲のチェック、不足項目の列挙、支払期日が納期から60日を超える場合の確認、取引条件の明示と支払期日の管理に関する注記（公正取引委員会の案内を参照し、適用関係を確認する旨）
- **操作**: 「AI で分解案を作る」「下書き保存」「確定して発行」（未承認案件・不足項目・外注枠超過のときは理由付きで無効）。発行後は受付番号と v1 の控えを表示。二重送信しても二重発注にならない
- **状態**: 入力済み、必須項目の不足、保留中の案件（正式発注不可）、AI の分解案、発行済み
- **対応する要求**: 02, 09, 11

#### B-03 発注の詳細

- **目的**: 条件の版・受諾・提出・委託元の検収・修正の仕分けを1つの発注で追う
- **利用者**: 受注側の経営層（JV責任者）、指定検収者、案件窓口
- **構成**:
  1. `PageHeader`（ID、件名、`VersionPin`）、`TradeStateStrip`
  2. 条件の版と差分（v1 と v2 の項目別比較。変更箇所を強調し、変更理由を表示）
  3. 受託者との相談（提示・既読・条件の相談・再提示・受諾の経緯。既読は受諾ではない）
  4. 提出（提出番号、確定コミット、外部の参照、確認結果、注意点、照合の結果。提出時の版で照合し、PR の先端が後で動いても対象は変わらない）
  5. 委託元の検収（成果完成型／稼働報告型の切替、分納ごとの完成条件別の合格・理由付き差戻し、給付の受領日・検査期日・検収日・支払期日、一部検収の説明、最終顧客の受入とは別記録である旨）
  6. 修正と追加依頼の仕分け（要望、出所、判定、根拠、次の対応。範囲外は追加見積へ）
  7. サイド: 当事者（発注者、受託者、指定検収者、案件窓口）、金額（社内のみ）、関連
- **操作**: 「条件を改訂」（新しい版の下書き。受託者が承諾するまで旧版が有効）、検収の「合格」「差戻し」（理由必須）、「追加見積へ」
- **状態**: 通常（発注者の視点。自己検収は不可で `SoDNotice`）、指定検収者の視点、差戻し、一部検収（分納1 合格・分納2 差戻し）、回答待ち、読み込み中、エラー
- **対応する要求**: 02, 04, 07, 24

#### B-04 外注候補と稼働枠

- **目的**: 本人が共有した稼働枠と、仮押さえ・受諾済みの枠を比べて依頼先を決める
- **利用者**: 受注側の経営層、外注枠の委任者（事業部長）
- **構成**: 月の切替、社内のみの注記（個人の予定表は取り込まない、個人の監視に使わない）、超過の警告、候補ごとの技能・単価（社内のみ）・共有された枠・受諾済み・仮押さえ・残り・共有日、仮押さえと受諾済みの枠の一覧（期限、割当者、枠に戻した理由）
- **操作**: 仮押さえの「解除」（枠に戻す）、「依頼書を作成」
- **状態**: 通常（仮押さえの重複で共有枠を超過）、辞退で枠を戻した、0件、読み込み中、エラー
- **対応する要求**: 10

#### B-05 発注・検収・請求・支払の照合

- **目的**: 分納別に検収・請求・支払を照合し、不一致を検出する
- **利用者**: 受注側の経営層、経理担当
- **構成**: `StatCard`（不一致、今月の支払予定、支払済み）、社内のみの注記、支払期日を繰り下げない旨、照合の表（発注・分納、給付の受領日、検収額と日付、請求書番号と請求額、支払期日、支払実績と取込元、照合の結果: 一致・一部検収・金額違い・二重請求・検収前の請求・支払期日超過）

- **状態**: 新規公開（既定。顧客チームの準備と JV への招待へ進む案内、譲渡条件の確認は出ない）、担当交代、アプリ移管（譲渡条件の確認と Q-04 への導線が出る）、加入状況未確認（作業表は仮）、読み込み中、エラー
- **対応する要求**: 56

#### Q-02 Apple Developer 組織登録の支援

- **目的**: 顧客が自社名義で組織登録するための準備と期限を管理し、加入の確認を根拠付きで記録する
- **利用者**: 案件窓口、JV責任者。手続きは発注側プロジェクト責任者が Apple 上で行う
- **構成**: 状態の帯、申請前にそろえる情報（法人名、D-U-N-S 番号、組織の Web サイト、組織のドメインのメール、契約権限のある申請者。担当・期限・状態）、顧客本人が Apple 上で行う手続き（Apple Account と2ファクタ認証、申請・本人確認・規約同意、年会費の支払い。担当・期限・状態・再開先）、Apple 上の手続きの注記、加入確認の根拠（チーム名、Team ID の末尾、確認した人、日時、方法、記録した人）
- **操作**: 加入を確認（Apple の確認が終わり顧客が加入を示すまで無効）、作業者の招待へ（加入済みのとき）
- **状態**: 新規申請中（既定。Apple の確認待ち）、加入済み（根拠を表示し、チーム確認へ進む）、不足項目あり（D-U-N-S の登録名の不一致、申請者の契約権限の未確認）、読み込み中、エラー
- **対応する要求**: 57

#### Q-03 App Store Connect の作業者招待

- **目的**: 顧客のチームの権限者が承認した宛先・役割・対象アプリだけを、許可された API で招待・照会・取消する
- **利用者**: 案件窓口、JV責任者
- **構成**: 範囲の説明（承認は顧客の権限者、受諾は招待された本人）、照合が必要な招待の帯、重複の帯、招待の一覧（宛先、役割と対象アプリ、承認者と日時、状態＝顧客の承認待ち／招待中（未処理）／参加済み／取消済み／期限切れ／照合中、操作）、承認済みの新しい宛先
- **表示項目**: 対象アプリを限定できない役割（Admin）は「チームのすべてのアプリに及ぶ」と明示
- **操作**: 招待を作成（承認済みの宛先だけ。送信中は無効、作成後は「作成済み」と受付番号。同じ宛先に未処理の招待があれば作成できない）、取消、所属と照合（未処理一覧から消えた招待を所属一覧と照合し、受諾・期限切れを確定）、再招待（期限切れは顧客の再承認が必要）
- **状態**: 通常、照合の結果: 参加済み、照合の結果: 期限切れ、重複の防止、空、読み込み中、エラー（最後に取得した一覧の時刻を表示）
- **対応する要求**: 58

#### Q-04 公開済み iOS アプリの移管

- **目的**: 別のチームで公開済みのアプリを顧客のチームへ移す。譲渡元の開始と譲渡先の承諾を別のタスクとして照合する
- **利用者**: 案件窓口、JV責任者、開発担当（移行作業）。開始・承諾は各チームの Account Holder が Apple 上で行う
- **構成**: 状態の帯、対象（アプリ、Bundle ID、譲渡元・譲渡先のチーム、公開済みのバージョン数）、譲渡の条件のチェック（公開済みのバージョンがある、両チームの契約が有効、譲渡元に未完了の手続きがない、利用中の機能の移行作業を確認済み。観点は自社でまとめたもので、最終的な条件は Apple の案内で確認する旨）、利用中の機能ごとの移行作業（プッシュ通知、App 内課金、Apple でサインイン、共有の保存領域。担当・状態）、開始と承諾の2つのカード、注記（配信チームの移管と知的資産の帰属は別記録。Y-04 へのリンク）
- **操作**: 所属を確認して完了にする（条件をすべて満たし、開始済みで、承諾を確認したときだけ。完了後は無効）
- **状態**: 条件確認中（既定）、未リリースのため対象外（この手順に進まず、新規公開の方式へ案内）、譲渡元が開始済み（承諾待ち。開始だけでは完了にしない）、移管完了（両方を照合し所属を確認）、条件不成立（理由と再確認の期限を記録）、保留（保留者・理由・再開予定を記録）、エラー
- **対応する要求**: 59

#### Q-05 運用権限の引き渡し

- **目的**: 資産ごとに引き渡し後の責任者と作業を決め、顧客が自社の権限で運用できることを確認してから JV の一時権限を外す
- **利用者**: JV責任者、案件窓口。確認は顧客の担当者・当番
- **構成**: 資産ごとの責任者（ストア、クラウド、ドメイン、障害通知、証明書・鍵、請求と更新。現在、引き渡し先、必要な作業、確認方法、期限、状態）、顧客による確認（次の版のアップロード、試験通知の受信、JV が作成した鍵の失効）、JV の一時権限の一覧、未完了の項目の帯（担当と期限を残す）
- **操作**: 引渡明細の控えを交付（秘密値を含まない）、JV の一時権限を解除（顧客の確認がすべて済むまで無効、解除の記録を残す）
- **状態**: 引き渡し中（既定）、顧客の確認済み（請求と更新が未完了で残る例）、一時権限を解除済み、読み込み中、エラー
- **対応する要求**: 60

#### X-15 アプリ・資産の引き渡し（顧客）

- **目的**: 発注企業が、配信名義、自社が行う作業、受注側・窓口の作業、運用の引き渡し先を確認し、運用開始を受領する
- **利用者**: 発注側プロジェクト責任者（藤井 晃）。顧客ポータルの「引き渡し」タブ
- **構成**: 状態の帯（自社の対応が必要な作業の件数と期限／受領待ちの案内／受領の控え）、配信名義（アプリ、配信する法人、方式、決定者）、貴社が行うこと（どこで・担当・期限・状態）、Apple 上の手続きの注記、JV の作業者の招待の承認（宛先・役割・対象アプリと範囲の説明）、受注側・案件窓口が行うこと、運用の引き渡し先（鍵やパスワードは表示しない）
- **操作**: 招待の承認・差戻し（承認後は無効、受付番号）、運用開始を受領（引き渡しの確認が済んだときだけ。受領後は無効、受付番号と控え）
- **状態**: 新規公開（Apple確認待ち）、招待の承認が必要、運用開始の受領待ち、受領済み、アプリ移管、読み込み中、エラー
- **対応する要求**: 56, 57, 58, 59, 60

### 6.24 提出から配備・受入まで

受託者の提出を検証と照合し、リリース候補、実行許可、配備、切戻し、取引の証跡までをつなぐ画面。

#### L-05 提出と検証の照合

- **目的**: 受託者の提出を、合意した完成条件・提出時点のコミット・同じコミットのビルドとテスト・検証者とそろえる
- **利用者**: 案件窓口、JV責任者（閲覧）
- **構成**: 提出ごとの照合表（発注、受託者、提出版のコミット、ビルド、テスト、完成条件の確認数、検証者）。選んだ発注の `TradeStateStrip`、完成条件ごとの結果と根拠、不足分の対応先、提出版（URL・コミット・受託者の確認・注意点）、関連リンク（T-06、L-06、V-09）
- **操作**: 不足分を対応先（検証者等）へ回す（窓口。回付済みは再送不可）
- **状態**: 通常、別コミットの成功結果を流用しようとした（`Banner`（失敗）で拒否し「別コミット（流用不可）」と表示）、提出なし、読み込み中、エラー
- **対応する要求**: 23

#### L-06 リリース候補と顧客向け説明

- **目的**: 複数人の提出と社内の変更から対象分だけを選び、リリース候補を固定する
- **利用者**: 案件窓口、JV責任者
- **構成**: 候補に入れるもの（提出・PR・変更要求。未提出や人間のレビュー承認がない変更は選べず理由を表示）、顧客向けの説明（AI 下書き。候補外の項目は「説明に載せないもの」として別に列挙）、移行と切戻しの手順、固定する版（候補ID・ダイジェスト・コミット）、試験、既知の問題、連絡先
- **操作**: 候補を固定（確認ダイアログ）。固定後は実行許可の回収へ
- **状態**: 選択中、固定済み、AI 無効（定型文で説明を組み立て）、読み込み中、エラー
- **対応する要求**: 25

#### L-07 Go/No-Go の回収と実行許可

- **目的**: 実務承認と必要な経営判断を回収し、成果版・ルール版・承認者・対象環境・時間枠を固定した実行許可を発行する
- **利用者**: 案件窓口（回収）、JV責任者（判断は M-02）
- **構成**: 回収の状況（`ChecklistPanel`: 候補の版一致、必須チェック、リリース管理者・PM の承認、Go/No-Go、環境と時間枠）、責任の分担、AI の評価は結果を変えない旨、許可に固定する内容（許可ID、候補とダイジェスト、ルール版とハッシュ、環境、時間枠、配備手順）
- **操作**: 実行許可を発行（条件がそろうまで無効化し理由を表示。二重発行しない）
- **状態**: 経営判断待ち、発行できる、発行済み、版の差替え、必須チェック失敗、承認期限切れ、読み込み中、エラー
- **対応する要求**: 26

#### L-08 配備依頼と完了確認

- **目的**: 事前登録した外部 CI/CD の手順だけを、許可された版・環境・時間枠で起動依頼し、結果を外部の実行IDで照合する
- **利用者**: 案件窓口、運用責任者
- **構成**: 配備の進行（起動依頼〈冪等キー＝実行許可ID〉、各段階、ヘルスチェック、外部結果との照合）、後続の作業（顧客への完了連絡、受入依頼、「公開済み」表示は確認まで止める）、実行許可、配備専用の接続（読取接続とは別）
- **操作**: 配備を起動依頼（1つの許可で1回だけ）
- **状態**: 時間枠待ち、配備中、結果未確認（通知途絶 → 実行IDで照会）、確認済み、同じ許可の再送（二重に配備しない）、読み込み中、エラー
- **対応する要求**: 27

#### L-09 配備失敗・切戻し・続報

- **目的**: 部分失敗時に後続を止め、運用責任者に前版・影響・切戻し手順を渡し、復旧確認と顧客への続報を追う
- **利用者**: 運用責任者（切戻しの判断）、案件窓口（続報）
- **構成**: 失敗の内容（失敗・完了した段階、止めた作業、前の版、顧客への影響）、承認済みの切戻し手順の進行、顧客への続報（確認者・送信状態）、責任の分担、案件の完了条件
- **操作**: 復旧を確認（切戻し実行後のみ）
- **状態**: 失敗、切戻し中、復旧確認済み（v1.4.0 は未配備のため案件は未完了）、読み込み中、エラー
- **対応する要求**: 28

#### V-09 取引の証跡と不足一覧

- **目的**: 任意の納入物について、発注版→受諾→提出→検証→委託検収→リリース→顧客受入の記録一式と不足箇所を再現する
- **利用者**: JV責任者、案件窓口
- **構成**: 納入物（発注）の選択、不足件数の `Banner`、`TradeStateStrip`、記録の連鎖（実行者・対象版・原本ハッシュ・時刻・訂正履歴・不足の注記）、経営側で確認したい問い4つと不足表示、証拠に数えないもの（AI の下書き）
- **操作**: 第三者に共有する範囲を選ぶ（V-08 へ）
- **状態**: 不足あり、すべてそろっている、読み込み中、エラー
- **対応する要求**: 34

## 7. 主要な利用の流れ

デザインはこの流れが途切れず辿れることを確認すること。

1. **導入（経営層）**: A-01 → A-04 → A-05（コードホスティング）→ A-06 → A-11（計画・カレンダー）→ A-13（適用範囲）→ A-07 → A-12（通知先）→ A-08（経営層の招待）→ A-09 → A-10 → M-01
2. **朝の確認**: O-01（判断待ち、遅延、同期の鮮度、AIの要約と根拠）→ M-01（ポートフォリオ）→ J-01 / J-10（案件の計画対予測）→ M-12（今週の会議と判断期限）
3. **経営判断**: O-02（判断待ち）→ M-02（選択肢・根拠・影響を確認し、理由を付けて判断。実務の承認者が別なら回付）→ M-03（判断ログ）。判断後のフォローアップは M-02 で追跡する
4. **案件の立上げ**: M-04 → M-05（事業ケース。現場が作成）→ M-06（開始・保留・却下）→ O-05（承認済みの事業ケースからプロジェクトを作成し、版を固定）
5. **優先順位と資源の配分**: M-07（シナリオ比較と順位変更の判断）→ M-08（役割別の需給と予算）→ M-09（ロードマップへの影響）
6. **要求の確定（実務）**: 文書・課題管理で作成された要求が同期される（R-01、R-02）→ R-03（AIレビュー、参考）→ R-04（実際の承認者に期限付き承認リンクを送る）→ X-06（顧客がアカウントなしで承認）→ R-05（版の差分と再承認）
7. **ゲートと例外**: Git サービス上の PR／MR → W-01（提供元ごとのゲート表示）→ G-02（ブロックの理由、異常、修正方法）→ E-02（現場の申請）→ E-03（独立した承認。重大なリスク受容は M-02 の経営判断へ）

10. **インシデント**: N-06 → N-07（受領と解決を分けて記録、エスカレーション、代替経路）→ N-08（訓練の記録）
11. **監査対応**: V-01 → V-02 → V-06（監査パックの出力）→ V-08（期限付き共有）→ X-04（評価者が閲覧）
12. **外注の発注と受諾（追補）**: M-06（開始承認）→ B-06（委託単位への分解）→ B-02（依頼書。必須項目がそろうまで発行しない）→ F-01（受託者の招待と本人確認）→ F-02 → F-03（条件を確認して受諾、または相談・辞退。受諾は版に紐付く）→ B-03（受諾した版と相談の経緯）
13. **質問と回答（追補）**: F-04（受託者が一度だけ質問）→ H-01 → H-02（窓口が根拠付きの回答案を作り、顧客へ確認）→ X-08 / X-09（顧客が回答）→ H-02 → F-04（確定した回答を本人にだけ返す）
14. **追加要望と再合意（追補）**: X-01a（顧客が6列目を希望）→ H-04（顧客条件と委託条件を別々に合意。顧客だけの同意では委託範囲は増えない）→ M-02（費用・期限の経営判断）→ F-03（新しい版の提示と受諾）
15. **提出から顧客受入まで（追補）**: F-05（確定コミットを提出し控えを受け取る）→ L-05（同じコミットの検証結果と照合）→ B-03（委託元が完成条件ごとに検収。支払期日は固定）→ L-06（リリース候補）→ L-07（実行許可）→ L-08（配備と完了確認）→ L-03 / X-03（顧客の受入）→ F-07（受託者の取引履歴）→ V-09（取引の証跡）
16. **顧客への公開（追補）**: U-01（顧客との関係）→ U-02（公開設定）→ U-03（顧客目線のプレビューと混入検査、公開版の確定）→ X-01（顧客の案件ホーム）→ U-04（公開停止と配信履歴）
17. **契約とアプリの引き渡し（追補）**: Y-01 → Y-02 / X-14（条項の協議と署名）→ Y-03 / Y-04（知的資産と権利の配分）→ Q-01（配信名義）→ Q-02 / X-15（顧客の組織登録）→ Q-03（作業者の招待）→ Q-05（運用権限の引き渡しと一時権限の解除）→ Y-06（権利の引渡明細）

## 9. 実装の制約（Rust 側への移植のため）

受け取った Next.js のモックは、Rust のバックエンドと組み合わせる形に移植する。移植しやすくするため、次を守ること。

- **画面は表示専用にする**。業務ロジック（ゲート判定、権限判定、状態遷移）を書かない。表示に必要な値と「操作できるか・できない理由」はすべて props で受け取る
- **Next.js 固有のサーバー機能を使わない**。Server Actions、Route Handlers、Middleware、サーバーでのデータ取得を使わない。`next/image`、`next/font` などに依存しない
- **データはモックで与える**。型付きの固定データを1か所に置き、ページはそれを読み込んで描画する。型も1か所にまとめる。項目名は将来のAPIに合わせて英語の snake_case にする
- **スタイルはCSS変数のデザイントークンと素のCSS（CSS Modules 可）にする**。実行時の CSS-in-JS は使わない。Tailwind を使う場合はトークンをCSS変数で定義する
- **依存ライブラリを最小にする**。UIライブラリやグラフ描画ライブラリを使う場合は、事前に名前と理由を挙げる
- **部品は第5章の名前で作る**。画面ファイルの冒頭に画面IDをコメントで書く
- **文言は辞書ファイルに集約する**
- **外部通信をしない**。アナリティクス、外部フォント、CDN、外部画像を読み込まない
- **サンプルデータは架空のもの**にする。実在の会社名、人名、ISO 規格本文を使わない
