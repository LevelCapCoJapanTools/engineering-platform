# Webデザイン依頼書

この文書は、Webデザイナー（エージェント）に画面デザインと Next.js による画面モックを依頼するためのもの。製品の前提は [SSOT](../SSOT.md) を正本とする。この依頼書と SSOT が食い違う場合は SSOT を優先し、食い違いを報告すること。

## 1. 依頼の概要

| 項目 | 内容 |
| --- | --- |
| 依頼内容 | 第5章の全部品と第6章の全画面のUIデザイン、および Next.js で動く画面モック一式 |
| 製品 | 小規模ソフトウェア開発組織向けの適合準備・継続的保証（Continuous Assurance）SaaS |
| 利用者 | 直接利用者は、5〜25名程度のソフトウェア開発会社の経営層（経営者、役員、事業責任者、CTO、事業部長、案件スポンサー）と、組織管理者・ポリシー管理者。PM・開発者・QA・顧客は既存システムで活動するプロセス上のアクターで、原則ログインしない（2026-11-28 の SSOT 確定事項）。外部の評価者は期限付きで閲覧する |
| 言語 | 日本語を主とする。英語化できるよう文言は1か所に集約する |
| 対象デバイス | デスクトップのブラウザを主とする（1280px以上）。「スマートフォン対応」と記した画面は390px幅でも全操作ができること |
| 製品名 | 未定。プレースホルダ「Product Name」を使う |

### 製品を一言で

課題・計画管理、カレンダー、Git・CI 上の開発（要求、設計、コード、テスト、承認）を同期し、統制項目（Control）と証跡に対応付ける製品。経営層には複数案件の計画・実績・リスク・判断事項を示し、経営判断を記録する。AIは要約とレビューを補助し、決定論的なルールが機械的に検証できる項目を評価し、権限を持つ人間が意味の判断と承認を行う。すべての結果は、改ざん耐性のある監査証跡として保存する。

訴求の中心は「現場に入力を増やさずに、経営層が案件の最新状況と判断事項を根拠付きで把握できる」こと。規格は裏側の枠組みであり、前面に押し出さない。

2026-11-28 の[機能ギャップ調査](../reserch/gap-analysis-vse-iso29110.md)を受けて、経営、連携と同期、通知とオンコールの画面（6.14〜6.17）を追加し、既存画面を経営層が閲覧・判断する前提に改訂した。ギャップIDと画面の対応は [ギャップ対応表](gap-coverage.md) を参照する。

## 2. 必ず守ること

### 表示と文言の制約

- 「ISO」のロゴ、またはロゴに似た意匠を使わない。製品名、ロゴ案に「ISO」を含めない
- 「ISO認証済み」「AIが適合を判定」「認証を取得できます」など、認証や適合判定を約束する表現を使わない。推奨する表現は「ISO/IEC 29110 の適合準備を支援」
- 規格は「ISO/IEC 29110-4-1:2018」のように正式な番号で参照する
- 規格本文の文章を、画面やサンプルデータに入れない。統制項目は `CTL-PM-001` のような架空の自社IDと、自社で書いた短い説明で表す

### 判断の主体を見分けられるようにする

この製品の核心は「誰が判断したか」の区別。全画面で次の4種類を、色だけに頼らずアイコンとラベルで区別する（部品 `ActorLabel`）。

| 主体 | 意味 | 表示の要件 |
| --- | --- | --- |
| CI | 決定論的なルールによる通過・ブロック | ゲートの結果として最も強く表示する |
| 人間 | 承認者の名前、ロール、時刻を伴う判断 | 誰が判断したかを必ず表示する |
| AI | 下書き、指摘、リンク候補 | 常に「AI・参考」と明示する。通過や合格のように見せない。採用・却下の操作を付ける |
| システム | 受付、署名、保管などの自動処理 | 控えめに表示する |

### 状態の語彙

全画面で同じ語と色を使う（部品 `StatusBadge`）。

| 対象 | 状態 |
| --- | --- |
| ゲート | 通過／ブロック／警告／例外適用中／実行中／未実行 |
| 承認 | 下書き／承認待ち／承認済み／差戻し／取り下げ |
| 要求・設計 | 下書き／レビュー中／承認待ち／承認済み／変更中／廃止 |
| AI所見 | 未確認／採用／却下 |
| 例外 | 申請中／有効／期限切れ／却下／取り下げ |
| リスク・是正 | 未対応／対応中／監視中／完了 |
| 変更要求 | 起票／影響分析中／承認待ち／承認済み／却下／反映済み |
| リリース | 準備中／ゲート確認中／承認待ち／リリース済み／受入済み／差戻し |
| 証跡 | 記録済み／署名済み／保管済み（WORM）／検証失敗 |

| 同期 | 同期中／遅延／古い情報／同期失敗／再認可が必要／初回同期中／停止中／未接続 |
| 案件の健全性 | 順調／注意／遅延／判定不可 |
| 日付の確度 | 確約／目標／予測／実績 |
| 経営判断 | 判断待ち／承認／条件付き承認／保留／却下／担当者へ回付 |
| 事業ケース | 作成中／提出済み／審議中／開始承認／保留／却下／終了 |
| 通知の配信 | 送信待ち／送信中／配信済み／受付済み（配信確認なし）／再試行中／失敗／再処理待ち／集約・抑止 |
| インシデント | 未受領／受領済み／解決（受領と解決を区別する） |
| 外部チェックの異常 | 古いコミットの結果／必須チェックなし／重複／キャンセル／タイムアウト／提供元不明／署名不一致（どれも通過扱いにしない） |
| 重大度 | 緊急／高／中／低／情報 |

ゲートの強制レベルは「警告のみ」「ソフト（例外で通過可）」「ハード」の3段階（部品 `EnforcementBadge`）。判定がどのレベルで出たかを常に添える。

### 出典と鮮度を必ず示す

経営向けの値の多くは、既存システム（課題・計画管理、カレンダー、Git、CI）から同期したもの。同期した値には出典（正本）と最終同期時刻を付ける（部品 `SourceTag`、`Freshness`）。同期が止まった・古いデータがある画面は、上部に `StaleDataNotice` を出し、古い値を最新のように見せない。正本で編集すべき項目は、本サービスに入力欄を置かず「正本で開く」リンクにする。

## 3. ロールと権限

1人が複数ロールを持つことがある（VSE では経営者が PM や技術責任者を兼ねることもある）。画面仕様の「操作」欄の権限は、このロール名で書く。ロールは人名と分けて設定し、役職から閲覧範囲や判断権限を自動で付与しない。

| 区分 | ロール | 所属 | 主な操作 |
| --- | --- | --- | --- |
| 直接利用者 | 経営者 | 開発会社 | ポートフォリオの確認、投資・優先順位・資源配分の判断 |
| 直接利用者 | 役員 | 開発会社 | 担当範囲の案件の確認と判断 |
| 直接利用者 | 事業責任者 | 開発会社 | 事業ケース、便益、ロードマップの判断 |
| 直接利用者 | CTO | 開発会社 | 技術リスク、品質統制、例外の判断 |
| 直接利用者 | 事業部長 | 開発会社 | 事業部内の案件・要員・予算の判断 |
| 直接利用者 | 案件スポンサー | 開発会社 | 担当案件の継続妥当性、重要判断、エスカレーション対応 |
| 直接利用者 | 組織管理者 | 開発会社 | 組織、利用者、連携、プランの管理 |
| 直接利用者 | ポリシー管理者 | 開発会社 | ゲートのルールと Control Pack の管理 |
| アクター | PM | 開発会社 | 計画、進捗、リスク、変更（課題・計画管理で実施） |
| アクター | アナリスト | 開発会社 | 要求の作成・管理（文書・課題管理で実施） |
| アクター | 設計者 | 開発会社 | 設計、ADR、レビュー（Git で実施） |
| アクター | 開発者 | 開発会社 | 実装、PR（Git で実施） |
| アクター | QA | 開発会社 | テスト、検証結果の記録（CI・テスト管理で実施） |
| アクター | リリース管理者 | 開発会社 | リリース準備と承認（リリース管理で実施） |
| アクター | 顧客 | 発注元 | 要求承認、変更承認、受入（期限付きの承認リンク、または顧客ポータル） |
| 外部 | 評価者 | 外部 | 共有された監査パックの閲覧のみ（期限付き） |
| 外部 | パートナー管理者 | コンサル等 | 委任された顧客組織の横断管理 |

アクターは本サービスのアカウントを持たず、外部システムの本人ID（GitHub、Jira、Slack 等）で記録する（部品 `ExternalActor`。対応付けは S-09）。経営層の画面では「経営の判断」と「実務の対応」を分けて示し（部品 `ResponsibilitySplit`）、経営層だけでプロセスを代替したように見せない。

職務分離: 作成者は自分の成果物を承認できない。判断の依頼者は自分の依頼を判断できない。ポリシー管理者は自分が関わる例外を承認できない。AIエージェントは承認、マージ、ポリシー編集、証跡削除ができない。操作できないボタンは非表示にせず無効化し、理由を表示する（部品 `SoDNotice`）。

## 4. 画面の共通仕様

個別の画面仕様に書いていない限り、次を適用する。

### 4.1 レイアウトの種類

| 種類 | 構成 | 使う画面 |
| --- | --- | --- |
| 公開レイアウト | `PublicHeader`、本文（最大幅1120px）、`PublicFooter` | 公開サイト |
| 中央寄せレイアウト | ロゴ、中央のカード（幅480px）、フッターのリンク | サインイン、招待、エラー |
| オンボーディング | ロゴ、`Stepper`（上部）、本文カード（幅720px）、「戻る」「次へ」 | オンボーディング |
| アプリ | `GlobalHeader`（上部固定）、`SideNav`（左240px、折りたたみ可）、`Breadcrumb`、`PageHeader`、本文 | 組織とプロジェクトの画面 |
| 詳細 | アプリのレイアウトの本文を、メイン（左）と `MetaSidebar`（右320px）に分ける | 各詳細画面 |
| ポータル | `PortalHeader`（プロジェクト名、ユーザー）、本文（最大幅800px）。サイドナビなし | 顧客ポータル、評価者ビュー |

### 4.2 一覧画面の共通仕様

- 上部に `FilterBar`（キーワード、状態、担当者、期間など画面ごとの条件）と、右端に主要な操作ボタン
- `DataTable`: 列の並べ替え、50件ごとのページ送り、行のクリックで詳細へ移動、列の表示切替
- 状態: 読み込み中（`Skeleton`）、0件（`EmptyState`。初回と絞り込み結果なしで文言を分ける）、取得失敗（`ErrorState` と再試行）
- 選択した条件はURLに残る前提でデザインする（再読み込みで保持）

### 4.3 詳細画面の共通仕様

- `PageHeader`: ID、タイトル、`StatusBadge`、主要な操作ボタン（最大3つ、残りは「その他」メニュー）
- `MetaSidebar`: 作成者、作成日時、更新者、更新日時、担当者、関連項目、承認状況（`ApprovalPanel`）
- メインの下部にタブ: 「内容」「関連」「履歴」（`Timeline`）「コメント」（`CommentThread`）
- 編集は同じ画面内で編集モードに切り替える。未保存で離れようとしたら `ConfirmDialog` を出す
- 承認済みの項目を編集すると状態が「変更中」に戻ることを、編集開始前に `Banner` で知らせる

## 5. 部品一覧

各部品について、全バリエーションと全状態をデザインすること。モックでは部品ごとに1つのコンポーネントにする。

### 5.1 レイアウト部品

| 部品 | 内容 | バリエーション・状態 |
| --- | --- | --- |
| `PublicHeader` | ロゴ、ナビ（機能、料金、セキュリティ、規格との関係）、「サインイン」、「PoCを相談」ボタン | スクロール時の縮小、スマートフォンではメニューボタンで開閉 |
| `PublicFooter` | 会社情報、利用規約、プライバシー、セキュリティ、お問い合わせ、規格の商標に関する注記 | — |
| `GlobalHeader` | ロゴ、`OrgSwitcher`、`SearchBox`、承認待ちアイコン（件数）、通知アイコン（未読数）、`UserMenu` | 件数0、件数あり、99+ |
| `OrgSwitcher` | 現在の組織名、所属組織の一覧、「組織を作成」 | 1組織のみ、複数、パートナー管理者（管理先組織も表示） |
| `UserMenu` | アバター、名前、メール、個人設定、テーマ切替、サインアウト | — |
| `SideNav` | 組織の項目（ダッシュボード、承認待ち、プロジェクト、ポリシー、設定）と、プロジェクト選択時のプロジェクト項目（概要、計画・管理、要求、設計、トレーサビリティ、検証、ゲート、例外、リリース、監査） | 展開、折りたたみ（アイコンのみ）、現在地、ロールで見えない項目は非表示、件数バッジ |

| `Stepper` | オンボーディングの手順表示 | 完了、現在、未着手、エラー |

## 6. 画面仕様

各画面の書式:

- **目的** — 画面で達成すること
- **利用者** — 主に使うロール
- **構成** — 画面を上から（または左から）順に分けた領域と、そこに置く部品
- **表示項目** — 表や詳細に表示するデータ
- **操作** — ボタンなどの操作、実行できるロール、実行後の結果
- **状態** — デザインが必要な画面の状態（共通仕様の状態は省略）

### 6.1 公開サイト

#### P-01 トップ

- **目的**: 経営層に、複数案件の計画・実績・リスク・判断事項を既存ツールから同期して一画面で示す価値を伝える
- **利用者**: 経営者、役員、事業責任者、CTO（未登録）
- **構成**
  1. ヒーロー: 見出し「全案件の計画と実績、判断事項をひとつの画面に」、説明、「PoCを相談」「機能を見る」、補足（既存のツールを読み取るだけ／開発者のアカウントは不要／判断は AI ではなく人）、ポートフォリオのイメージ（案件ごとの健全性、`SourceTag`、`PlanDates`（compact）、判断待ち）
  2. 課題 4 件: 遅れに気づくのが遅い、判断の根拠が残らない、現場に報告書を書かせている、品質の説明と監査前の証拠集め
  3. 仕組み 4 段: 既存システムから同期（システム）→ AI が要約（AI・参考）→ ルールと CI が検査（CI）→ 責任者が判断（人間）
  4. 主な機能 6 件: ポートフォリオ、計画とカレンダーの同期、経営判断の記録、投資と配分、ゲートと例外、証跡と監査パック
  5. 導入の流れ: 計画とカレンダーを接続 → コードホスティングを接続 → 警告モードで開始 → 段階的に強制
  6. 連携先: 課題・計画管理、共有カレンダー、コードホスティング、チャット、オンコールを `ProviderBadge`（ベータ・予定の表示付き）で列挙
  7. 信頼（学習に使わない、無効化できる、判定はルールと人）、セキュリティと稼働状況へのリンク、規格との関係の注記、CTA
- **対応する要求**: ORG-11, STD-08, 2.4

#### P-02 機能紹介

- **構成**: 機能ごとの節。先頭に経営層向けの 5 節を追加: ポートフォリオ（`SourceTag`・`PlanDates`）、計画とカレンダーの同期（`RoadmapTimeline`、当初・改訂・予測・実績の区別、非公開予定を取り込まない、読み取り専用）、経営判断の記録（`ResponsibilitySplit`）、投資と配分（個人の稼働監視をしない旨）、連携・通知・オンコール。既存の要求管理〜監査パックは維持。「顧客ポータル」は「顧客の承認と受入」に改め、期限付きの承認リンクを主にする

#### P-03 料金

- **構成**: 課金は経営層シート＋プロジェクト数。開発者・PM・QA・顧客は課金対象外であることをリードと比較表に明記。プラン 4 枚（Starter: 2 シート・3 プロジェクト、Team: 5 シート・10 プロジェクト、Partner: 15 シート、Private）。比較表に シート数、プロジェクト数、アクター（課金なし）、計画・カレンダー同期、コードホスティング 4 種、チャット通知、オンコール連携、投資と配分を追加。追加サービスに「追加の経営層シート・プロジェクト」。FAQ に「開発者の分の料金」「GitLab・CodeCommit・Azure Repos」「上限でデータが消えるか」

- **構成**: 開発に関わる人数（25 人以下か）、同時に開発する製品、チーム構成、クリティカリティ（一般／業務上クリティカル／安全）、開発の進め方。結果の `Banner`（対象／要確認（理由の列挙、画面と監査パックに「要確認」と表示）／対象外（「対応」と表示しない））。認証や適合の判定ではない旨
- **状態**: 対象、要専門家確認、対象外
- **対応する要求**: STD-04, SI-14, STD-08

### 6.3 組織の画面

#### O-01 経営ダッシュボード

- **目的**: 経営層が、案件全体の状況と経営判断が必要なことを短時間で把握する
- **利用者**: 経営者、役員、事業責任者、CTO、事業部長、案件スポンサー
- **構成**
  1. 同期が古い・止まっている出典の帯（`StaleDataNotice`。例: Jira の再認可切れ、GitLab の遅延）と「連携の状況」への導線
  2. `StatCard` ×6: 判断待ち（うち3日以内）、遅延・注意の案件（予測が遅れたマイルストーン数）、予算超過見込み、証跡準備度（平均）、対応中のインシデント（未受領数）、7日以内に期限が来る例外
  3. 経営判断が必要なこと: 期限・影響額・重大度順の判断カード（最大4件）。実務上の承認者が別にいるものは回付の案内を表示
  4. 案件の健全性と計画対予測の表: 案件、健全性、終了日（当初→予測とずれ）、予測コスト／予算、証跡準備度、出典と鮮度
  5. 対応の分担（3列）: 経営判断が必要／運用担当の処理（連携の再認可など）／開発チームの対応（外部IDの担当者と出典のツール）
  6. 重大リスクと統制の状況: 影響×発生可能性が高い未完了リスク、ブロック中の PR、期限が近い例外
  7. ゲート運用の指標（既存）
  8. 右列: AIによる要約（参考。元データの ID リンクと確信度。確信度が低いものは警告）、予算・要員の要約（役割別・期間別。個人の稼働は出さない）、データの出典（案件ごとの `SourceTag`）
- **操作**: 各カード・行から詳細へ。ポートフォリオ、スケジュールへの導線
- **状態**: 通常、データが古い（全出典が古い同期時刻）、AI無効（`AIUnavailableNotice`）、空（連携先の接続・案件受付への導線）、読み込み中、エラー
- **対応する要求**: ORG-03、PM-09、4.2.1-10（経営ビュー）、4.2.1-8（同期健全性の可視化）、4.10（経営向け要約に元データと不確実性）、4.11（判断・運用・開発の責任主体を分けて提示、鮮度表示）、2.4／2.5

#### O-02 経営判断（受信箱）

- **目的**: 経営層が判断すべき項目を漏れなく処理し、実務の承認と混同しない
- **利用者**: 経営層
- **構成**
  1. タブ: 判断待ち／担当者へ回付済み／判断済み（件数付き）
  2. 絞込み: 種類（投資、優先順位、要員・資源、リスク受容、例外、リリース・顧客説明、変更・追加費用、予算、便益・継続）、案件（組織全体を含む）
  3. 判断カード: 種類、重大度、ID、期限、タイトル、影響（金額）、案件、依頼者（外部IDのアクターは「外部ID」表示）。並びは期限→影響額→重大度
  4. 実務上の承認者がいる判断には「正しい承認者へ回付」ボタン。回付のモーダルで理由（必須）を入力し、承認者に期限付きの承認リンクと通知を送る
  5. 「実務の承認状況（参照のみ）」: 要求・設計・例外・リリース等の承認依頼を、承認する人（ロール）、依頼者、期限で表示。この画面からは承認しない
- **操作**: 内容を確認して判断（M-02 へ）、回付、判断ログへ
- **状態**: 通常、空、読み込み中、エラー、絞込み結果なし
- **対応する要求**: ORG-04、PM-09、4.8（経営層だけでプロセスを代替しない、実務の承認者の記録を保持）、2.5

#### O-03 通知

- **目的**: 自分宛ての通知と、その配信結果を確認する
- **構成**: 未読／すべてのタブ、重大度・案件の絞込み、通知の一覧（重大度、本文、出来事の種類、案件、日時）。各通知で「配信 N 件」を開くと、チャネルごとの配信状態（`DELIVERY_STATUS`）を表示し、配信ログへ移動できる
- **操作**: 既読・未読、すべて既読、自分の通知設定（S-08）、通知ルール（N-03）
- **状態**: default、empty、loading、error
- **対応する要求**: ORG-05

#### O-04 プロジェクト一覧

- **構成**: 列に 健全性（同期失敗・再認可が必要なら「判定不可」）、スポンサー、終了（予測）（`PlanDates` compact）、計画の出典（`SourceTag` compact。正本がなければ「計画の正本なし」）を追加。`StaleDataNotice`。健全性で絞り込み。「ポートフォリオで比較」。閲覧範囲内の案件のみ表示
- **状態**: 通常、古い情報あり、絞り込み、空、読み込み中、エラー
- **対応する要求**: ORG-03, 4.2.1-8, 4.11

#### O-05 プロジェクトの作成

- **目的**: 開始承認済みの事業ケースからプロジェクトを作成し、計画の正本と版を固定する
- **構成**
  1. 元になる事業ケース（開始承認済みのみ。作成済みは選べない）。なければ案件受付への導線
  2. 基本情報（名前、ID、顧客とスポンサーは事業ケースから引き継ぐ、データ分類）
  3. 進め方と用語: アジャイル／反復・段階型／ウォーターフォール、製品の工程（計画〜納入）と案件での呼び方の対応表（ガイドの例示を必須にしない）
  4. 計画の正本と連携: 計画の正本、共有カレンダー、対象リポジトリ、同期の方向（読み取りのみ）
  5. 統制のセットと版の固定: プロファイル、Control Pack、ゲートのルール（ハッシュ）、テンプレート、強制レベル、固定の確認者（ポリシー管理者）。変更には移行レポートと承認が必要
  6. 実務の担当（外部ID）: PM、QA、リリースの承認者、顧客の承認者（期限付きの承認リンク）。`ExternalActor` 表示。QA とリリース承認者の兼務を警告
- **状態**: 通常、入力エラー、職務分離の警告、承認済みの事業ケースなし
- **対応する要求**: STD-03, SI-14, PM-11, ORG-01, 4.8

#### O-06 横断検索

- **構成**: 種類に 案件、判断、計画（マイルストーン）、会議、リスク、インシデント を追加し、PR は「PR・CI」に。同期した項目は出典の `ProviderBadge` を表示。閲覧範囲外の項目は件数も含めて出さない
- **状態**: 通常、初期、閲覧範囲で検索（説明の `Banner`）、0件、読み込み中、エラー
- **対応する要求**: ORG-06

### 6.4 プロジェクト: 計画と管理

- **対応する要求**: SI-13

- **操作**: 「ファイルを取り込む」（`Modal`: ファイル、種類、構造化データの形式、データ分類、閲覧できる人、関連付ける項目。Highly Confidential は AI に送らない旨）
- **状態**: 一覧の共通状態、形式エラーのみ、取込みモーダル
- **注意**: docs-as-code は必須にしない。形式エラーの文書は取込みを保留し、証跡として扱わない

### 6.5 プロジェクト: 要求・設計・トレーサビリティ

#### R-01 要求一覧

- **目的**: 要求の状態、承認版、受入基準、設計・テストへのつながりを一覧で確認する
- **利用者**: 経営層（閲覧）、組織管理者
- **構成**: 見出し（説明、`SourceTag`: docs/requirements と件数、操作: CSV 出力・正本で開く）、閲覧専用の注記、`FilterBar`（状態、種類、担当者、リンクの欠落、AI所見）、トレース率の `CoverageMeter`、`DataTable`（REQ-ID、タイトル、種類、優先度、状態、担当者 `ExternalActor`、出典※、正本ファイル※、承認版（再承認待ちの版を併記）、承認者※、受入基準、設計、テスト、AI所見、更新日時。※は初期非表示）
- **操作**: 行を選んで「承認者に依頼」（R-04）、行クリックで R-02
- **状態**: 通常、読み込み中、空（正本に要求がない／未連携。連携の確認へ）、絞り込み結果0件、エラー、同期遅延（`StaleDataNotice`）
- **対応する要求**: SI-01, SI-02, 4.11（正本と同期時刻の表示）

#### R-02 要求の詳細

- **目的**: 1件の要求の内容、承認版の固定、状態遷移、承認記録、下流へのつながりを根拠付きで確認する
- **利用者**: 経営層（閲覧）
- **構成**
  1. 見出し: REQ-ID、タイトル、状態、版、承認版タグ（ロック）、未確認のAI所見数、`SourceTag`。操作: 正本で開く、版を比較（R-05）、AIの所見（R-03）、（承認待ち・変更中のとき）承認者に依頼（R-04）
  2. タブ「内容」: 本文、受入基準（なければ警告）、種類・優先度・出典・版・正本ファイル・関連課題
  3. タブ「トレース」: 設計→コード／PR→テストケース→実行結果→検証→妥当性確認→リリース成果物のリンク表（記録された場所、確定者。AI候補は「AI候補・未確定（確信度）」）
  4. タブ「承認と状態遷移」: 版ごとの承認記録表（役割、承認者、結果: 承認／未判断／差戻し／無効、記録場所、日時。職務分離で無効になった承認も理由付きで残す）、状態遷移のタイムライン（遷移、版、記録場所、理由）
  5. タブ「AIの所見」（R-03 の埋め込み）、「コメント」（正本から同期）
  6. 右列: 状態と `StateFlow`、承認版の固定（版、日時、内容のハッシュ）、担当者、現在の版の承認（`ApprovalPanel` は判断不可・注記「承認者本人が正本または期限付き承認リンクで行う。経営層は代行しない」）、データ分類、関連する変更要求
- **状態**: 通常、承認済み、変更中（承認版 v3 のまま v4 が再承認待ち。差分への導線）、承認待ち、職務分離（作成者の承認を数えない `SoDNotice`）、差戻し（理由と日時）、廃止、同期遅延、読み込み中、エラー
- **対応する要求**: SI-01, SI-02, SI-04, 4.8（作成者と承認者の分離、承認後の版変更による失効）

#### R-03 AI要求レビュー

- **目的**: AIの指摘を人が判断し、要求の品質を上げる
- **構成**: 左に要求の本文（指摘箇所をハイライト。ハイライトを押すと右の所見へ移動）、右に `AIFindingCard` の一覧（種類ごとにまとめる: 不審な指示、曖昧性、矛盾、テスト可能性、不足）。上部にレビュー実行の情報（実行者、日時、モデル、テンプレートのバージョン、対象の版）
- **操作**: 所見ごとの採用（本文の修正画面へ。提案文を挿入可）・却下（理由必須）、「再レビュー」
- **状態**: 実行中、所見0件、本文が更新され所見が古い（`Banner` と再レビューの案内）、本文にAIへの指示とみられる文がある（`Banner`（失敗）: AIは従っていないこと、確認を依頼した相手を表示し、該当箇所をハイライト）、AI無効

#### R-04 要求の承認依頼

- **目的**: 選んだ要求の承認を、実際の承認者に期限付き承認リンクで依頼する
- **構成**: `Modal`。対象要求の表（状態、受入基準、未確認のAI所見、除外）、承認者（顧客・PM。作成者は選べない）、リンクの有効期限、依頼メッセージ
- **操作**: 「依頼する」→ 承認者ごとに1回だけ使えるリンク（`/approve/<token>`、送信先メール、メールの確認コードで本人確認、有効期限）を一覧表示
- **状態**: 条件を満たさない要求を含む、すべて条件を満たす、送信済み
- **対応する要求**: SI-02, 4.8（承認依頼・期限・本人確認）, ORG-07（期限付き承認リンクでの外部承認）

#### R-05 要求の版比較

- **目的**: 要求の版の差分と再承認の要否・状況、旧版（承認版）の証跡の保持を確認する
- **利用者**: 経営層（閲覧）
- **構成**: 見出し（状態、`SourceTag`、要求に戻る、正本の履歴を開く）、再承認が必要／再承認済みの `Banner`、比較元・比較先の版の選択（承認版を明示、各版の保存者・日時・理由）、本文の `DiffViewer`、受入基準の差分（追加／削除／変更なし）、再承認の状況（その版の承認記録、承認者に再依頼）、旧版の証跡（承認版、承認日時、内容のハッシュ、承認者、記録先の Evidence Manifest）、影響を受ける設計・テストの一覧
- **状態**: 通常（REQ-0008: 承認版 v3 → v4 再承認待ち）、再承認済み、比較できる版がない、読み込み中、エラー
- **対応する要求**: SI-01（変更前後の比較）, SI-02（承認版の固定、再承認）, SI-05, 6.1（承認済み要求の改訂は差分・再承認・旧版証跡を残す）

#### D-01 設計・ADR 一覧

- **構成**: `SourceTag`（docs/design）、閲覧専用の注記、`FilterBar`、`DataTable`（ID、タイトル、種類、状態、対応する要求、作成者・レビュー者 `ExternalActor`、代替案の数、正本※、更新日時）。「作成」ボタンは廃止し「正本で開く」

### 6.6 プロジェクト: ゲート・PR・例外

#### G-01 ゲート実行の一覧

- **目的**: 接続したすべての Git サービスの PR／MR とブランチについて、ゲート A〜D の判定を確認する
- **利用者**: 経営層（閲覧）、ポリシー管理者
- **構成**: `StatCard`（ブロック中、例外適用中、実行中、通過率）、`FilterBar`（提供元、判定、ブロックしたゲート、作成者の種類、ブランチ）、表（実行ID、対象＝PR／MR 番号・タイトル・リポジトリ・ブランチ、提供元 `ProviderBadge`、コミット、作成者 `ExternalActor`、ゲート A〜D、総合判定、強制レベル、ポリシー、実行日時）

- **状態**: 読み込み中、0件、絞り込み結果0件、エラー

#### G-02 ゲート実行の詳細

- **目的**: 判定の理由と根拠を、ルール・統制項目・判定主体・証跡まで辿れる形で示す
- **構成**

  2. ゲートごとの `GateResultPanel`
  3. ルールと判定の根拠（表）: ルールID、説明（自社作成）、対象の統制項目（V-02 へのリンク）、判定の主体（CI／人間）、必要な証跡、結果、修正案
  4. 入力した外部チェック結果（表）: チェック名、提供元、コミット、結果、扱い、受信日時。異常（`CHECK_ANOMALY`: 古いコミットの結果、必須チェックなし、重複、キャンセル、タイムアウト、提供元不明、署名不一致）はどれも「通過として扱わない」と表示する
  5. 必要な人間の承認（ゲートC）: 経営層の画面からは承認しない。承認は Git サービス上のレビューで行われ、外部IDで記録される
  6. AIの参考所見（判定に使わない）
  7. 判定の再現情報（ポリシー版・ハッシュ、入力スナップショット、CI 実行ID、コミット）と「保存済みの入力で判定を再現」（G-06）

- **状態**: 通過、ブロック、警告、例外適用中、実行中、新しいコミットで失効（失効した判定・承認・外部チェックを列挙し、最新の実行へ誘導）、外部チェック結果の異常

- **構成**: `FilterBar`（提供元、作成者、レビュー）、表（PR／MR 番号・タイトル・リポジトリ、提供元、作成者 `ExternalActor`、ゲート、レビュー、対応する要求、更新日時）。用語は提供元に合わせる（GitLab は MR）

#### G-04 ゲートの適用設定

- **目的**: ゲートの強制レベルを段階的に上げ、適用範囲・停止・再開を統制する
- **利用者**: 経営層（CTO・経営者は承認）、ポリシー管理者（申請）
- **構成**
  1. 承認待ちの変更（`Banner`。承認は申請者以外の CTO または経営者）
  2. 段階導入の状況（警告のみ → ソフト → ハード。各段階の意味と適用日）
  3. 適用範囲ごとの強制レベル（表）: 範囲（プロジェクトの既定／ブランチ／リリース）、対象、強制レベル、適用開始、次の段階（承認状態）。狭い範囲が優先
  4. ゲートの種類（表）: PR／MR（A〜D）、マイルストーン、顧客承認、リリース、受入。判断のきっかけ、強制レベル、状態（一時停止中は再開予定日）

- **状態**: 承認待ちあり、承認待ちなし、一時停止中、閲覧のみ（`SoDNotice`）、読み込み中、エラー
- **対応する要求**: 4.4-3, 4.4-5, 4.4-7

#### G-05 必須チェックの登録状況

- **目的**: ゲートが各 Git サービスで必須として登録され、ブランチ保護が保たれていることを確認する
- **構成**

- **状態**: 問題あり、すべて登録済み、読み込み中、対象なし（連携と同期へ誘導）、エラー

#### G-06 判定の再現

- **構成**: 再評価の入力（入力スナップショット、コミット、元の判定日時、元のルール版とハッシュ、再評価に使うルール版の選択、判定の主体）、結果の `Banner`（一致／不一致）、比較表（総合判定、ゲート A〜D、理由のルールID、Manifest のダイジェスト）、不一致の原因
- **操作**: 再評価する（外部サービスに問い合わせない）、ゲート実行の詳細・Evidence Manifest へ
- **状態**: 一致、不一致（ルール版の違い、保管済み入力のハッシュ不一致）、未実行、実行中、入力を読み込めない
- **対応する要求**: 4.4-2, 6.1

#### E-01 例外の一覧

#### E-03 例外の詳細・承認

  8. 右列: 状態遷移、リリース承認（実務の承認者が Git サービス上で承認し外部IDで記録。経営層の画面からは承認しない）、受入の状況、属性
- **操作**: Go/No-Go を判断（`Modal`: Go／条件付き Go／No-Go、理由必須、条件付きは条件必須）、受入の状況へ、構成管理へ

### 6.8 証跡と監査

#### V-01 監査ダッシュボード

- **目的**: 統制項目ごとの証跡の準備状況を確認し、評価前に対応すべきことを把握する
- **利用者**: 経営層（要約）、組織管理者、ポリシー管理者
- **構成**
  1. 経営向けの要約: 充足・一部充足・欠落・例外・検証失敗の件数と、評価前に対応が必要な項目。項目ごとに `ResponsibilitySplit`（経営判断／実務の対応）と、実務担当を `ExternalActor` で示す。「適合の判定や認証ではない」と明記
  2. `StatCard` ×4: 充足率、欠落している証跡、検証に失敗した署名（V-07 へ）、有効な例外
  3. 活動別のカバレッジ（PM 4 活動・SI 6 活動の棒）
  4. 統制項目の表: ID、説明（自社）、層、充足状態（検証失敗を含む）、証跡（逆引き。統制項目→証跡ID）、機械検証、人間承認、証跡数、最終更新
- **状態**: 通常、読み込み中、統制項目0件、エラー。検証失敗のある統制項目は「検証失敗」と表示し、充足に数えない
- **対応する要求**: 4.9-6、STD-08、4.11

#### V-02 統制項目の詳細

- **構成**: 規格から証跡までの連鎖（統制項目 → プロセス領域 → 組織の手順 → 成果物（出典と鮮度の `SourceTag`）→ 機械ルール・人の判断（`ExternalActor`）→ Evidence Manifest）、根拠の参照（番号と箇条番号のみ）、検証方法、紐づく証跡、例外、属性、組織での調整
- **状態**: 充足、一部充足、欠落、例外適用中、検証失敗（`Banner`（失敗）。充足として扱わない）
- **対応する要求**: STD-02、4.9-6

#### V-03 Evidence Manifest 一覧

- **構成**: ID、対象、作成日時、スキーマの版、署名、直近の検証（一致／失敗の理由）、保管、承認の数。ヘッダーから V-07 へ
- **対応する要求**: 4.9-1、4.9-2

#### V-04 Evidence Manifest の詳細

- **構成**
  1. 署名の検証結果
  2. 内容の要約
  3. スキーマと版: スキーマ、プロファイル仕様（番号のみ）、Control Pack、ゲートのルール、テンプレート、ポリシー
  4. ダイジェスト一覧（ファイル、SHA-256、サイズ。不一致を強調）
  5. 承認（承認者は外部IDで記録）、AIレビューの記録（モデル・テンプレート・入出力のハッシュ）、例外
  6. 検証の履歴（日時・結果・理由・実施）、生データ（JSON）
  7. 側面: 保管先、保管先ロケーター、保持期限
- **状態**: 検証成功、失敗（ハッシュ不一致）、失敗（証明書・鍵の期限切れ）、失敗（保管先にない）、未署名、保管待ち。失敗はどの理由でも証跡として扱わない
- **対応する要求**: 4.9-1、4.9-2、6.5

#### V-05 監査ログ

- **構成**
  1. 連鎖ハッシュの検証結果: 欠番・不一致なし、または不一致の連番
  2. 表: 連番、日時、主体、操作、対象、変更前 → 変更後、連鎖ハッシュ、詳細（event_id、prev_hash）
  3. CSV／JSON 出力
- **状態**: 通常、改ざん検出（`Banner`（失敗）。該当する連番を赤で表示し、WORM の写しと照合して通知）、読み込み中、0件、エラー
- **対応する要求**: 4.9-5

#### V-06 監査パックの出力

- **構成**
  1. 範囲（リリースまたは期間）
  2. 含める内容: 対応表（出典と同期日時を含む）、成果物（納入物）、証跡、Manifest、承認、例外、監査ログ、ファイルハッシュの一覧と検証手順
  3. 生成後に表示するもの: パック内のファイルと SHA-256 の一覧、期限付き共有（V-08 へ）
  4. 過去の出力
- **対応する要求**: 4.9-7

#### V-07 署名と検証

- **目的**: 署名鍵と透明性ログの状態、検証の失敗とその理由を確認する
- **利用者**: 組織管理者、CTO（鍵の切替の承認）
- **構成**
  1. 検証失敗の `Banner`（理由別の件数。該当の統制項目は充足に数えない）
  2. `StatCard`: 検証済み、検証失敗、最終の定期検証
  3. 署名鍵の表: 鍵の別名、状態（使用中／切替予定／検証のみ／失効）、管理先（KMS 等）、方式、指紋、作成日、切替日。秘密鍵は取り出せない
  4. 鍵の切替の申請（CTO が承認。申請者は承認できない）
  5. 透明性ログ（記録先、状態、最終の記録、件数）
  6. 検証の履歴（すべて／失敗／一致）
  7. 失敗の理由の説明（ハッシュ不一致、証明書・鍵の期限切れ、保管先にない、鍵の失効）
  8. 評価者による独立した検証（VERIFY.md）
- **状態**: 通常、鍵の切替が近い、透明性ログの停止（署名を保留キューに入れる）、読み込み中、エラー
- **対応する要求**: 4.9-2、6.5

#### V-08 共有リンクとアクセス記録

- **目的**: 評価者への期限付き・読み取り専用の共有を管理し、アクセスを監査する
- **構成**
  1. 拒否したアクセスの `Banner`
  2. 共有リンクの表: ID、監査パック、宛先、範囲、期限（残り日数）、状態、保護（メール認証、DL可／閲覧のみ）、閲覧数／DL数、最終アクセス、失効
  3. アクセス記録: 日時、共有、操作（閲覧／ダウンロード／拒否）、人、対象、結果、接続元（一部を伏せて表示）。共有ごとに絞り込める
- **操作**: 失効（`ConfirmDialog`）。期限の延長は新しい共有として発行し、発行者と承認者を記録する
- **状態**: 通常、拒否あり、0件、読み込み中、エラー
- **対応する要求**: 4.8（評価者共有）、4.9-7、6.5

### 6.9 ポリシーと Control Pack

#### C-03 組織での調整

- **構成**
  1. 基準版を上書きせず、差分として保存する旨の `Banner`
  2. 表: 調整の種類、内容・理由、代替手段・リスク、有効期間・基準版、申請者 → 承認者、状態
  3. 申請の Drawer: 種類、内容、理由、代替手段、リスク、有効期限、承認者（申請者は選べない）。必須項目は理由・リスク・有効期限・承認者

#### C-04 ポリシーのバージョン比較（Should）

- **構成**: プロジェクトごとの影響、新たに未充足になる項目、実行記録（作成・承認・対象除外・実行。旧版での判定は保持）、承認（ポリシー管理者と CTO）
- **対応する要求**: STD-06

#### C-06 適用範囲の確認

- **目的**: 案件が Control Pack の想定範囲かを示し、範囲外の案件に「対応」と表示しない
- **構成**: 案件ごとの総合結果（対象／対象外／要専門家確認）と、項目の表（人数、製品数、チーム数、クリティカリティ、開発形態：記録した値／想定／結果）。範囲外・要確認の場合の扱い。「適合の判定ではない」と明記
- **状態**: 通常、0件、読み込み中、エラー
- **対応する要求**: STD-04

#### C-07 出典と利用許諾

- **目的**: 参照する規格文書の入手と利用許諾の状態を管理する
- **構成**: 本文を保存しない方針の `Banner`、許諾が未確定の文書の警告（Gate 0）、文書の表（正式番号、用途、入手状況、利用許諾、利用できる範囲（DB収録・プロンプト・テスト）、条件、担当・確認日）、ロゴ・認証表示を使わない注記
- **対応する要求**: STD-07、STD-08

#### C-08 Control Pack のレビュー記録

- **目的**: Control Pack の承認者・レビュー版・差戻し・適用判断と、評価者からの形式フィードバックを残す
- **構成**: 対応中の差戻しの `Banner`、レビューと承認の表（ID、版、種類、レビュー者・役割、日付、内容、状態）、評価者からのフィードバック（テーマ、内容、対応、状態）。評価者のフィードバックは適合の判断ではない旨を明記
- **操作**: レビューを依頼
- **状態**: 通常、0件、読み込み中、エラー
- **対応する要求**: STD-09

### 6.10 設定

#### S-01 組織の設定

- **構成**: 組織名、表示ID、ロゴ、タイムゾーン、既定の言語（日本語標準・English）、日付の表示形式、氏名の表示順、週の始まり、年度の開始月、営業日カレンダー（祝日・年末年始）、通貨。組織削除の影響に連携と取り込んだ複製の削除を追記
- **対応する要求**: ORG-09, 4.11, 4.2.1-5

#### S-02 利用者とロール

- **目的**: 直接サインインする利用者（経営層、組織管理者、ポリシー管理者）を管理する
- **構成**

  2. 職務分離のチェック（ポリシー管理者の不在、判断者が 1 名のみ、ポリシー管理者と CTO の兼務）

  4. 一覧: 利用者（役職）、ロール、閲覧範囲の要約、サインイン方式と MFA、最終アクセス、状態、操作（ロール変更、閲覧範囲と判断権限、MFA の再設定要求、無効化）

#### K-02 連携の追加

- **目的**: 取得するデータと書込みの用途を確認したうえで、外部サービスを接続する
- **利用者**: 組織管理者
- **構成**（`Stepper`: 種類 → サービス → 接続先 → 権限と取得データ → 対象範囲 → 正本 → 確認）
  1. 種類: `OptionCard`。計画管理と共有カレンダーに「優先」を表示
  2. サービス: ベータ・予定・非推奨（Opsgenie）を表示。予定は選択不可、非推奨は警告。CodeCommit 選択時は計画管理を別途接続する案内
  3. 接続先（ホスティング境界）: GitHub.com／Enterprise Cloud／Enterprise Server、GitLab.com／Self-Managed、Azure DevOps Services／Server、AWS アカウント ID・リージョン・引き受けるロールの ARN。自社運用は URL と TLS 検証の説明
  4. 権限と取得データ: 権限ごとの用途と読み取り／書込みの区別。資格情報は暗号化して保管し、組織・リポジトリ単位で分離し、画面・ログに出さない旨
  5. 対象範囲: カレンダーは共有カレンダーのみ（個人の予定表は既定で対象外）、非公開予定の除外、取得する項目の最小化（本文・参加者一覧は既定で取得しない）。個人予定を含めた場合は警告。SCM はリポジトリの選択
  6. 正本: 正本にする／参照のみ。初期は読取一方向で、ゲート結果の書込み以外は書き戻さない
  7. 確認: 設定の一覧と、初回は全件、以降は差分の説明
- **操作**: 戻る、次へ、接続して初回同期を始める（K-03 の初回同期中へ）
- **状態**: 各ステップ、権限不足（ステップ4でエラー。読み取りのみの接続ではゲートを必須にできない旨）、接続失敗（確認でエラー、問い合わせ用ID、再試行）
- **対応する要求**: SCM-02、SCM-09、SCM-10、4.2.1-1、4.2.1-6、4.2.1-13、4.5.2（AWS アカウント・リージョン、IAM ロール）、4.5.4、4.7（Opsgenie の非推奨）

  3. `StatCard`: 最終成功、最終試行、同期の遅れ、対象数
  4. タブ「同期の状態」: 方式、周期、差分の位置（カーソル／syncToken／deltaLink）の有効・失効（失効時は全件再同期）、次回の実行、エラーの詳細。Webhook の検証方式・結果・最終受信・24時間の検証失敗。レート制限の残量と回復時刻、429 と Retry-After に従った待機（重複送信しない）。欠落期間の再取得（期間、状態、補完件数）。このサービスで使える能力の要約（K-04 へ）

#### K-06 正本と同期ルール

- **目的**: 項目ごとの正本、同期の方向・周期、日付とカレンダーの扱い、削除時の扱いを決める
- **利用者**: 組織管理者
- **構成**

- **操作**: 保存
- **状態**: 通常、正本どうしの食い違い（`Banner`: 正本の値を表示し、PM に通知。どちらも書き換えない）、読み込み中、エラー
- **対応する要求**: 4.2.1-1、4.2.1-3、4.2.1-5、4.2.1-6、4.2.1-7、4.2.1-13、4.2.1-14、6.4（日付の境界、取消・移動の区別、当番表との分離）

#### K-07 受信イベントと再同期

- **目的**: 受け取ったイベントが正しく一度だけ処理されたことを確かめ、失敗を再処理する
- **利用者**: 組織管理者
- **構成**
  1. `StatCard`: 24時間の受信、重複として無視、署名の不一致（拒否）、再処理待ち
  2. 署名不一致を拒否した場合の `Banner`（本文は保存しない）
  3. 処理の順序: 署名・送信元の検証 → 配信 ID で重複除外 → SHA と発生時刻で順序確認 → 共通データへ変換 → コミット変更で古い結果・承認を失効 → 記録（指数バックオフ、上限で再処理待ち）
  4. イベントの表（`FilterBar`: 結果、送信元、検索）: 受信日時、送信元、種類、対象と SHA、配信 ID、署名、結果（処理済み、重複、順不同、再試行中、再処理待ち、拒否、照合して補正）、試行回数、内容
  5. 欠落期間の再取得の表
  6. 特別なイベントの扱い: force-push、PR／MR の再作成、フォーク、マージコミット、削除、リポジトリの移管、利用者の退職・権限変更
- **操作**: 再処理（再処理待ち）、今すぐ再試行（再試行中）
- **状態**: 通常、0件、読み込み中、エラー
- **対応する要求**: SCM-01、SCM-03、SCM-04、SCM-05、SCM-06、4.2.1-9、4.5.2（再送、PR 再作成、フォーク、マージコミット、force-push、削除、退職、移管）、5.2、6.2

#### K-08 初期インポートと診断

- **目的**: 既存プロジェクトを取り込み、経営ダッシュボードに出す前にデータの欠けや重複を直す
- **利用者**: 組織管理者
- **構成**
  1. 初回の取込みの表: 対象、進捗、件数、状態（完了・取込み中・失敗と理由）
  2. `StatCard`: 重複ID、未リンク、日付の欠損、同期の停止
  3. 同期停止がある場合の `Banner`（その案件は「判定不可」）
  4. 診断の結果の表（重大度順）: 種類、対象、内容、直し方。直すのは正本の側で、本サービスに入力し直さない
- **操作**: 診断を再実行、対応付け（K-05）、連携を開く（K-03）、正本で開く
- **状態**: 通常、取込み中、問題なし、読み込み中、エラー
- **対応する要求**: 4.11（初期インポートと差分同期、重複ID・未リンク・日付欠損・同期停止の診断、入力の重複を避ける）

## 9. 実装の制約（Rust 側への移植のため）

受け取った Next.js のモックは、Rust のバックエンドと組み合わせる形に移植する。移植しやすくするため、次を守ること。

- **画面は表示専用にする**。業務ロジック（ゲート判定、権限判定、状態遷移）を書かない。表示に必要な値と「操作できるか・できない理由」はすべて props で受け取る
- **Next.js 固有のサーバー機能を使わない**。Server Actions、Route Handlers、Middleware、サーバーでのデータ取得を使わない。`next/image`、`next/font` などに依存しない
- **データはモックで与える**。型付きの固定データを1か所に置き、ページはそれを読み込んで描画する。型も1か所にまとめる。項目名は将来のAPIに合わせて英語の snake_case にする
- **スタイルはCSS変数のデザイントークンと素のCSS（CSS Modules 可）にする**。実行時の CSS-in-JS は使わない。Tailwind を使う場合はトークンをCSS変数で定義する
- **依存ライブラリを最小にする**。UIライブラリやグラフ描画ライブラリを使う場合は、事前に名前と理由を挙げる
- **部品は第5章の名前で作る**。画面ファイルの冒頭に画面IDをコメントで書く
- **文言は辞書ファイルに集約する**
- **外部通信をしない**。アナリティクス、外部フォント、CDN、外部画像を読み込まない
- **サンプルデータは架空のもの**にする。実在の会社名、人名、ISO 規格本文を使わない
